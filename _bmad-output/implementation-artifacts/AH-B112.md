# AH-B112 — Lock the intent-overlap counter's read-modify-write in intents.hit()

## Reproduction

1. Hold a claim on `shared.py` in worktree B, and edit `shared.py` from worktree A in one session.
2. Issue two edits at once, as parallel tool calls do, so two hook processes call
   `intents.hit()` for the same session, worktree and path.
3. Both read the counter file before either writes it; both compute 1 and both write 1.
4. Observed: both edits get `warn`. Expected: one `warn` and one `deny`.

The test in `tests/test_intents.py` reproduces it in one process by widening the window between
the read and the write and starting two threads at a barrier.

## Root cause

`hit()` reads the per-session counter JSON, increments it and writes it back through
`_write()`. The atomic rename in `_write()` stops a torn file but not a lost update: nothing
serializes the read-modify-write, so two callers can both read the old value.
[Source: lib/harness_core/intents.py#hit]

## Acceptance criteria

1. **Given** one claim and no prior hits, **when** two `hit()` calls for the same session,
   worktree and path run concurrently, **then** they return 1 and 2, so the `deny` variant answers
   one `warn` and one `deny`, and the stored count is 2.
2. **Given** the lock cannot be taken (no `fcntl`, or the lock file cannot be opened), **when**
   `hit()` runs, **then** it counts unlocked as before and never raises, because a failure to lock
   must never be what blocks an edit.
4. **Given** another process holds the lock, **when** `hit()` runs, **then** it counts unlocked
   after at most `HITS_LOCK_BUDGET` seconds instead of waiting for the holder.
3. **Given** the existing per-worktree counter tests, **when** the suite runs, **then** they pass
   unchanged.

## Design

A `_hits_lock(directory)` context manager takes `fcntl.flock(LOCK_EX)` on one `.lock` file in the
hits directory and `hit()` runs its read, increment and write inside it. Closing the stream
releases the lock.

- One lock file for the directory rather than one per counter, so `sweep()` and `release()`, which
  glob `*.json`, have no lock files to age out. Contention is negligible: a hit happens only on an
  overlapping edit.
- `fcntl` is imported optionally, as `claude/hooks/approvals.py` does; any `OSError` degrades to
  the unlocked count.
- `LOCK_EX | LOCK_NB` polled every 10 ms for at most 0.5 s (`HITS_LOCK_BUDGET`), then the unlocked
  fallback: a blocking lock held by a stuck process would stall the edit hook until the runtime's
  PreToolUse timeout, while ordinary contention clears in milliseconds and still serializes.
- Must not change: the counter file format, its path, `answer_for()` or any hook.

## Regression test

`ConcurrentHitTests.test_two_concurrent_hits_on_one_claim_warn_once_and_deny_once` in
`tests/test_intents.py` patches `intents._read` to sleep 0.3 s after reading, starts two threads
at a barrier, and asserts counts `[1, 2]`, answers `warn` and `deny`, and a stored count of 2.
Against the pre-fix module it fails with `[1, 1] != [1, 2]`.

`test_two_concurrent_edits_through_the_hook_warn_once_and_deny_once` drives the real path: one
claim, two concurrent `lifecycle.dispatch()` edits, each in its own process because dispatch
captures hook output through the process-wide stdout, with `Path.read_text` slowed for counter
files because the hook loads its own copy of the ledger. Pre-fix both edits are warned.
`test_a_held_lock_falls_back_to_an_unlocked_count_within_the_budget` holds the lock and asserts
`hit()` returns within the budget.
