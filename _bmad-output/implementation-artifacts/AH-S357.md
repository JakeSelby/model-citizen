## Story

As a maintainer, I want every paid run and every apply started from the CLI to need a person's confirmation, so that an agent driving the Studio loop cannot spend money or change the live configuration on its own.

## Context and value

#998 lets agents drive the Studio loop from the CLI. Today a paid run or an apply goes through with a spend token or a revision, and no person confirms it. The harness already has a channel for this: the command grader asks, an `approve <code>` reply lets one command through in `auto` mode, and `bypassPermissions` uses the confirm marker (`docs/runtime-controls.md`).

## Acceptance criteria

1. A CLI command that spends (a paid replay, eval, native or draft-test run) or applies a draft asks for a person's confirmation through the harness approval channel in every permission mode; in `auto` mode it is refused with an approval code that covers that exact command once.
2. An agent cannot confirm its own command: a token, a revision, an environment variable or a marker the agent writes does not count as confirmation.
3. The Studio's own buttons keep their confirmation dialog, and the activity log records that a CLI spend or apply was confirmed.
4. Free commands (status, reports, plans and dry runs) need no confirmation.
5. Tests cover each criterion, including an agent-written bypass that is refused.

## Design

### Approach

Grade the Studio's spending and applying CLI commands as asks in the command grader, so the existing approval channel confirms each one, and make the CLI refuse a spend or apply that did not pass through it.

### Decisions and alternatives

- Reuse the grader's channel rather than a Studio-only prompt, so confirmation works the same in every runtime and the agent cannot grant it.
- Open for the builder: how the CLI proves the confirmation happened, for example a one-time grant that only the approval path writes. Whatever it is, an agent must not be able to write it.
- Built (second round, after review found a same-user grant, a terminal `yes` and a pre-written prompt grant all forgeable): the CLI, and each Studio spend route on both faces, ask macOS LocalAuthentication for Touch ID or the login password at the moment they would spend or apply (`lib/harness_core/presence.py`). The grader stays as a first layer that asks or refuses and files nothing.
- Conservative defaults taken where the story was open: the confirm marker counts in no mode for these commands, so `bypassPermissions` uses the approval code too; Codex refuses; `draft rollback` and `draft recover` count as applies; a spend hidden in a substitution, inline interpreter text or an unread wrapper is refused in every mode; where presence cannot be shown (off macOS, no desktop session, Codex) the CLI and the Studio refuse; the Studio's own spend routes ask too, so a session or bootstrap token alone spends nothing.

### Do not implement

- A new approval interface.
- Changes to the Studio's own confirmation dialogs.

### Completion notes

- `grade-bash.cli_confirmation` classifies paid starts and applies and answers ask, deny with an approval code, or pass, ahead of the stance threshold and the marker; it files nothing, and refuses inline interpreter text that names a spend.
- `presence.confirm` is the one function that can say yes: `/usr/bin/osascript` by absolute path, a fixed JXA script and a fixed environment, evaluating `LAPolicyDeviceOwnerAuthentication`. Inputs only make it refuse.
- The CLI asks it for `runs start --confirm-spend` and `draft apply|rollback|recover`; the replay, eval, native and draft-test start handlers ask it on both faces, after the request is checked and before the run starts. A Studio apply runs the CLI, which asks.
- Each confirmation appends a `studio.person-confirmed` event to the decision ledger whatever `telemetry.decisions` says; Activity titles it "Spend or apply confirmed in person".
- The suite never raises the real dialog: `isolation.stub_presence` switches it off in children and answers yes in-process; `tests/presence_stub_cli.py` runs a child CLI as a person who said yes.
- Residual, documented: an agent running its own Python against the run library is outside any same-account check.
- The CLI asks before it validates the draft, revision or apply id, so a request that would fail its lookup still raises the dialog; asking after the lookup would need a hook inside the apply, rollback and recover locks.
