## Story

As a maintainer, I want every paid run and every apply started from the CLI to need a person's confirmation, so that an agent driving the Studio loop cannot spend money or change the live configuration on its own.

## Context and value

#998 lets agents drive the Studio loop from the CLI. Today a paid run or an apply goes through with a spend token or a revision, and no person confirms it. The harness already has a channel for this: the command grader asks, an `approve <code>` reply lets one command through in `auto` mode, and `bypassPermissions` uses the confirm marker (`docs/runtime-controls.md`).

## Acceptance criteria

1. A CLI command that spends (a paid replay, eval, native or draft-test run) or applies a draft asks for a person's confirmation through the harness approval channel in every permission mode; in `auto` mode it is refused with an approval code that covers that exact command once.
2. An agent cannot confirm its own command: a token, a revision, an environment variable or a marker the agent writes does not count as confirmation.
3. The Studio's own buttons keep their confirmation dialog, and the activity log records that a CLI spend or apply was confirmed.
4. Free commands (status, reports, plans and dry runs) need no confirmation.
5. Tests cover each criterion, including an agent-written bypass that is refused.

## Design

### Approach

Grade the Studio's spending and applying CLI commands as asks in the command grader, so the existing approval channel confirms each one, and make the CLI refuse a spend or apply that did not pass through it.

### Decisions and alternatives

- Reuse the grader's channel rather than a Studio-only prompt, so confirmation works the same in every runtime and the agent cannot grant it.
- Open for the builder: how the CLI proves the confirmation happened, for example a one-time grant that only the approval path writes. Whatever it is, an agent must not be able to write it.
- Built: a one-use grant for the command's exact words, kept in the approvals store (whose Bash and file-tool writes are already refused), alive ten minutes. `grade-bash` files it beside the native prompt on Claude Code and after consuming the user's `approve <code>`; the Studio server files it for the CLI apply, rollback or recover its own dialog confirmed. The CLI takes one before it spends or applies, or accepts a `yes` typed at a terminal when no agent runtime variable is set.
- Conservative defaults taken where the story was open: the confirm marker counts in no mode for these commands, so `bypassPermissions` uses the approval code too; Codex, with no typed approval, refuses; `draft rollback` and `draft recover` count as applies; a spend hidden in a substitution, a shell's `-c` text or an unread wrapper is refused in every mode.

### Do not implement

- A new approval interface.
- Changes to the Studio's own confirmation dialogs.

### Completion notes

- `grade-bash.cli_confirmation` classifies the Studio CLI's paid starts and applies and answers ask, deny with an approval code, or pass, ahead of the stance threshold and the marker; the lifecycle dispatcher composes it into the Bash answer and logs `cli_confirmation` on the decision row.
- `approvals.grant` and `take_grant` keep the one-use grants beside the typed approvals; the CLI's `person_confirmed` takes one, or a terminal `yes` outside an agent runtime, and refuses with `person_confirmation_required` otherwise.
- Each confirmed CLI spend or apply appends a `studio.cli-confirmed` event, which Activity titles "CLI spend or apply confirmed". The Studio's dialogs are unchanged; its server files a grant for the CLI it runs.
- Differs from the design: the marker no longer confirms these commands in `bypassPermissions`, which takes the approval code instead, and rollback and recover are treated as applies.
- Residual, documented: a declined native prompt leaves its grant unused until it expires, and a spend reached through an unread program (a script file) is not asked about; the CLI then refuses it for want of a grant.
