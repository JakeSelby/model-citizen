# AH-B128 — Three timing tests fail under a loaded full-suite run and pass alone

## Reproduction

Run the full suite concurrently with other test processes. The adapter timeout test can exhaust
its 0.2-second budget during Python startup before reaching `open`; the two framework-notice tests
can exhaust the SessionStart budget before the integration check returns.

## Root cause

The assertions concern operation semantics and integration output, but their setup uses production
wall-clock deadlines. Scheduler load therefore changes which branch the tests exercise.

## Acceptance criteria

1. Given an adapter timeout during describe or open, a controlled clock proves the correct
   indeterminate status, termination, persisted error, and absence of retries.
2. Given a framework integration, the notice tests execute the real check with a controlled test
   budget and assert its content and non-mutating behavior.
3. Production hook deadlines remain unchanged, and all affected modules pass on both interpreters.

## Design

Use a fake adapter process and deterministic monotonic values in the timeout regression. Keep the
real viewer/invoke error and session-record paths. For integration-content tests, override the
hook's remaining budget in test code while running its real check; the subprocess test uses a
small loader wrapper to apply that override in the child. Keep an outer timeout for hung tests.

Merely raising the 0.2-second threshold was rejected because it still couples the selected branch
to machine load. No production timeout or runtime behavior changes.

## Regression test

The timeout test asserts describe/open call order and exactly one kill/wait for the timed-out
child. The framework tests still run real integration checks and assert the notice and unchanged
configuration. Their inner deadlines no longer depend on time already spent in the SessionStart
hook.
