## Context

PR #583 (merged 2026-09-23, closing #333) scoped qualification-evidence invalidation per target. From
its body:

- evidence is invalidated by the shared runtime source plus that runtime's own adapter directory, with
  the adapter files shared code reads carved back into every target's set;
- only `hook.py` is per-runtime, so a fix confined to one runtime's hook no longer costs the other
  runtime's targets;
- it fails closed, and the catalog declares the scope in a versioned `evidence_invalidation` block.

The PR body ends: "Part 1b, per-case scoping, is a policy edit and is filed as decision #582 rather than
built here."

The issue gives the reason it is a decision rather than engineering: the catalog's evidence
requirements are a v1 stable interface, and a published sentence in `docs/compatibility.md` defined
when qualification holds. Replacing it with a path-scoped rule is a policy edit, so it needs an explicit
yes.

**The issue's quotation is out of date.** It quotes the sentence as "no subsequent runtime-source
changes". At `origin/main`, after PR #583, `docs/compatibility.md` reads "subsequent change under the
paths that invalidate this target", and its section "Which source change invalidates which evidence"
describes the per-target rule. The decision is unchanged: per-case scoping would amend that text again.

The 2026-09-23 PRD lists this as open question 1, "Should qualification evidence be invalidated per
case, or only per target (#582)?", blocking FR-51 and needed by v0.14.0. The spine lists it under
Deferred: "Per-case evidence invalidation (#582). Per-runtime scoping (AD-4) holds until then."

## Options

From the issue:

1. **Accept per-case, path-scoped invalidation, and amend the published sentence.** Each required case
   declares the source paths it depends on. A change under an unmapped path invalidates everything,
   failing closed. The map version is recorded in the catalog and on each evidence record, so a reviewer
   can see what was assumed. The issue estimates about 200 lines plus tests, and a saving of about 45
   percent of a qualification round. The issue says the #340 analysis recommends this option.
2. **Keep whole-source invalidation per target, as #333 landed it**, and revisit after one round
   measures the per-target saving. The issue gives no case for or against it beyond that.

The 45 percent figure is the issue's estimate, not a measured result.

## Decision

Decided by the owner on 2026-09-26: option 1, per-case, path-scoped evidence invalidation with a
versioned case-to-path map. Its terms:

- each required case declares the source paths it depends on;
- a change under a path no case maps still invalidates everything, failing closed;
- the map's version is recorded in the catalog and on each new evidence record, so a reviewer can see
  what was assumed;
- a record without a map version is treated as whole-target scoped.

The owner's choice is the explicit yes for amending the published rule in `docs/compatibility.md`.
Following the issue's "Done when", this file carries the story that defines the map format, built in
the same pull request.

## Design

Per-case scoping sits inside the per-target scoping #583 landed; it never widens a target's path set.

- **Map format.** `evidence_invalidation.case_paths` in `compatibility/catalog.json`:
  `{"version": N, "cases": {"<case>": ["<path>", ...]}}`. Every required case is a key and no other
  case is; a path is a literal file or directory under one of `SOURCE_PATHS`, with no glob, `.`, `..`,
  or leading or trailing slash; a directory covers the files under it. `case_path_map` validates it,
  and `catalog()` refuses a malformed map.
- **Map identity.** `case_map_identity` is `{"version": N, "sha256": <digest of the canonical cases>}`.
  The acceptance runner's `scoped()` writes it into each new record as `case_map`.
- **Validation.** `evidence_errors` lists the files changed since the record's commit inside the
  target's path set, plus the carved-back shared files. `stale_cases` returns the cases whose paths
  those files fall under, or None, meaning the whole record, when the record's `case_map` is missing
  or differs from the catalog's, or when any changed file lies under no case's paths.
- **Stale results.** A stale case's result neither passes nor blocks. A rerun record carrying only the
  stale cases, linked beside the older record, completes the claim. A stale case nothing answers is
  reported as `<case> is stale in linked evidence: source changed under <files>`.
- **Seed map, version 1.** Both runtimes' `worker.py` are mapped to `cost-posture`,
  `framework-spawn-routing`, `role-confinement` and `spawn-confinement`. The other eight cases map
  nothing. Every other path stays unmapped, so it still invalidates every case. The argument for the
  entry is in `docs/compatibility.md`.

Alternatives considered:

- A path-keyed map. It was rejected because the decision says each case declares its paths, and
  because a case-keyed map forces a claim for every new required case.
- Version alone, with no digest. It was rejected because an edit that forgets the version bump would
  then re-scope older records silently. With the digest, such an edit fails closed.

Default taken: the seed map claims only `worker.py`. It is the one coupling whose call sites could be
shown to reach no hook or session start. Hooks such as `tier-agent-spawns.py`, `stop-gate.py` and
`usage-log.py` run on events every case can raise, or are read by the decision log, so they stay
unmapped until someone argues them case by case.

## Consequences

From the issue's "Done when" section:

- if option 1 is chosen, it becomes a story that defines the map format;
- if option 2 is chosen, this issue closes.

Option 1 was chosen, so this issue carried the story. It amends `docs/compatibility.md` and adds a
versioned case-to-path map to the catalog and the map identity to each new evidence record. Existing
records carry no map identity, so they keep the whole-target rule until they are superseded. The honesty
risk named in #333 is accepted: a coupling the map does not model passes unnoticed for the case it
reaches, so each entry is argued in the published doc.

Bound requirement: FR-51: Scoped evidence invalidation, whose status line says "Per-case scoping is a
pending decision". Bound decision: AD-4: Evidence-backed compatibility.

## Review findings

- CodeRabbit, PR #893, round 1: a `case_paths` key set to `{}`, `[]` or `null` was read as no map, so
  a broken declaration quietly turned per-case scoping off and new records omitted `case_map`.
  Fixed: only an absent key means no map; a present one must be a valid map or loading fails, with a
  test for each empty form.
