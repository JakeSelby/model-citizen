## Goal

Keep governance fail-closed while recording which governed Bash segment failed. Provider setup
errors produce one error row per positive-grade segment, and a judgment error on one segment does
not prevent later segments from being judged or logged [Source: #897].

## Acceptance criteria

1. A provider setup failure logs every governed positive-grade segment with its resolved action,
   counterparty and grade, an unknown level, and an `ask` outcome.
2. A provider judgment failure logs that segment's resolved fields, continues through later
   segments, and cannot weaken an earlier or later deny.
3. Error paths remain fail-closed in prompting and automatic modes, and provider policy loading
   still completes before the first segment is judged.

## Tasks

- [x] Separate provider setup from per-segment judgment handling (AC 1, 2, 3).
- [x] Emit one truthful error row for each affected segment without inventing a level (AC 1, 2).
- [x] Add multi-segment setup, mid-segment error, later-deny and decision-row regressions (AC 1–3).
- [x] Run the focused suite under current Python and Python 3.9, then the repository gate (AC 1–3).

## Dev notes

`policy/hooks/grade-bash.py#govern` owns provider selection, policy loading, judgment and governance
rows. `tests/test_governance_binding.py` exercises the binding and the persisted decision schema.
Keep `grade` (the deterministic command classification) distinct from `level` (a provider answer):
when setup or judgment fails, the row retains grade and records `level: null` [Source:
policy/hooks/grade-bash.py#_log; Source: lib/harness_core/decision.py#Decision].
