## Story

As the maintainer, I want the command hook to enforce the autonomy levels in my governance policy, so that a push, merge or deploy the policy gates cannot run just because the model forgot a check.

## Context and value

AH-S266 gave the `local` provider a policy shape that can carry every repository's levels, but nothing consults it: `decision.py` says the binding is a later story, and `grade-bash` answers on the stance alone. Until this lands, per-repository levels are advice the model must remember to ask for. Measured over thirty days of the maintainer's sessions, a check the model had to remember was absent before the first push in about a quarter of the sessions that pushed. A PreToolUse hook sees every command, so the check cannot be skipped. AH-B105 (#859) supplies the approval channel that auto mode needs, so this story builds on it.

## Acceptance criteria

1. **Given** provider `none`, **when** any command is graded, **then** the hook's output is byte-identical to today's.
2. **Given** provider `local` and a policy putting `coding.git_push` at level 2 for this repository, **when** `git push` (grade 2) runs, **then** a prompting mode gets `ask` and auto mode gets a deny carrying an AH-B105 approval code; the reason names the level and its source.
3. **Given** a level-3 pair, **when** the same push runs, **then** the hook prints nothing, as today.
4. **Given** a grade-3 command the grader already gates, **when** the provider says `allow`, **then** the grader's answer stands: the provider never relaxes it.
5. **Given** a command, **when** it is classified, **then** `git push` is `coding.git_push`, `git commit` is `coding.git_commit`, `gh pr merge` is `coding.pr_merge`, a deploy verb is `coding.deploy`, and anything else is `coding.shell_exec`; a compound command takes the strictest answer across its segments.
6. **Given** a `git -C <dir>` or a leading `cd <dir> &&`, **when** the counterparty is derived, **then** it names that directory's repository and branch, not the session's.
7. **Given** a configured provider that raises, including a `PolicyError`, **when** a command is graded, **then** the hook asks, or in auto mode denies with a code, and names the error. It never falls back to allow.
8. **Given** an agent write to the user-level `governance.json`, any `.agent-harness/governance.json` or the harness user `config.json`, by redirect, `tee`, `sed -i`, `cp`/`mv` or a file tool, or any `harness config set governance...` command, **then** it is gated as a level-1 action.
9. **Given** a governed decision, **then** one decision-log row records the class, counterparty, level, grade and outcome.

## Design

### Approach

- After `grade-bash` grades a command, and only when `governance.provider` is not `none`, load the provider through `decision.select_provider`. Import it lazily, so `none` pays nothing.
- Classify each segment and derive its counterparty. For each segment the grader would allow, call `decide(Action(class, grade), counterparty)`. An `ask` from any segment tightens the whole command.
- Emit through the grader's existing mode split: `ask` in prompting modes, and a deny carrying the AH-B105 code in `auto` and `bypassPermissions`. An approved code lets the command through once.
- Wrap every provider call. Any exception becomes a tightened answer that names it (fail closed, as #868 wants for the stance).
- The user `config.json` and `harness config set governance...` are guarded as the policy files are, because the configuration selects the provider: without the guard an agent held at a level could switch governance off rather than edit a policy.
- A governed segment's counterparty is resolved only when every directory change before it on the line is statically known: a `cd` or `pushd` to a literal path with no `-`, `$`, `~user`, glob or substitution, or a `git -C <literal>`. The walk visits segments, and the substitutions inside them, in execution order with the directory then in effect. Any other change before it (`cd -`, `cd "$X"`, `popd`, a `cd` in a subshell, substitution, pipeline or background job, `env -C`, `--git-dir`) makes the counterparty `repo:unknown/local`, which no pair names, so the class default governs. One fail-closed rule instead of parsing each case.
- A write operand whose directory cannot be resolved, under an unknown directory or with a variable or substitution in its directory, is kept as written and judged by its name: one ending in `governance.json` or `config.json` is a level-1 write. An operand that is itself a variable, such as `> "$F"`, cannot be judged without running the line and is left to the threat model: the guard stops an agent that names the file, not one that hides it.
- An `apply_patch` names its paths in the patch, and the file-tool guards (approvals store, policy files, `config.json`) read `*** Delete File:` paths as well as added, updated and moved-to ones, so a delete-only patch of a guarded path is guarded as a write is.
- The policy-file guard is a path check: in the grader's write-target detection for Bash, and in the PreToolUse module that handles file tools, registered through the hook manifests #863 adds.
- Write each governed decision to the decision log under its own point. Update `decision.py`'s module docstring, `docs/runtime-controls.md`, `product.json` and a `changelog.d` fragment.

### Decisions and alternatives

1. **Tighten-only.** The grader's answer is the floor, and the provider can only add friction. A provider fault or a hostile repository policy can then at worst restore today's behaviour. Rejected: letting the provider allow what the grader gates, which widens authority on a policy file's say-so.
2. **Fail closed when a provider is configured.** Choosing a provider is asking to be governed, so a provider that cannot answer must not quietly govern nothing. Rejected: falling back to the grader's answer, which turns a typo in a policy file into no governance.
3. **Classify in the grader, not in the provider.** The grader already decomposes compound commands and resolves wrappers; a second parser would disagree with it. Rejected: passing raw command text to the provider.
4. **Guard policy writes as level 1 rather than deny them.** The user still edits their policy through the agent, with an explicit approval each time. Rejected: an outright deny, which would force every graduation into a separate terminal.

### Do not implement

- No change to grading, thresholds, the approval channel's design (AH-B105), or the `jev` provider.
- No new action classes, no network, and no switching of anyone's configured provider.
- No retirement of any user's personal rule: that happens outside this repository.

## Review findings

CodeRabbit, first pass on #889:

1. **A graded command with no graded segment skipped a broken provider** (`policy/hooks/grade-bash.py`). The segment walk dropped a `cd` that writes through a redirect, so `cd sub 2> err.log && ls` graded 1 while every segment it kept graded 0, the loop asked nothing, and an unknown provider or a malformed policy let it through. The finding's own example, `cd $(cat x)`, grades 0 here and is rightly never governed. Fixed three ways: the provider is selected, loaded and its policy read for the command's directory before any segment is judged, so an unusable provider asks for the whole command and names the error; a graded `cd` is governed where it runs; and a line graded above 0 whose segments all grade 0 is governed whole at its grade. `FailClosed` tests cover an unknown provider and a malformed policy on those lines.

CodeRabbit, second pass on #889, two authorization bypasses in the counterparty:

2. **`cd - && git push` was governed as the starting repository**, though it runs in `OLDPWD`.
3. **`cd ../other && echo "$(git push)"` governed the substitution with the starting directory**, because substitutions were walked before the segments that change directory.

Both fixed by the static-directory rule in Design: substitutions are walked inside their own segment with the directory in effect, and every directory change that is not a literal path makes later segments `repo:unknown/local`. `UnknownDirectory` tests cover `cd -`, the substitution, `cd "$D"`, `pushd` and `popd`, subshell, pipeline and substitution `cd`, a dynamic `git -C`, `env -C`, `--git-dir`, and a literal `cd` that still resolves.

CodeRabbit, third pass on #889:

4. **A policy write under an unresolvable directory escaped the guard.** After `cd "$TARGET"`, the relative operand in `echo x > governance.json` resolved to nothing and was dropped, and the raw fallback needs `agent-harness/governance.json` in the text; `cd "$(git rev-parse --show-toplevel)/.agent-harness" && sed -i ... governance.json` passed the same way. Fixed: an unresolved operand is kept as written and one named `governance.json` or `config.json` is a level-1 write. `PolicyWrites` tests cover both forms, and a `notes.txt` write under the same `cd` stays ungated.
