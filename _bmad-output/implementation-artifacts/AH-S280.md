## Story

As the repository owner, I want a weekly scan that files each finding as a private draft security
advisory with a proposed patch, so that a flaw in the hooks or governance code reaches me before anyone
else sees it.

## Context and value

The repository's scanners are clean: CodeQL, Dependabot and secret scanning show no open alert, and
private vulnerability reporting and push protection are on. The risk that matters is logic flaws in the
hooks and governance code, which only an audit that reads the code finds. A public issue or pull request
for a hook bypass would disclose it before installed checkouts update. claude-code-action keeps
`show_full_output` false by default because run logs are public
[Source: https://github.com/anthropics/claude-code-action]. Traces to FR-73
([#951](https://github.com/JakeSelby/model-citizen/issues/951)).

## Acceptance criteria

1. **Given** the weekly schedule, **then** a run audits the hooks, governance and CLI code and runs
   zizmor on the workflows, inside the bot's budget.
2. **Given** a finding, **then** it becomes a draft repository security advisory with a proposed patch,
   and nothing about it appears in an issue, pull request, run log, step summary or artifact.
3. **Given** a finding that matches an open advisory, **then** no second advisory is created.
4. **Given** an advisory, **then** the fix is applied in the advisory's temporary private fork, with the
   Gate run there by hand because status checks do not run in temporary forks, and ships as a patch
   release under `docs/releasing.md`.
5. **Given** the scan's agent, **then** it never holds a token that can push code or change settings.

## Design

### Approach

- **Scan:** weekly, off-hours, counted against the weekly cap (#946). claude-code-action with
  `show_full_output` left false; zizmor's output goes to a file the agent reads, never to the log;
  nothing in the step summary; no uploaded artifact.
- **File:** `POST /repos/JakeSelby/model-citizen/security-advisories` as a draft, with the finding and a
  proposed patch in the private description, and a fingerprint so a repeat is recognised. The writer
  job holds the App's repository security advisories write permission (#945); the agent does not.
- **First task:** confirm an installation token may create an advisory, since the REST page lists
  installation tokens but also requires a security manager or administrator
  [Source: https://docs.github.com/en/rest/security-advisories/repository-advisories].
- **Fix, default: the owner's session applies it.** The bot drafts the advisory with a proposed patch,
  and a session under the owner's identity applies the fix in the private fork on the owner's go. This
  is the recommended option, taken as the default pending the owner's confirmation. A temporary private
  fork needs Administration write to create; status checks do not run in it and no protection rules
  apply, so whoever fixes runs the Gate by hand, and the advisory merges the fork's pull requests.

### Decisions and alternatives

- **Who applies the fix (decision 3, default pending the owner's confirmation).** Chosen: the bot
  drafts, and a session under the owner's identity applies the fix in the private fork, because creating
  the fork needs Administration write, which would let a hijacked bot edit its own rulesets.
  Alternative: a second App with Administration write fixes unattended; faster, but an admin-capable key
  sits in the repository's secrets.
- **Draft advisories, not issues.** Private by construction. Rejected: a private issue tracker or a
  labelled public issue.
- **Fingerprint the finding.** Rejected: matching on title text, which varies between runs.

### Do not implement

- Any public trace of an unfixed finding, including a failing check.
- An App or token with Administration write.
- Automated patch releases; a patch release keeps its hand-run qualification steps.
