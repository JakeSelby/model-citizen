## Story

As a Claude Code user who installs the plugin, I want it listed and installed as `model-citizen`, and doctor
to recognize my existing `agent-harness` install, so that the plugin carries the product's name and my
current install is neither broken nor silently doubled.

## Context and value

The rename (AD-24) changes the plugin and marketplace ID. Claude Code keys an installed plugin by
`<plugin>@<marketplace>`, so existing installs keep `agent-harness@agent-harness` until the user reinstalls.
Whether Claude Code carries an install across a renamed plugin is unverified, which is the rename's main
risk: doctor must recognize both IDs, and warn when both are enabled, because the skills would then load
twice. This is PR B of the plan.

## Acceptance criteria

1. **Given** `.claude-plugin/plugin.json` and `marketplace.json`, **then** the plugin `name` and the
   marketplace `name` are `model-citizen`, the `displayName` is Model Citizen, and the descriptions name
   Model Citizen. Their `homepage` and `repository` URLs are unchanged here.
2. **Given** a settings file enabling `agent-harness@agent-harness` only, or `model-citizen@model-citizen`
   only, **when** doctor runs, **then** it reports the marketplace plugin as installed, under either
   marketplace name.
3. **Given** both IDs enabled, **when** doctor runs, **then** it warns that the skills would load twice.
4. **Given** `docs/runtime-installation.md`, **then** it carries the new install command and the migration
   steps for an existing plugin install.
5. **Given** a scratch profile, **when** the v0.13.1 marketplace install is updated to this branch, **then**
   whether Claude Code keeps the old ID is recorded for the release notes.
6. **Given** Claude Code's settings enabling the pre-rename `agent-harness@<market>` plugin, **when**
   doctor or sync runs, **then** it names the old ID and points at `citizen upgrade`; doctor's
   both-enabled warning points there too, and sync says nothing when the old ID is not enabled.
7. **Given** that install, **when** `citizen upgrade` runs, **then** it runs, through the `claude`
   CLI and in this order, `claude plugin uninstall agent-harness@<market> --scope <scope>`,
   `claude plugin marketplace remove <market>`, `claude plugin marketplace add <source>` with the
   source recorded in `known_marketplaces.json`, and `claude plugin install
   model-citizen@model-citizen --scope <scope>`, the scope read from `installed_plugins.json`.
   `--dry-run` prints the commands only; a failed step stops the run and prints the rest; with
   nothing old found it says so and exits 0; without the `claude` CLI it prints the in-session
   `/plugin` steps and exits 1.

## Design

### Approach

- Rename the plugin and marketplace in both manifests; leave URLs and the `version` field.
- In doctor's plugin install state, accept `agent-harness@agent-harness` and `model-citizen@model-citizen`
  as the enabled key and either marketplace name in the known marketplaces and the plugin cache; add the
  both-enabled warning.
- Add the install and migration steps to `docs/runtime-installation.md`, the old ones removed first:
  `/plugin uninstall agent-harness@agent-harness`, `/plugin marketplace remove agent-harness`,
  `/plugin marketplace add JakeSelby/agent-harness`, `/plugin install model-citizen@model-citizen`.
  Skills move from `/agent-harness:<skill>` to `/model-citizen:<skill>`. The slug in the `add` line
  moves to `JakeSelby/model-citizen` with the other URLs in AH-C079.
- Add a changelog fragment `changelog.d/878.changed.md`: "The plugin is now `model-citizen@model-citizen`;
  reinstall it."

### Decisions and alternatives

- **Recognize both IDs rather than migrate the install.** The harness does not own Claude Code's plugin
  state, and the checkout install is unaffected by the plugin change.
- **Warn, do not fail, when both are enabled:** a doubled skill set is noisy, not unsafe.
- **Offer the move, do not make it unasked (maintainer decision, 2026-09-25).** Checkout users on
  the old plugin ID get `citizen upgrade`, which drives Claude Code's own `claude plugin` commands
  rather than editing its state files; doctor and sync only point at it. A plugin-only install has
  no CLI and keeps the `/plugin` steps.
- **URLs wait for AH-C079,** after the GitHub rename, so no manifest points at a repository that does not
  yet exist.

### Do not implement

- No `homepage` or `repository` change, and no fix to the stale plugin `version` fields; the plan defers
  that to a follow-up.
- No hooks in the plugin (AD-19).
- No command rename (AH-S267) and no copy outside the install doc (AH-S269).

### Completion notes

- Both manifests now name the plugin and marketplace `model-citizen`, displayName Model Citizen;
  `homepage`, `repository` and `version` are unchanged.
- `bin/harness` gains `PLUGIN_NAMES`; `plugin_install_state` accepts either plugin name as the
  enabled key, either repository name for a registered marketplace, and either name in the plugin
  cache. With both IDs enabled it records the older one under `doubled`, and
  `_plugin_install_line` adds a `plugin warning` line naming the `/plugin uninstall` to run.
- The install doc carries the new commands and a migration subsection.
- The scratch-profile check (AC 5) ran on Claude Code 2.1.280 through its `claude plugin` commands,
  with an empty `CLAUDE_CONFIG_DIR`, a scratch `HOME` and working directory outside the home
  directory, a scrubbed environment, and a local git server standing in for GitHub. Installed from
  v0.13.1, the plugin was `agent-harness@agent-harness`. After the marketplace updated to this
  branch, Claude Code kept the marketplace as `agent-harness` and the plugin as
  `agent-harness@agent-harness`, still enabled, and reported it as failing to load: "Plugin
  agent-harness not found in marketplace agent-harness". Adding the same repository again printed
  "Marketplace 'agent-harness' already on disk" and registered nothing, so installing
  `model-citizen@model-citizen` then failed, and the uninstall and removal after it left no plugin.
  Uninstalling and removing first, then adding and installing, left `model-citizen@model-citizen`
  enabled from a marketplace named `model-citizen`. The install doc and the changelog fragment carry
  that order.
- The install doc's `add` line keeps `JakeSelby/agent-harness`, which resolves before the GitHub
  rename and redirects after it; AH-C079 moves it with the other URLs.
- ACs 6 and 7 follow the maintainer's 2026-09-25 decision. `plugin_install_state` gains `old`, the
  enabled keys whose plugin name is a pre-rename one. Doctor adds a `plugin upgrade` line naming
  the old ID, that it fails to load once its marketplace updates, and `citizen upgrade`; the
  both-enabled warning now names `citizen upgrade` before the `/plugin uninstall` alternative.
  Sync prints one `notice` line before its print-only return, and nothing when no old ID is enabled.
- `citizen upgrade` builds its plan in `plugin_upgrade_plan`: each old key's scopes from
  `installed_plugins.json` (a list or a single record per key, `user` when none is recorded, and a
  project or local install run from its `projectPath`), the marketplace source from
  `known_marketplaces.json` (github `repo`, git or url `url`, directory `path`), then the steps in
  the order the scratch-profile check verified. It skips the `add` when a `model-citizen`
  marketplace is already registered and the `install` when the new ID is already enabled, so the
  both-enabled case only uninstalls and removes. A marketplace with no recorded source runs nothing
  and exits 1. Every command goes through `_run_claude`, the seam the tests stub; no test runs the
  real CLI.
