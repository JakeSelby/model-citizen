## Story

As a developer measuring my instruction rules inside the harness, I want `harness usage --rules` to list
every rule in my loaded instruction surface as measured, dark or unmeasured, with the share measured,
and to load my declarative detectors, so that I get the rule-level view standalone `ruleprobe` gives
without leaving the harness.

## Context and value

Today `harness usage --rules` reports hits keyed by detector. The rule-level report (each rule measured,
dark or unmeasured with its reason, the share of rules measured, and declarative detectors) exists only
in standalone `ruleprobe` run with `--rules`. The PRD's first-contact path (UJ-3) needs that view inside
the harness too. FR-20 and FR-67 both list this as planned and unscheduled; the re-derived epic map
places it under this epic, whose coverage includes both.
[Source: https://github.com/JakeSelby/agent-harness/issues/647]

## Acceptance criteria

1. **Given** a loaded instruction surface, **when** `harness usage --rules` runs, **then** it lists every
   rule, including rules imported into external roots, as measured, dark or unmeasured.
2. **Given** an unmeasured rule, **when** it is listed, **then** its reason is shown.
3. **Given** the report, **when** it is printed, **then** it states the share of rules measured.
4. **Given** a declarative detector in `.ruleprobe/detectors.yaml`, **when** `harness usage --rules`
   runs, **then** the detector is loaded without a code change and its rule counts as measured.
5. **Given** a detector with zero hits over the reporting window, **when** the report runs, **then** it
   is listed, not omitted (FR-20).

## Design

### Approach

Bring the rule-level classification the vendored `ruleprobe` engine already performs under `--rules`
into `harness usage --rules`, and load `.ruleprobe/detectors.yaml` alongside the built-in detectors.
The spine requires that path: when the harness loads declarative detectors, it reads them through the
same engine (AD-13).

### Decisions and alternatives

- The vendored `ruleprobe` 0.1.0 wheel, already the engine `rule-detectors.py` runs, reads the
  detector file and rule front matter (AD-13). No new dependency, and nothing reads the
  standalone package at runtime; a file written for `ruleprobe` 0.2 features the 0.1.0 engine
  lacks, such as `schema_version`, is a finding with its line rather than a detector.
- Default taken: only the repository's `.ruleprobe/detectors.yaml` is read, not the per-user
  `~/.config/ruleprobe/detectors.yaml`, because the story names the repository file and a
  session is measured by the detectors its repository ships.
- Default taken: the session hook runs the declarative detectors of the session's repository,
  because a rule reported measured by a detector that never runs would be a quiet zero (AC 4).
- Default taken: a `detector:` block in a rule file's front matter is reported unmeasured with
  that reason, because the session hook does not run it.
- Default taken: the surface is this repository's rules less those switched off, each
  registered primitive root's rules, and each stance at its selected variant named by its
  dimension; when two files share a rule name the first holds its detectors and the second is
  unmeasured with the reason, as the `delegation` rule and stance do.
- Default taken: states, share and block layout follow `ruleprobe` 0.2's `--rules` summary:
  dark counts in the denominator, the share is floored, `<1%` when a measured rule would floor
  to zero; a malformed entry is printed under `findings:` and does not change the exit code.

### Do not implement

- Grouping by mode and switch state, which FR-20 plans separately for v0.14.0.
- Proposing a detector from a rule's prose, which FR-67 lists as a separate planned item.
