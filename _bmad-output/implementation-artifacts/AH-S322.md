## Story

As the Model Citizen release maintainer, I want an honest path for a presentation-only patch to
reuse a prior release's native evidence, so that release-pinned documentation can be corrected
without paying for a native qualification round that exercises unchanged client behavior.

## Context and value

`model-citizen.dev` renders the README, documentation and product data from an immutable release
tag. The public rename therefore cannot reach the reference site from `main` alone. The current
release contract binds evidence records to `harness_version`, requires the catalog version to equal
`VERSION`, and treats every change under `VERSION`, `bin`, `lib`, `adapters`, `primitives`, `policy`,
`templates` and `config.example.json` as qualification-relevant.

Investigation exposed a bootstrap conflict in the approved plan: adding carry-forward support to
`lib/harness_core/compatibility.py` changes qualified runtime source. The v0.14.1 candidate cannot
both contain that mechanism and truthfully claim that its runtime is byte-identical to v0.14.0.
The maintainer approved a one-release exception: v0.14.0 evidence may be reused for unchanged
client-facing behavior while v0.14.1 discloses its compatibility and release-reporting change. The
release is neither newly qualified nor described as byte-identical, and the exception cannot apply
to a later release.

## Acceptance criteria

1. **Given** a released catalog with qualified native evidence, **when** a later patch declares a
   permitted reuse basis, **then** the catalog names the prior version, tag, qualification source
   commit and exact limitation without rewriting any evidence artifact.
2. **Given** a permitted patch candidate, **when** release preflight validates it, **then** it
   verifies ancestry, patch ordering, the allowed source delta and equality of all carried client,
   case, evidence-digest, limitation and support claims.
3. **Given** a non-patch version, missing tag, unavailable ancestry, changed evidence or claim, or
   source change outside the selected exception, **when** preflight runs, **then** it fails closed
   with the first named mismatch.
4. **Given** an ordinary candidate or released catalog without reuse metadata, **when** existing
   compatibility and release commands run, **then** their qualification behavior is unchanged.
5. **Given** the new release path, **when** maintainers read `docs/releasing.md` and release output,
   **then** they can distinguish newly qualified, carried evidence and explicitly excepted source.

## Design

### Approach

Add explicit catalog metadata for a one-release bootstrap exception and the future carry-forward
contract. Compare against the immutable prior release tag rather than a mutable branch or
pre-release commit, and keep one validator in `harness_core.compatibility` so CLI status, release
notes and preflight cannot disagree. The validator accepts v0.14.1 only when the delta outside the
new compatibility/release-reporting implementation is presentation and release metadata; future
carry-forward accepts only a `VERSION` delta across qualified runtime source.

### Decisions and alternatives

- Compare against `v<prior-version>`, because the prior release tag is the immutable public claim;
  the qualification source commit predates release metadata.
- Preserve evidence bytes and digests. Rewriting `harness_version` in an old evidence record would
  fabricate an observation that never ran.
- Keep normal release behavior as the default. Reuse requires explicit metadata and every lookup,
  parse, ancestry or equality failure is a refusal.
- v0.14.1 alone may use the explicit bootstrap exception approved on 2026-09-27. The alternatives
  rejected were a new native round, leaving the reference site stale, and overlaying `main` content
  onto a release-pinned site.

### Do not implement

- Running native acceptance or qualification.
- Changing client support states, required cases, invalidation scopes, limitations or evidence.
- Changing site pinning, release deployment or the public documentation in this PR.
- Creating a general waiver for runtime fixes, policies, primitives, adapters or templates.

  exception. It compares the candidate to the prior immutable tag, including source delta and all

## Review findings

Three isolated review layers completed against the same staged diff. Dispositions below are the
maintainer triage record; duplicate findings remain listed so every reviewer result is accounted
for.

All patch dispositions below are implemented with focused regression coverage. E13 remains the
recorded rejection; no self-referential diff hash was added.

## Review Triage Log

- **B1 — patch:** compare the whole release delta and permit only named presentation/release paths
  plus the explicit bootstrap implementation paths; executable installer/workflow changes must
  fail closed.
- **B2 — patch:** validate reuse against the immutable current release when tagged, then report
  later runtime changes as drift instead of raising while reading the released catalog.
- **B3 — patch:** replace the free-form limitation with exact, kind-specific disclosure text.
- **B4 — patch:** resolve and pin `refs/tags/<version>^{commit}` once; never accept a branch or mix
  objects if a ref moves during validation.
- **B5 — patch:** require the reuse object to contain exactly the supported fields.
- **E1 — patch:** reject JSON booleans as reuse schema versions.
- **E2 — patch (duplicate B5):** reject unknown or misspelled reuse fields.
- **E3 — patch (duplicate B3):** require the canonical no-rerun limitation for the selected kind.
- **E4 — patch:** reject semantic versions with leading-zero numeric identifiers.
- **E5 — patch:** when a chain includes the v0.14.1 exception, disclose that exception in release
  output rather than naming only the immediately prior tag.
- **E6 — patch (duplicate B4):** require an immutable tag ref.
- **E7 — patch (duplicate B4):** pin one prior-tag commit for every lookup in a validation hop.
- **E8 — patch:** reject a prior catalog that is not a JSON object with a named mismatch.
- **E9 — patch:** cap reuse-chain depth and refuse overlong chains explicitly before recursion can
  fail.
- **E10 — patch:** compare carried JSON claims with type-sensitive canonical equality so `true`
  cannot substitute for `1`.
- **E11 — patch:** require both prior and candidate limitations to be lists of nonempty strings.
- **E12 — patch (duplicate B1):** reject changes to executable surfaces such as the installer.
- **E13 — reject:** a hash embedded in the file whose diff it authenticates is self-referential and
  would also make reviewed amendments impossible. The approved exception is bounded instead by
  exact version, exact changed behavior-file set, immutable ancestry, full review and one-use kind.
- **V1 — patch:** exercise invalid reuse through the real `catalog` consumer.
- **V2 — patch:** prove prior-version evidence passes, and current-version evidence fails, through
  `evidence_errors`.
- **V3 — patch:** independently prove valid reuse suppresses release-time drift while a later
  runtime change restores the drift error.
- **V4 — patch:** cover a tag whose catalog and `VERSION` disagree.
- **CR1 — patch, resolved:** CodeRabbit found that the reuse branch checked only runtime-path
  equality after resolving the current immutable tag. It now also requires that release commit to
  be an ancestor of `HEAD`; non-ancestral history reports drift and blocks release.
