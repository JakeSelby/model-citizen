## Story

As a harness maintainer, I want each recommendation the harness gives the user recorded with whether it was followed, so that adherence can be measured as one of the three axes of every comparison.

## Context and value

Adherence is one of the three axes every comparison is measured on (PRD §1). The harness already emits recommendations to the human, such as the usage feed's hand-off and clear-context nudges, but nothing records whether they were followed. AD-23 treats adherence events as observation, so they fall under #791's zero-footprint test.

Depends on #789 and #791. Consumer: #692. Traces to AD-23 and PRD §1.

## Acceptance criteria

1. Given a recommendation emitted by a hook or stance, when it is emitted, then an adherence event records its kind, the emitting module, the session and the turn.
2. Given the next N turns, with N fixed per recommendation kind, when the user acts or does not, then a response event records followed, not followed or unknown.
3. Given the events, when they are read back, then an adherence rate per recommendation kind can be computed without reading message bodies.
4. Given the bare arm, then recording adherence adds nothing to model context, under #791's test.

## Design

### Approach

- `policy/hooks/adherence.py` is a kernel library beside the hooks, standard library only. Its
  `KINDS` table names every recommendation a hook emits, the `hooks/<id>` that emits it, the
  window of prompts within which acting on it counts, and the observation events that count as
  acting. `emit(kind, session_id, turn, env)` appends one `emitted` row to
  `~/.local/state/agent-harness/adherence.jsonl`: `adherence_id`, `recommendation`, `module`,
  `session_id`, `turn`, `ts`, `profile_fingerprint` and `schema_version` 1. It returns nothing and
  swallows every error.
- The usage feed's fresh-session nudge is the one emitter. The feed keeps a `turns` count of the
  session's prompts in its state file, kept across a transcript reset, and passes it as the turn.
- `respond(row, observed)` reads the session's rows in the observation ledger
  (`observation.jsonl`, #791), using only `event` and `session_id`. After the emitting turn's
  `UserPromptSubmit`: a `follow` event before the window passes is `followed`; the prompt
  `turn + window + 1` is `not_followed`; otherwise `unknown`, with reason `unobserved` when the
  ledger never reached the emitting turn and `window_open` when it did.
- `settle(env, now)` appends a `response` row, joined by `adherence_id`, for every emission it can
  now answer. A followed or not-followed reading is final; an unknown one is written only once the
  emission is a day old. `rates(rows)` returns, per recommendation, emitted, followed,
  not followed, unknown, pending and `rate`, which is followed over judged.

### Decisions and alternatives

- **The answer comes from observation rows, not the feed.** Whether a session ended is a
  SessionEnd, which the feed never sees; the observation ledger records every event as
  identifiers only, and AD-23 names adherence as observation. The alternative, the feed counting
  its own later prompts, could say "not followed" but never "followed".
- **Recording is not live-answerable yet.** #791 shipped the observation entry point unregistered,
  by the owner's decision, and opt-in registration is #867. So this builds and tests the reading
  on recorded rows: fixtures, and the rows a scripted bare-arm session writes through
  `observe.py`. Until #867 lands, every live emission is answered `unknown` with reason
  `unobserved`. This change does not register the recorder.
- **The turn is the feed's prompt count, matched to the observation ledger's prompt ordinal.**
  A timestamp match was rejected: the recorder and the feed run concurrently on the same prompt,
  so a one-second stamp cannot say which prompt a row belongs to. The count drifts only when the
  feed skips a prompt, when its lock is contended or its mode is off.
- **Window of three prompts for `fresh-session`.** The line says finish the task, write the
  handoff, start a fresh session: two turns of work and then the exit. `/clear` and an exit raise
  SessionEnd and count as following; a compaction does not, and continuing compacted does not.
- **An unknown is held for a day before it is written,** because an unknown written early could
  never be upgraded when the rows arrive. A second response to one emission is ignored.
- **No switch.** The rows hold identifiers only, like the observation ledger, which has none;
  the decision log's switch exists because its rows hold command text.
- **A kernel library beside the hooks, not `lib/harness_core`:** the feed is reached through
  `~/.claude/hooks/harness`, where nothing above resolves, the reason `decisions.py` gives.

### Do not implement

- Registering the observation entry point in `harness sync` (#867).
- A `harness` report command or a benchmark reader for the rates; the consumer is #692.
- Other recommendation kinds: a subagent's over-budget line and the width note are figures, not
  recommendations with an observable follow, and a stance's text is resident context with no
  emission event.
- A switch under `telemetry`, or removing the ledger in `harness uninstall`.

## Review findings

- CodeRabbit round 1, `policy/hooks/usage-feed.py` (major): the feed's `turns` count can fall
  behind the observation ledger's prompts, when a prompt loses the lock or a state file is reset,
  and a lagging turn closes the three-prompt window early as not followed. Fixed: `respond` takes
  the later of the emission's turn and the session's prompts the ledger stamped no later than
  the emission, with regression tests for a lagging turn, a leading turn and later prompts.
- CodeRabbit round 2, `policy/hooks/adherence.py` (major): timestamps are whole seconds, so a
  next prompt stamped in the emission's own second would count as preceding it. Answered, not
  changed: the emission is written in the emitting prompt's hook and the next prompt waits on the
  model's answer, so this needs a sub-second turn and moves the anchor one prompt at most. A finer
  marker needs a ledger read in the feed hook or an observer schema change, outside this story.
