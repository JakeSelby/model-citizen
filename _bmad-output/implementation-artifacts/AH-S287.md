## Story

As a developer, I want to browse every module with its manifest, projection and context cost, so that I know what my harness loads and what it costs.

## Context and value

Browse every module the harness can load (rules, stances and their variants, skills, hooks, roles, workflows, modes and output styles) from the core and from each primitive root. Each module shows its manifest fields from `primitives/manifests.json`, its on or off state, rendered and source views, the files it projects to for each runtime, and its static context cost.

## Acceptance criteria

1. Given a module in a developer's primitive root with the same name as a core module, then both are listed with their roots and the collision is flagged.
2. Given a module switched off, then it shows as off, with the layer that switched it off.
3. Given a rule, then its page shows the files it projects to for Claude Code and for Codex, and its token cost from the static context figure.
4. Given a library of 500 modules, then search and the filters by kind, root, state and cost answer in under 100 ms.

## Design

### Approach

Add a read-only `module_library` provider behind an authenticated Studio endpoint. It inventories
the core and configured primitive roots without collapsing duplicate names, joins the effective
selection and its source layer, and computes the same chars-per-four soft context estimate used by
the policy resolver. The React Library route receives the versioned inventory once, then performs
search and kind, root, state and cost filtering in memory.

### Decisions and alternatives

- Keep duplicate modules as separate rows and flag every member of the collision; first-wins would
  hide the exact problem the Library is meant to expose.
- Return source, rendered text and runtime destination metadata in one authenticated response;
  per-module endpoints would add latency and an unnecessary path-identity surface.
- Filter an already-built inventory in memory. Re-reading the filesystem for each keystroke was
  rejected because the 500-module latency criterion is specifically about interactive filtering.
- Label context figures as soft estimates and state the method. Hooks, modes and presentation
  modules report zero resident tokens rather than implying that event-time or optional text is free.

### Do not implement

Editing modules, applying selection changes, measuring runtime token use, and resolving collisions
are out of scope. The Library reports current local state and links no mutation.

## Review findings

Self-review found that hook catalog entries have no primitive directory; the inventory now skips
directory enumeration for them and adds kernel hooks through their authoritative registry. Focused
tests cover the regression. Spec review found the presentation projection named only Claude Code;
the mapping and regression coverage now also name Codex's aggregated `AGENTS.md` projection.
Quality review found modes were treated as informational and always on; active and inactive modes
now report on/off state, selection-layer provenance and switchability explicitly.
