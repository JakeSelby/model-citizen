## Story

As a developer who reads or exports the harness's ledgers, I want every ledger row to carry a schema
version and every reader to tolerate fields it does not know, so that an upgrade never leaves old rows
unreadable or breaks an older reader on newer rows.

## Context and value

The usage ledger and decision log are public surface: their schemas and exported attribute names. The
issue records that their rows carry no schema version and that readers do not tolerate every change a
writer might make. AD-11 in the 2026-09-23 spine requires additive schema changes, a version on each row
from the next ledger change on, reader tolerance for unknown fields, and fold maps for renames; the
spine marks AD-11 partial, with the schema version planned under epic #636 [Source: ARCHITECTURE-SPINE.md#AD-11].

On `main`, the CLI already folds one kind of rename: `renamed_ids()` and `folded_rules()` in
`bin/harness` count a renamed detector's hits under its successor, from the registry's own `RENAMED`
map. AD-11 names this as the precedent.
[Source: https://github.com/JakeSelby/agent-harness/issues/644]

## Acceptance criteria

1. **Given** a row written by a newer writer, **when** the current reader reads it, **then** it is read
   without error.
2. **Given** a renamed field, **when** a reader reads an old row, **then** the field is folded to its
   new name.
3. **Given** each case above, **when** the suite runs, **then** a test covers it.

## Design

### Approach

- Add a schema version to each ledger row, from the next ledger change on.
- Make every ledger reader ignore unknown fields rather than fail on them.
- Ship a fold map with any field rename, on the pattern of the detector-id fold.
- Document the rule.

### Decisions and alternatives

- **Additive only:** schema changes add fields; renames fold; nothing is removed in place (AD-11).
- **Versioning starts at the next change**, not by rewriting existing rows; AD-11 allows only the usage
  worker's `upsert` to rewrite a ledger.

### Do not implement

- Rewriting historical rows to add a version.
- Changes to the export channel, which AD-11 keeps OTLP only and off by default.

### Completion notes

- Both ledgers stamp `schema_version: 1` on every row they write from this change on:
  `stamped()` in `usage-log.py` covers `upsert`, `append_row` (and so the provider rows
  `harness_core.decisions.ledger` appends) and the rows the worker exports live; `_append` in
  `decisions.py` covers decision and outcome rows. A row without the key reads as version 0.
- Each module owns an empty `FIELD_FOLDS` map, `old name: new name`, and a `fold()` that moves an
  old key to its new name and keeps the new one when a row carries both. The two ledgers are
  versioned apart, so each module keeps its own map; the fold itself is seven lines in each.
- Every usage-ledger reader goes through `ledger_rows()`: `recorded()`, `harness usage`,
  `harness usage export` (through the new `usage_ledger()` in `bin/harness`) and
  `harness_core.decisions.ledger.rows()`. `decisions.read_rows()` folds for `usage --by decision`
  and the evaluation report.
- `upsert` keeps every row it does not replace byte-for-byte as written and matches on the folded
  key, so no old row is rewritten to carry a version or a new field name.
- Readers already read by `.get`; the tests now prove a version-99 row with unknown scalar and
  nested fields reads through each report without error.
- `schema_version` is a new flat scalar, so the OTLP export carries it as an attribute like any
  other added field; the export channel itself is unchanged.
