## Reproduction

On Codex, run a shell command that the output filter targets, for example `python3 -m unittest -v .`,
with the harness hooks active. The issue records the observation natively on `codex-cli-macos` during
the 0.11.0 qualification: the command runs unfiltered, because the composed `PreToolUse` rewrite
(`updatedInput`) never reaches the client.

The issue also records a control: a stub hook that sent `updatedInput` together with `allow` was
accepted by Codex, and the rewritten command ran. So the client can apply a rewrite; the harness does
not send one.

## Root cause

Traced in `lib/harness_core/lifecycle.py` at `origin/main`:

- `dispatch()` grades each Bash command through `grade-bash`. It appends an `allow` only when the grade
  is 0, or when plan-mode investigation allows a grade-1 command. It then appends the result of the
  `filter-output` hook.
- `_encode_pre()` drops a plain `allow` on Codex, because the client rejects the whole hook output when
  it carries an unsupported `allow`. It attaches `updatedInput` on Codex only when the strongest
  decision is already `allow`, or when the tool is `Agent`. The code comment reads "Codex requires
  allow for rewrites. Do not manufacture an approval to format output."
- The issue states that every command `filter-output` rewrites is grade 1. With no `allow` among the
  composed results, the rewrite is discarded on Codex.

`docs/runtime-controls.md` states the same rule from the policy side: "Output filtering never grants an
otherwise unapproved shell command merely to rewrite it."

## Acceptance criteria

The issue records a decision to take, not a fixed outcome. Its two options give these criteria:

1. **Given** Codex and a command that `filter-output` rewrites, **when** option 2 is chosen and every
   composed policy would have let the command run, **then** the hook output carries `allow` with the
   rewritten input, and the filtered command runs.
2. **Given** the same command, **when** option 1 is chosen instead, **then** the docs state that output
   filtering is a Claude Code capability, and the Codex limitation stays declared.
3. **Given** a command that a composed policy denies or asks about, **when** either option is taken,
   **then** no `allow` is sent for it on Codex. [ASSUMPTION: read from `_encode_pre` in
   `lib/harness_core/lifecycle.py`, which returns early on `deny` or `ask`; #292 does not state it.]

## Design

Open. The issue names two options:

1. Keep the encoder rule, and document that output filtering is a Claude Code capability.
2. Send `allow` with a rewrite when every composed policy would have let the command run anyway.

Option 2 conflicts with the published sentence in `docs/runtime-controls.md` quoted above, so choosing
it means amending that sentence too. [ASSUMPTION: the issue does not name the doc sentence; the
conflict is read from the doc at `origin/main`.]

The issue records the gap as a 0.11.0 limitation. `compatibility/catalog.json` still lists it at
`origin/main`: "On Codex, output-filter rewrites are never applied … Tracked in #292."

Do not implement: an approval for a command that a composed policy denies or asks about (AC 3).
[ASSUMPTION: read from the code, not from #292.] The issue records no scope or out-of-scope section.
