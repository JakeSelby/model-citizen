## Story

As the repository owner, I want the burndown bot to work CodeRabbit's review through to merge on its
own pull requests, so that it finishes what it starts and a pull request lands only when every condition
an agent-landed pull request needs holds.

## Context and value

`AGENTS.md` sets the conditions under which an agent may merge without asking: nothing waits on the
maintainer, the Gate passed and every required check is green on the head commit, and a CodeRabbit pass
completed after the last change with each finding fixed or answered and every thread resolved
[Source: AGENTS.md#coderabbit-review-and-merging]. It also records the traps: the `Review skipped` status
posted on every push is not a pass, and neither is the empty review a thread reply creates. A pass
finishes seven to eleven minutes after it starts. The bot must meet the same bar. Traces to FR-72
([#949](https://github.com/JakeSelby/model-citizen/issues/949)).

## Acceptance criteria

1. **Given** a completed CodeRabbit pass on a Claude-lane pull request, **then** the same arm fixes or
   answers each finding, resolves its thread and requests `@coderabbitai review`.
2. **Given** a fourth round, or any human comment, **then** the pull request gets `bot::needs-owner` and
   the bot stops.
3. **Given** every required check green on the head commit, a completed pass after the last change,
   every thread resolved and nothing waiting on the owner, **then** the bot merges with
   `--match-head-commit`, bringing in `main` first when behind.
4. **Given** the merge switch off, **then** the bot labels the pull request `bot::ready-to-merge`
   instead of merging.
5. **Given** a `Review skipped` status, or an empty review created by a thread reply, **then** it never
   counts as a pass.

## Design

### Approach

- Trigger on the `CodeRabbit` commit status reading `Review completed` on `burndown/*` heads, with a
  scheduled sweep as the fallback for a missed event.
- The review round runs in the pull request's own arm, so the trial's treatment covers the whole
  attempt; the round count comes from the completed passes on the pull request.
- The agent's structured result declares any default it took on the owner's behalf; a declared default
  means `bot::needs-owner`.
- **Merge switch, default off.** The merge switch is a repository variable that starts off, so the bot
  stops at `bot::ready-to-merge` until the owner flips it. This is the recommended option, taken as the
  default pending the owner's confirmation.
- The merge job holds the App token and checks the conditions itself; it never trusts the agent's claim
  that they hold.

### Decisions and alternatives

- **Merge authority (decision 2, default pending the owner's confirmation).** Chosen: a merge switch
  that starts off, because the autonomy stance bars an unattended loop from graduating itself.
  Alternative: merge from the first pull request, as first asked; the ruleset (zero approvals, required
  checks, resolved threads) and the `/land` conditions already bind it. If the owner chooses the
  alternative, the switch starts on and nothing else changes.
- **Status trigger with a sweep.** Rejected: polling alone, which spends runner minutes waiting through
  a pass's seven to eleven minutes.
- **Three rounds.** Matches the working-style cap of two to three review rounds per story.

### Do not implement

- Merges to `stable`, or any release step.
- Codex-lane review rounds; #950 routes those to `@codex` and reuses this story's merge job.
- A ruleset change of any kind.

## Tasks

- [ ] Trigger on the `Review completed` status on `burndown/*` heads, with a scheduled sweep (AC: 1)
- [ ] Run the review round in the pull request's arm: fix or answer, resolve, re-request (AC: 1)
- [ ] Stop with `bot::needs-owner` on a fourth round, a human comment or a declared default (AC: 2)
- [ ] Write the merge job: check every condition, update from `main`, merge with `--match-head-commit` (AC: 3)
- [ ] Add the merge switch, off by default, and the `bot::ready-to-merge` path (AC: 4)
- [ ] Exclude `Review skipped` and empty thread-reply reviews from the pass count (AC: 5)

## Dev notes

### Bound decisions and requirements

- FR-72 Review through to merge: "a human comment or a fourth round stops the bot and labels the pull
  request for the owner; a skipped review or an empty thread-reply review never counts as a pass."
- The `/land` conditions in `AGENTS.md`.
- The autonomy stance: never self-graduate.

### Files to touch

- `.github/workflows/burndown.yml`, written by a session under the owner's identity

### Testing

- Unit tests for pass detection on recorded status and review fixtures: `Review completed`,
  `Review skipped`, and an empty thread-reply review (AC 5).
- Unit tests for the merge conditions on recorded fixtures: each condition failing alone (AC 3).
- Unit tests for the stop: round four, a human comment, a declared default (AC 2).
- AC 1 and AC 4 live on the first bot pull request, recorded on #949.
