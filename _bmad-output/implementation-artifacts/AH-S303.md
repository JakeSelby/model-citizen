## Story

As a maintainer, I want to run native acceptance case by case from the Studio, so that I check real client behaviour for exactly the cases a change touches.

## Context and value

Pick a client, exactly three cases and the model, and run `native_acceptance.py` against a target from the Studio. Each case shows passed, failed or unverified with its evidence, and a failed case reruns alone at the same commit, reusing the verdicts the partial log already holds.

## Acceptance criteria

1. Given three cases picked, then only those cases run, and each verdict shows with its evidence.
2. Given a rerun at the same commit, then cases that already have a verdict are skipped, as the script skips them.
3. Given an interrupted run, then the verdicts in its partial log are kept and shown.

## Design

### Approach

Add a native-acceptance adapter beside the generic Studio run core. It owns the request DTO, sends
installed, release, branch, worktree and draft requests through #984's TargetService, runs from its
immutable prepared source/profile, builds the fixed `native_acceptance.py` argv without a shell, and turns
the runner's durable JSON-lines progress log into case rows for the Studio. The log remains the
authority: Studio filters it by client, commit and model, keeps the latest line for each selected
case, ignores a torn final line, and never rewrites or deletes completed evidence.

Experiments renders a Mantine panel from that DTO: client, model, case selection, provider basis and
both spend caps first. The preview is returned by paid admission without starting a process and the
single-use confirmation launches that exact selection. The evidence view then renders one
literal `passed`, `failed`, `unverified` or `pending` row per selected case with its observation.
Resume reuses the same progress identity, so the native runner skips passed and failed verdicts and
runs only unverified or interrupted cases. Retrying a failed case creates a fresh progress identity
and selects only that case, matching the qualification runner's documented contract.

Paid launch admission instruments the native runner at its per-case boundary. Claude receives its
native `--max-budget-usd` control on every turn, case totals come from `total_cost_usd`, the set
stops before its next case at `--spend-cap`, and the runner writes the exact result schema the
Studio spend guard validates. A resumed paid set seeds its total from the preserved case spend,
so the remaining cap includes the whole set, while the new result reports only spend incurred by
that process and the usage ledger never counts a preserved case twice. The native adapter estimates
same-scale runs from cumulative per-case progress evidence, so the shared result and estimator contracts
remain unchanged and a partial resume cannot poison future previews with only its incremental cost.
Codex token totals are normalized and priced through the existing
usage/pricing modules for reporting, but Codex launch is refused because it has no in-flight dollar
cap. Missing or malformed accounting refuses settlement and never becomes zero spend.

### Decisions and alternatives

- Preserve and read the runner's native progress format rather than mirror verdicts in a Studio-only
  file. A second record would diverge after interruption and violate file authority.
- Scope resume identity to client, source commit, model and progress ID. A verdict from another
  candidate or model cannot suppress a case.
- Display the full commit supplied by the target resolver as immutable context; the browser does
  not type or override evidence identity. Before launch it displays the target kind/reference and
  says the commit resolves at launch rather than inventing a commit for a dirty worktree snapshot.
- Use a fresh progress ID for an explicit failed-case retry. The runner deliberately preserves a
  failed verdict when the same log is resumed.
- Keep case observations adjacent to literal verdicts and expose parse warnings. Dropping malformed
  complete lines as if no evidence existed would turn corruption into an empty state.
- Refuse paid launch without bounded accounting. Treating native acceptance as free, using the host
  ledger, or inventing zero spend are rejected because each case runs in a disposable home.
- Use client output at the case boundary rather than waiting for each disposable home's detached
  SessionEnd ledger. The ledger can be deleted before it flushes; Claude's result and Codex's event
  stream are the immediate authoritative accounting sources.

### Do not implement

Do not change native acceptance case semantics, qualification evidence, target-profile creation,
the generic run supervisor, navigation, shared Studio styles or the spend-guard contract. Do not
run live clients in automated tests.

## Review findings

- Scope review: target creation belonged to #984. Removed it and now consume only #984's strict
  immutable resolved-target contract; shared route registration remains a serial integration task.
- Quality review: resumed spend was counted as zero. Preserved case spend now seeds the resumed set
  before another case can launch, while incremental run spend remains separate for the ledger,
  with a $0.80-then-$0.20 regression under a $1.00 cumulative cap.
- Quality review: one progress identity allowed concurrent writers and unsafe paths. The runner now
  holds a nonblocking exclusive lock and validates owned private directories/files before writing.
- Quality review: an in-flight preview could resolve after the operator edited inputs. Preview
  generations now invalidate both stale successes and failures, and only the current generation
  can confirm a launch.
- Quality re-review: private-parent checks broke ordinary CLI output locations and cumulative spend
  would double-count resumed usage. Strict directory policy is now scoped to Studio-owned evidence,
  compatibility paths remain supported, and result spend is incremental while cap spend is cumulative.
- Final quality review: incremental resume spend would understate the next same-scale estimate. The
  native adapter now samples cumulative per-case progress while the shared paid result and usage
  ledger remain incremental.
- Final scope and quality review: removed native behavior from generic run/spend contracts, moved
  target identity and estimator state behind the native adapter, made dirty snapshots resumable by
  synthetic commit, bounded malformed case input, and separated completed failures from interruption.
- Final re-review: require exactly three cases at both boundaries, consume #984's TargetService
  without a native resolver/service, normalize all target kinds to full commits, clear stale evidence
  during paid start, restore stored selection on resume, and reject non-finite/invalid metrics.
- Final retry review: exact-three admission applies to fresh sets; a failed row issues a distinct
  one-case retry identity that is admitted only after rechecking its original failed evidence.
  Commit lookup covers every retained native identity, so synthetic worktree commits remain reusable
  after more than one hundred later runs.
