## Story

As a developer, I want Claude Code's plugin evals in the Studio's run store, so that plugin and skill results sit beside the harness's own runs.

## Context and value

Claude Code ships its own efficacy tool: per Anthropic's plugin-evals docs, `claude plugin eval` runs cases with and without a plugin, grades them (a regex, a tool-called check or an LLM rubric), and writes an aggregate result and an HTML report. It measures plugins and skills, not instruction files. It was the only first-party efficacy tool the 2026-09-26 field check found (#1005). Importing its reports puts plugin and skill evals beside the harness's own runs, in the same history and comparison views.

## Acceptance criteria

1. Given a result file from `claude plugin eval`, when `citizen runs reindex` runs, then it is imported as a run with its cases, its two arms (with and without the plugin) and its scores.
2. Given a result file in an unknown format version, then the import skips it and reports it, and never guesses.
3. Given an imported run, then its detail page links the original HTML report.

## Design

### Approach

A new parser, `lib/harness_core/studio/plugin_evals.py`, reads each
`<eval dir>/results/<timestamp>/aggregate-result.json` and normalizes it into the run store's
indexed record, the same shape the benchmark and native-evidence importers produce.
`RunStore._import_repository` calls it during `citizen runs reindex`, after the existing sources,
so an unreadable or unsupported result lands in the reindex `skipped` list with its reason.

Discovery looks in the repository-root `evals/` directory and in each plugin found by a
`.claude-plugin/plugin.json` manifest at the root or up to two directories down, using the
manifest's `experimental.evals` directory when it names a safe relative path. A result or eval
directory that resolves outside the repository is ignored.

The record keeps suite id `claude-plugin-eval`, target kind `plugin` with the plugin names as its
ref, arms `with` and `without` as the result carries them, a `scores` block (overall, mean delta,
cases passed of total, partial and its reason), and one case per result case, keyed
`plugin:<plugin>/<case>`, holding its with and without scores, delta, pass rates and every run with
its grader verdicts. A case passes when its with-arm score meets the suite threshold, which is the
tool's own `casesPassed` definition. A report written beside the result is declared as the second
artifact and named in `report`.

The run detail labels the two artifacts `Result JSON` and `HTML report`; the report entry carries
`href` `/api/runs/plugin-eval-report/<run id>`. That new session-authenticated GET route serves the
original file under a `sandbox allow-scripts` content security policy, and the detail page renders
the entry as a link that opens in a new tab.

### Decisions and alternatives

1. **Exact version match.** Only `schemaVersion` 1, an integer, is read. A string `"1"`, a boolean,
   a missing version or any other number is skipped and reported, never coerced. Unknown fields
   inside a version 1 document are ignored, as the format's documentation asks of readers.
2. **Shape errors skip the file.** An arm other than `with` or `without`, a score outside 0 to 1 or a
   repeated case name makes the whole result skipped with a reason, rather than half-imported.
3. **Status.** A finished run is `succeeded` when every case met the threshold, else `failed`,
   matching the tool's exit code. A partial run is `capped` for `cost_ceiling`, `cancelled` for
   `interrupted`, and `failed` for `auth_failed` or an unknown reason.
4. **Case identities are namespaced** by plugin, so a plugin case never merges into the history of
   a benchmark task that happens to share its name.
5. **The report is served, not embedded.** Showing it through the existing text evidence viewer was
   rejected: that viewer caps at 64 KiB and shows source, not the report. A `file://` link was
   rejected because browsers refuse it from an http page. The report runs third-party inline script,
   so the route sends a `sandbox` policy without `allow-same-origin`: the page gets an opaque origin
   and can reach neither the Studio session nor its API, and `default-src 'none'` stops it loading
   anything. The route maps to `citizen runs evidence`, which already prints a declared artifact, so
   it needs no new CLI command.
6. **The completion time is derived** from `startedAt` plus `durationSeconds`, so duration shows in
   history the same way it does for other runs.

### Do not implement

- Running `claude plugin eval` from the Studio, or a suite catalog entry for it.
- Discovering results written to a custom `--output-dir` outside a discovered eval directory.
- Showing per-case scores or deltas in the run detail page; they are in the indexed record.
- Publishing or linking the claude.ai-published copy of a report.

## Review findings

1. An extreme `durationSeconds` or a start near year 9999 overflowed and aborted reindex. Durations
   are now capped at a year and any overflow skips that file with a reason.
2. The file cap was checked after every result was parsed. Discovery now stops before reading once
   the cap is passed, and records one skip instead of aborting the benchmark rows already imported.
3. The report route is now tested over real HTTP: sandbox policy on the response, wrong Host,
   missing session, a symlinked report and an oversized report.
4. The stored raw document kept absolute paths; `suite.root`, `plugins[].path` and `tracePath` are
   now removed.
5. Run detail read the whole report to decide availability; it now stops at the bounded stat checks.
6. Added the `changelog.d/1009.added.md` fragment.
