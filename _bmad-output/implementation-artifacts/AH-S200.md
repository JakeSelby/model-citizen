## Story

As a developer using the harness, I want to select a named mode that bundles a set of selections, for
my configuration or one session, so that I can switch the harness into a known shape without setting
each unit by hand, while any key I typed myself still wins.

## Context and value

Epic #552 defines a mode as a named set of selections, with users keeping their own keys above any
mode [Source: #552]. This story adds the mechanism and two shipped modes; #558 adds the `superpowers` mode on top of
it [Source: #558]. On `main` there is no `primitives/modes/` directory and no `docs/modes.md`.
[Source: https://github.com/JakeSelby/agent-harness/issues/557]

## Acceptance criteria

1. **Given** the five sources, **when** selections resolve, **then** a test proves the order default,
   mode, user, project, session.
2. **Given** an unknown mode, or a mode naming an unknown unit or a non-selection key, **when** it is
   selected, **then** it is an error before sync touches a file.
3. **Given** a mode file that switches a core hook off without the acknowledgement, **when** it is
   loaded, **then** it is refused.
4. **Given** a user primitive root, **when** it adds a mode under `modes/`, **then** the mode is
   available; a duplicate name is an error.
5. **Given** `harness config set mode minimal`, **when** `harness sync` runs, **then** it produces the
   documented state and `harness diff` is clean.
6. **Given** the docs, **when** `docs/modes.md` is read, **then** it lists what each shipped mode
   changes, with the precedence rule stated once.

## Design

### Approach

- A mode file is `primitives/modes/<name>.json`: `schema_version`, `description`, then selection keys
  in the #554 selection shape.
- `mode` in `config.json`, or `HARNESS_MODE` for one session, selects a mode; `harness selection`
  reports `mode:<name>` as a source.
- A mode sits below the user's explicit keys.
- Shipped modes:
  - `full`: empty apart from its description; the implicit default.
  - `minimal`: every hook on; the cost, delegation and autonomy stances kept; every other stance `off`
    or `light`; every workflow off.

### Decisions and alternatives

- **A key you typed always wins over a mode** (issue text).
- **User roots may add modes**, with duplicate names refused.
- **Init's defaults sit below the mode (AD-2 mechanism).** `config.json` records the stances
  `harness init` wrote as defaults, with each value, under `init_defaults: {"stances": {name: value}}`;
  the resolver moves each one that still holds its recorded value into an `init` layer between
  `default` and `mode:<name>`. `harness init --yes` and a `config set` that creates the file mark
  every stance; interactive init marks only the answers Enter took, not a typed answer equal to the
  offer; `config set stances.NAME` unmarks that stance, and a hand edit of the value makes it typed. Rejected: treating a value equal to the
  built-in default as unset, which would stop a typed default from beating a mode; and having init
  omit default stances, which changes the written file for every user.
- **Shadowed keys are reported, whatever their value.** `selection()` returns
  `shadowed: {kind: {unit: source}}` for every unit the mode set that a higher layer also set, and
  `harness selection` prints one line per key. `shadowed` joins `sources` as a key a selection
  document may carry, so the output still reads back as a session file.
- **A mode is validated when it is loaded.** Strict resolution refuses an unknown mode, a missing
  `schema_version` 1 or `description`, a non-selection key (including `mode` and `sources`), a unit
  nothing installs, a switch value other than `on` or `off`, and a core hook `off` without
  `core_switches_acknowledged: true` in the user configuration. A hook is known when it declares a
  manifest or is one of the four core ids. Duplicate names are refused on every strict resolution,
  selected or not. Non-strict callers (hooks) run without a mode they cannot use.
- **Stance variants are not checked in the mode file.** `sync` checks every layer's variants the
  same way, so a mode's unknown variant fails there, as a user's does.

### Do not implement

- The `superpowers` mode and the `delegated` variants (#558).

### Recorded gap against the spine and PRD

AD-2 requires that "a developer's explicit choice shadows a mode key, while a value `harness init` wrote
as a default does not", and names #557 as the story that picks the mechanism. FR-16 makes it testable:
after a default `init`, selecting the `superpowers` mode changes `plan-ceremony`, and `harness selection`
names every mode key a user key shadowed. This issue's acceptance states only that a user's explicit key
wins; it has no criterion that separates init-written defaults from typed keys, and none for reporting
shadowed keys. Recorded here; the issue was not changed.

## Review findings

CodeRabbit, round 1 on PR #862, all fixed in the shepherd's review commit:
- Interactive init marked a typed answer equal to the offered value as an init default. `_ask_entry`
  now reports whether Enter took the default, and only those answers are marked.
- A mode file could set a stance to `null` or an empty string and still validate. `validate_mode`
  now refuses a stance value that does not name a variant.
- A stance edited by hand in `config.json` after init stayed in `init_defaults`, so a mode overrode
  it. `init_defaults` now records each value, and a stance counts as init's only while it holds it.
- Outside the diff: the `docs/preferences.md` selection example named an unshipped mode; it now
  names `minimal`.

CodeRabbit, round 2, answered without a change:
- A mode naming a nonexistent stance variant, such as `autonomy: aks`, passes the resolver, and
  grade-bash then grades under its default threshold. The resolver treats variants as opaque in
  every layer and sync checks them, and the same fallback follows from `HARNESS_STANCE_AUTONOMY` or
  a session file, so it predates modes. The fix is grade-bash failing to its strictest threshold on
  an unknown variant, raised as its own issue.
