# AH-B024 — harness sync ignores HARNESS_STANCE_ variables that harness stances honours

## Reproduction

Set `HARNESS_STANCE_<DIM>` to a variant other than the one selected in the configuration file, then run
`harness stances` and `harness sync`. The issue records it natively on `codex-cli-linux` for `commits`,
`cost` and a custom dimension, during the 0.11.0 qualification:

- `harness stances` reports the environment's variant;
- `harness sync` exits 0 and leaves the previously selected variant linked;
- `harness diff` reports no drift.

## Root cause

At `origin/main` the behaviour is deliberate in code, and the doc disagrees with it:

- `_cmd_sync_unlocked` in `bin/harness` collects every `HARNESS_STANCE_*` and `HARNESS_IDENTITY_*`
  variable, plus `HARNESS_PROJECT_CONFIG` and `HARNESS_PERMISSIONS`, and removes them before it loads
  the configuration. When any is set it prints: "sync projects user defaults; project/session overrides
  stay in the session". The drift check filters the same variables.
- `cost_table` in `bin/harness` gives the reason: "a sync projects user defaults and a session's
  `HARNESS_STANCE_*` stays in the session".
- Commit ca5547f, "fix(stances): keep session choices out of global projections (#106)", introduced the filtering.
- `docs/preferences.md` still says: "At sync time the env value is what gets linked."

So the issue's "ignores" describes intended code with a stale doc.

## Acceptance criteria

The issue asks for one of two outcomes, and ties the choice to #276:

1. **Given** a `HARNESS_STANCE_<DIM>` variable, **when** `harness sync` runs, **then** either the
   env-selected variant is linked as `docs/preferences.md` says, or the doc says the variable affects
   resolution only.
2. **Given** the outcome chosen, **when** `harness diff` runs afterwards, **then** it agrees with
   what `harness stances` reports, or the doc explains why not. [ASSUMPTION: the issue names the diff
   observation but does not state a criterion for it.]

## Design

Decided by the owner on 2026-09-26, through #276 (option 2): a project or session stance selection
reaches the model at session start, where `harness-session.py` injects the resolved variant's text
when it differs from the synced one, within the always-loaded budget. #894 built that. So #294 takes
the issue's second exit: the doc says the variable affects resolution, not the linked text.

- **Sync.** `harness sync` keeps projecting user-level selections only, as it has since #106. A
  `HARNESS_STANCE_<DIM>` variable is a session selection: `harness stances` and the hooks resolve it,
  the session-start hook injects its text, and sync never links it. Sync's scope notice stays as it is.
- **Diff.** `harness diff` reports linked state against the user's layers, so a session selection is
  not drift. When a project or session selection is set it now prints a scope line saying so,
  mirroring sync's notice; `--quiet` output is unchanged.
- **Docs.** `docs/preferences.md` loses "At sync time the env value is what gets linked" and says the
  above; `docs/sync-model.md` gains the diff line.
- **Alternatives rejected.** Linking the env variant at sync: it writes a session's choice into a
  global projection every other session reads, which #106 removed and FR-2 forbids.

Do not implement: a sync that writes a session's selection into a global projection. Commit ca5547f
removed exactly that.

## Regression test

`tests/test_sync_session_stance.py` runs a real sync in a temporary home with the user selecting
`testing: required` and `HARNESS_STANCE_TESTING=off` set. It asserts the scope notice, that the linked
`testing.md` resolves to `required.md`, that `harness stances --json` reports `off` from the `session`
layer, and that `harness diff` exits 0 with its scope line and "no drift". A second case asserts no
scope line from either command without a session selection. The first case fails without the diff
change.

## Review findings

- CodeRabbit, PR #907, round 1: the `diff` scope line compared `user_defaults_env()` with the whole
  environment, which also drops `HARNESS_IDENTITY_*`, so an identity-only override printed a stance
  scope notice. Fixed: `selection_override` checks the stance-selecting keys directly, with an
  identity-only regression test that fails on the old comparison.
- CodeRabbit, PR #907, round 2: a blank `HARNESS_STANCE_*` value chooses nothing in the resolver, but
  `selection_override` still counted it. Fixed: a key counts only with a nonblank value, with a test.
- CodeRabbit, PR #907, round 3: a project or session config that names no stance still counted.
  Fixed at the root: `selection_override` asks the resolver for the stances with and without the
  project and session layers and reports a selection only when they differ, which covers every
  earlier case too; a test uses a project config that names no stance.
- CodeRabbit, PR #907, round 4: `docs/sync-model.md` and the changelog fragment said the notice
  appears whenever a selection is set. Fixed: both say it appears when a project or session selection
  changes a resolved stance.
