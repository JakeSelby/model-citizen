## Story

As a developer, I want the evaluation tiers, and a rule's unit eval one click from that rule, so that I can test whether a single rule works.

## Context and value

The v0.15.0 evaluation engines become catalog suites: offline replay of stored transcripts through the rule-detector registry (#510), the hook permutation matrix under each stance variant (#511), the micro-task tier on a cheap model (#512), and the two-by-two unit evals of one rule (#797). A developer runs a rule's unit eval from that rule's library page.

## Acceptance criteria

1. Given a rule with a unit eval, when "Test this rule" is pressed, then the two-by-two runs against the chosen target and the result shows on the rule's page.
2. Given the hook matrix, then each hook, variant and recorded call shows its verdict in a grid.
3. Given an engine not yet merged, then its suite is absent from the catalog, not broken.

## Design

### Approach

`lib/harness_core/studio/eval_tiers.py` turns four engines into allowlisted suites in
`policy/studio/suites.json`, launched only through the run supervisor (#980):

- `rule-detection` (free, #510) runs `cost_bench.py detect --raw` over a copy of a saved raw
  directory and prints the engine's detection rows.
- `hook-matrix` (free, #511) loads `tests/fixtures/hook-calls/hook_matrix.py`, computes its compact
  matrix and lists every cell that moved from the committed one.
- `micro-tier` (#512) and `unit-eval` (#797) spend usage. Each resolves its target through the
  replay's resolution (#984), so it gets a full revision and refuses a dirty worktree or an edited
  draft. It previews through `RunSupervisor.spend_preview` and starts only with the guard's one-use
  token (#985). The runner calls `cost_bench.py replay --exploratory` from the repository with that
  revision as `--tag`, then writes the guard's spend result from the engine's `spend.json` and records
  `cost_bench.py summarise --json` verbatim as the analysis.

`/api/evals/catalog`, `/run`, `/preview`, `/start` and `/result` serve the Experiments page's tier
panel and the Library's "Test this rule" on each rule's page. The paid result goes through #1062's
generic analysis view (`engineLeaves`), and the hook matrix shows as a calls-by-variants grid per hook.

### Decisions and alternatives

1. **Engine presence decides the catalog.** Each tier names the engine files it needs. A missing
   file leaves the tier out of `/api/evals/catalog` and the Library, and a launch is refused with
   `eval_engine_absent` (404). The rejected alternative was a static list that fails at run time.
2. **The engine runs from the Studio's repository, with the target's revision as `--tag`.** This is
   the live replay's model: one engine version and a parity check that holds. Running from the
   target's own checkout was rejected, because an older target lacks the engine.
3. **Paid tiers always run exploratory.** No pre-registration path is offered, so no history row is
   written. This is the conservative default; registered tier runs stay on the command line.
4. **One spend case per run, named after the suite.** The engine reports a single charged total, and
   per-arm cases would be a Studio-derived split.
5. **"A rule with a unit eval" means every library rule, while the unit-eval engine is present.**
   The engine refuses a unit it cannot separate before any spend. Offering only rules follows the
   story's wording; skills, roles, workflows and hooks are left out.
6. **Rule detection reads a user-supplied absolute raw directory.** Studio replays keep no raw
   streams to offer as a list. The directory is copied first, so it is never written.

### Do not implement

- No registered (history-writing) tier runs, no pack selection for the micro tier or the unit eval,
  and no task subset for the unit eval: the engine's defaults apply.
- No Studio-derived figure, verdict or re-shaped grid: engine output only.
- No `product.json` line (the Studio landing copy goes to the maintainer separately).

### Testing

- `tests/test_studio_eval_tiers.py` covers several things. The catalog is filtered by engine
  presence (AC 3). The unit eval runner's analysis equals `cost_bench.py summarise --json` and
  `studio/tests/fixtures/eval-unit-analysis.json`, and its spend result passes
  `spend_guard.read_result` (AC 1). The hook matrix runner equals the committed engine matrix, and
  its expanded cells match `studio/tests/fixtures/eval-hook-grid.json` (AC 2). Rule detection
  equals the CLI. The file also covers admission (preview, confirm, changed revision, dirty
  target), route refusals, and live-server 401/403/400 on every route.
- `studio/tests/eval-tiers.test.ts` checks four things. The analysis fixture is shown leaf for
  leaf through the generic view. The grid expansion digest matches the engine's. The grid renders
  every call and variant. The tier panel and "Test this rule" are absent without their engine.
- Regenerate both fixtures with `python3 tests/test_studio_eval_tiers.py --write`.
