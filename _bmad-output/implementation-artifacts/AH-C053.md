## Goal

Prove the Python 3.9 floor on every pull request and in the merge queue, so a 3.9 syntax error cannot
merge and surface only at release.

The issue states the gap: CI runs the suite on the runner's system Python only, and the 3.9 floor is
proved locally and by the release lifecycle runs.

At `origin/main`, `.github/workflows/ci.yml` runs on `push` to `main`, `pull_request` and
`merge_group`. Its comment in the `smoke` job says: "No job in this workflow pins an interpreter, so
this one runs the same Python as `test`; the 3.9 floor is proved by running the suite locally under
it." `AGENTS.md` asks contributors to "keep the code free of syntax newer than 3.9", and says tests run
under the system Python 3.9 and under a current Python.

## Acceptance criteria

From the issue:

1. **Given** a pull request that uses syntax newer than Python 3.9, **when** CI runs, **then** a
   required check fails.
2. **Given** the merge queue, **when** a queued pull request is tested on the merge commit, **then**
   the same 3.9 check runs there. [ASSUMPTION: from the scope line "on every pull request and in the
   merge queue"; the acceptance section names only pull requests.]

## Tasks

- [x] Add a CI job that runs the suite, or at least a syntax check, under Python 3.9 (AC 1). Both:
  the `test-py39` job runs the whole suite under 3.9, and `tests/test_python_floor.py` parses every
  tracked Python source with the 3.9 grammar inside the required `test` check.
- [x] Trigger it on `pull_request` and `merge_group` (AC 2). The workflow already has both triggers;
  the new test asserts they stay.
- [ ] Add `test-py39` to the `main` ruleset's required checks, so a runtime-only 3.9 failure also
  blocks the merge (AC 1). Left to the repository owner: a ruleset change is outside the diff.
- [x] Prove it: a probe file holding a `match` statement, staged locally, failed
  `test_every_tracked_python_source_parses_at_the_floor`; the probe was then removed.

Scope from the issue: "Run the suite, or at least a syntax check". Which one is not decided.

## Dev agent record

- **Default taken:** CI runs the full suite under Python 3.9 as a parallel job, `test-py39`, that is
  not a required check. Making it required is the repository owner's ruleset step; no ruleset was
  changed.
- **Verification:** the new tests pass under Python 3.9 and 3.14 locally; the repository gate ran
  on the commit.
- **Licensing review:** `actions/setup-python` at `ece7cb06caefa5fff74198d8649806c4678c61a1` is the
  `v6.3.0` tag per `git ls-remote`; its `LICENSE` at that commit is MIT, GitHub, Inc. and
  contributors, and upstream restricts its bundled npm code to permissive licences. It runs on the
  CI runner and ships in no artifact, so it is recorded in `THIRD_PARTY_NOTICES.md` rather than in
  `third-party.json`.
- **PRD:** NFR-2 carries a dated `Default taken:` amendment saying this change closes the gap for
  syntax and that `test-py39` blocks a merge once the ruleset requires it.

## Review findings

- **CodeRabbit, `tests/test_python_floor.py`: `feature_version=(3, 9)` is best effort under a newer
  parser.** Valid: Python 3.14 accepted `f"{d["k"]}"` with `feature_version=(3, 9)` and Python 3.9
  rejected it. Fixed: the required `test` job now installs 3.9 through the same pinned
  `actions/setup-python`, off PATH, and runs `tests.test_python_floor` under it before the suite; a
  new test pins that step, and another asserts 3.9 rejects the sample.
