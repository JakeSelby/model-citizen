## Story

As a developer, I want to compare two runs with paired intervals and an honest verdict, so that I can tell a real change from noise.

## Context and value

Pick two runs of the same suite and see them paired by task or case: the per-task deltas, the pass-rate difference and the Cost-of-Pass ratio with the paired, task-clustered intervals from #795, and a verdict worded by the evidence standard (improved, worse or inconclusive). A pair that cannot be compared (different suites, task sets or models) says why instead of comparing.

## Acceptance criteria

1. Given two runs on different task sets, then the comparison is refused and names the difference.
2. Given a ratio whose interval spans 1.0, then the verdict reads inconclusive, whatever the point estimate.
3. No figure shows without its interval and trial count when the method gives one.
4. The numbers equal the analysis library's for the same rows, in tests.

## Design

### Approach

A side is one target of one finished live replay, named by run id and target index (1 or 2). Its
harness arm's native rows are the run under comparison; its bare arm stays with the target's own
recorded `cost_bench.py summarise` analysis, which is shown beside it unchanged.
`lib/harness_core/studio/compare.py` loads both sides through the run supervisor, reads the rows
the replay summary lists, and checks that they ran the same tasks, model, trials per task and
evaluator pack (the identity #1062's `comparison_key` hashes) under the same per-trial budget cap
and the same pinned row stamps (CLI version, container platform, price table, replay tier),
and that each side's run succeeded, did not stop at its spend cap and finished every task and trial
it requested. Every difference and shortfall refuses the comparison and is named (AC 1). A comparable pair is relabelled `base`
and `candidate` and passed to `replay_stats.compare` with the base as control; its output is
returned verbatim, so every estimate, effect, paired task-clustered interval, n and reading is the
engine's (AC 2, 3, 4). A draft side carries `replay.draft_staleness`, the check #1062's draft
comparison records already use.

`POST /api/runs/compare` and `citizen runs compare BASE CANDIDATE [--json]` call the same
`compare_runs`. The Experiments page gains a compare panel, prefilled from a replay's first
matched draft comparison, that shows refusals, one headline per measure built only from engine
fields, both sides with their recorded analyses, and every leaf of the engine output through
#1062's generic `engineLeaves` view.

### Decisions and alternatives

- `replay_stats.compare` over `replay_stats.analyse(arms=...)`: `analyse`'s verdict is defined for
  harness against bare only (`replay_pair` strips it for two harness arms), while `compare` reads
  each measure against a control for any arm and says `inconclusive` when the interval spans no
  effect. Both use the same seeded task bootstrap, so their Cost-of-Pass intervals agree.
- The reading is the engine's (`lower`, `higher`, `inconclusive`, `unavailable`), shown with the
  preferred direction: `lower (better)`, `lower (worse)`, or the reading alone when it is
  inconclusive or the measure has no direction. The engine states no direction in its output, so
  `compare.PREFERRED`, next to the engine call, is the one table: a lower Cost-of-Pass and a higher
  pass rate, the two measures the evidence standard's decision rule judges. Per-attempt cost,
  tokens, turns and tool calls get no direction: a run that gives up early is cheaper per attempt
  without being better.
- A direction is withheld, and the plain reading shown with the neutral badge, whenever the result
  could not be cited as evidence: either side not pre-registered or the arm exploratory
  (docs/evidence-standard.md, protocol items 1 and 7), or runs from different dates.
- The pinned stamps refuse on a difference (protocol item 2, pinned inputs, and item 4, held
  constant). The run date is item 4's run window, which two separate runs never share, so a
  different date is named and withholds a direction rather than refusing the comparison. `flat` is never shown: the
  engine says inconclusive, not equivalent. Better, worse and undirected badges differ in fill and
  border as well as colour.
- Each headline carries the engine's `estimand` and, when the engine marks the arm exploratory,
  its reasons, as the engine's own text report does.
- Refusal requires each side to have finished what it requested, in a succeeded run that did not
  stop at its cap, because `compare` silently pairs only the tasks both arms share; a run stopped at
  its cap would otherwise compare a subset. The per-trial budget cap must match too: it is the
  native `--run-cap`, which bounds both cost and pass rate.
- A stale draft side is still compared and marked stale in the panel, the CLI text and the JSON
  `stale` list, rather than refused. Only drafts are checked; any other target reads
  `freshness not checked`, never `current`.
- A refused comparison answers 200 with its reasons; an unknown run is 404, malformed input 400, an
  unfinished or unreadable run 409. The CLI exits 1 on a refusal and 2 on an error.

### Do not implement

No interval, ratio, delta or reading computed in Studio or the browser; no per-task delta table,
which needs an engine breakdown for two harness arms (`cost_bench.per_task` covers bare against
harness only) and is left to a follow-up issue; no matched-rerun action; no
change to the replay runner or to live configuration.
