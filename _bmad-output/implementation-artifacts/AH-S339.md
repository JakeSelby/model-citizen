## Story

As the maintainer, I want a registered run to take two or more models as separate strata, so that a
result on one model is not read as general and each model's verdict stands on its own rows.

## Context and value

Epic #1175 asks whether the harness result generalises beyond one model. Before this story
`replay --model` named one model, every arm ran it, and `summarise` read one row set. A second model
needed a second invocation with nothing tying the two together, and nothing stopped rows from two
models being analysed as one sample, which would pair a task across models.

## Acceptance criteria

1. **Given** `replay --model A,B` or `--model A --model B`, **when** the run starts, **then** each
   model runs as its own stratum with its own schedule, caps, preflight and arm builds.
2. **Given** a stratified run, **then** every row carries `model` and `stratum`, and each stratum's
   rows land in `<tag>/<model>/results.jsonl` with their own history row and series.
3. **Given** `--dry-run` with two models, **then** it lists each stratum and prints its worst-case
   price.
4. **Given** rows from two strata, **when** `summarise` runs, **then** every section is reported per
   stratum, and `--pool` is refused unless the run's pre-registration fills **Pooled analysis**.
5. **Given** rows from two strata, **then** SM-2's analysis refuses them as one sample.
6. **Given** an evidence bundle from a stratified run, **then** `design.strata` records every model
   and each row's `stratum` must be the design's model.

## Design

### Approach

`cmd_replay` parses `--model` with `replay_strata.parse_models`. One model runs exactly as before.
Several models run `_cmd_replay` once per model on a copy of the arguments carrying `stratum` and
`strata`, so every existing control applies per stratum unchanged. `replay_tag` writes a stratum's
rows under its own folder and the stamp adds the two keys. `summarise` groups rows by `stratum`,
runs the existing report on each group, and pools only through `replay_strata.pool`, which reads
the plan at its registered commit.

### Decisions and alternatives

- A stratum is a whole run per model rather than models interleaved in one schedule: each keeps its
  own spend cap and preflight, and a single-model run's code path is untouched.
- Pooled rows relabel tasks as `<stratum>/<task>`, so the bootstrap clusters task-and-model pairs;
  pairing a task across models was rejected because the arms of different models are not paired.
- An evidence bundle holds one stratum and records the others in `design.strata`, rather than the
  verifier learning multi-model schedules.

### Do not implement

No interleaving of models within one schedule, no cross-model contrast or interaction test, and no
stratum support in the micro tier, which pins its manifest's model.

trial is exploratory, so `--pool` reads the registered plan, not today's file.
