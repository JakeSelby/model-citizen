## Story

As a harness maintainer, I want every CLI selection read to go through `policy/hooks/posture.py`, so
that the CLI and the hooks can never act on different stance variants.

## Context and value

AD-2 in the 2026-09-23 spine makes `posture.py` the only resolver and records the CLI's second ladder as
a migration still in progress; epic #636 exists to close such migrations [Source: #636]. On `main`, `bin/harness`
`load_config` implements its own precedence (the example config, the user config, the
`HARNESS_PROJECT_CONFIG` file restricted to stances, then `HARNESS_STANCE_*` and other session
variables), beside `posture.resolve(env, strict, table)`. The CLI already loads `posture.py` through
`load_posture()` for the lint's sidecar validation, but not for stance precedence.

The issue cites #294 as the evidence of disagreement: `harness stances` honours `HARNESS_STANCE_*` while
`harness sync` ignores it.
[Source: https://github.com/JakeSelby/agent-harness/issues/643]
[Source: https://github.com/JakeSelby/agent-harness/issues/294]

## Acceptance criteria

1. **Given** the CLI, **when** it needs a stance, **then** nothing outside `posture.py` resolves stance
   precedence.
2. **Given** every layer, **when** a test compares `harness stances` output with what sync applies,
   **then** they agree.
3. **Given** #294, **when** this lands, **then** #294 closes through this change or together with it.

## Design

### Approach

Route every CLI selection read through the kernel resolver and remove the second ladder in
`load_config`. Non-stance keys (identity, permissions, manage flags) are outside this issue's text.

### Decisions and alternatives

- **One resolver, not two kept in step:** the issue removes the ladder rather than syncing it with
  `posture.py`.
- **`harness stances --json` keeps its shape** across the migration, because the session hook reports
  stances through it (AD-2).

### Do not implement

- The selection document and switch kinds (#554), which also touch the resolver.
- Changes to non-stance configuration keys.

### Recorded contradiction

Criterion 2 compares `harness stances` with "what sync applies, for every layer". On `main`, sync
deliberately withholds session and project keys (`HARNESS_STANCE_*`, `HARNESS_IDENTITY_*`,
`HARNESS_PROJECT_CONFIG`, `HARNESS_PERMISSIONS`) and prints "sync projects user defaults;
project/session overrides stay in the session", a rule introduced in commit ca5547f (#106). FR-2 also requires that a
session override never rewrites the user's global selection. For the session and project layers, then,
sync applying what `harness stances` prints would contradict FR-2. #294 itself offers the other exit [Source: #294]:
document that the variable affects resolution only. Which one holds is not recorded; the issue was not
changed.

### Completion notes

- #554 had already routed `load_config` through `posture.selection()`, but it still laid the example
  and user stances under the resolver's answer. That merge is gone: `cfg["stances"]` is the
  resolver's answer, `None` values dropped, and nothing else. Behaviour is unchanged, because the
  resolver already returns every built-in stance and every usable user value.
- The env filter sync and `harness diff` each spelled out is one helper, `user_defaults_env()`. It
  chooses which layers the resolver is handed; it decides no precedence.
- `harness stances --json` keeps its shape.
- The session-layer contradiction was not settled here. The parity test holds today's FR-2
  behaviour: the default, user and mode layers agree exactly with what a sync links, and for the
  project file, session file and `HARNESS_STANCE_*` a sync links what `harness stances` prints with
  that layer withheld, and prints its scope notice. If #294 settles the other way, that test's
  session case is the one to change. #294 therefore stays open.
