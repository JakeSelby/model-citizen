## Story

As a developer, I want to run a suite against my installed version, a release, a branch, a worktree or a draft in isolation, so that I compare versions and test drafts without touching my live harness.

## Context and value

Every run names its target, and the target's harness is built into a temporary home the way `cost_bench.py replay --tag` builds a tag, never into the live one. A target is the installed version, a release tag, a branch or commit, a managed worktree including its uncommitted work (snapshotted as a commit first), or a Studio draft at a checkpoint. A draft's configuration goes into the profile with it, so a stance change is what gets measured.

## Acceptance criteria

1. Given a draft target, then the run's profile carries the draft's modules and configuration, and the live home is unchanged, byte for byte.
2. Given a worktree with uncommitted changes, then the run records the snapshot commit it ran, and the worktree is left as it was.
3. Every run record carries the target's version, commit, draft and config digest.
4. Given a suite that does not support a target kind, then the catalog refuses the run before it starts.

## Design

### Approach

Resolve every supported target to a full commit before the supervisor writes its immutable creation
record. Reserve the run identity and queue position under the supervisor lock, build outside it, then
atomically finalize the authoritative record or recover an abandoned reservation. Clone that commit
beneath the run-owned target directory, write configuration only into its mode-0700 profile, and
invoke the target checkout's own `bin/harness sync` there. The profile's links therefore point at the
kept immutable checkout beside it, never at the installed checkout. The creation record binds both
prepared paths, and the detached worker executes the suite from that immutable source checkout.

A managed worktree is snapshotted in a private clone: capture its revision, complete tracked diff and
untracked manifest, apply that image, then verify the same image still exists before committing with a
fixed Studio author. One retry tolerates a concurrent edit; a second mismatch refuses a torn target. A
draft uses the existing draft read/checkpoint authority for the saved revision and configuration, then
clones that revision. Run creation records version, full commit, draft identity and the canonical
configuration digest.

### Decisions and alternatives

- Use the harness's existing `sync` command as the sole profile projection authority, matching the
  built-profile rule already used by replay; reject a second implementation of projection semantics.
- Keep the cloned source beside the profile for the life of the run because native projections are
  links into that checkout; reject deleting the source after sync or linking back to live source.
- Snapshot dirt in a clone rather than stashing, resetting or committing the selected worktree. The
  source checkout's index, branch, files and untracked work remain byte-for-byte as selected.
- Resolve target support through the suite catalog before target resolution or profile construction,
  so an unsupported kind cannot create files or launch a process.
- Require callers to supply the repository or a target service explicitly; catalog relocation cannot
  silently disable target preparation. Run target-controlled sync with a minimal credential-free
  environment and mandatory host isolation: macOS sandbox denial or a Linux network namespace that
  fails closed when unavailable. Reject checkout/profile symlinks that escape, are broken or loop.
- Keep clone, Git pruning and sync outside the global supervisor lock. Reservations are mode-0600
  recovery records, so concurrent builds proceed while dead preparation state is cleaned safely.
- Validate paid confirmation before preparation, but consume it only after the target built and the
  durable creation record exists. Recovery consumes a pending token only when its record survived;
  build/durable-write failure leaves it reusable. Recovery reads the authoritative sidecar rather
  than its disposable JSON cache, and an extant preparation reservation blocks admission until token
  consumption completes.

### Do not implement

- Target pickers, run-console presentation and server routes owned by the suite/native-run stories.
- Network fetches for missing branches, commits or releases; only locally available Git objects run.
- Applying, rebasing or editing a draft; this story consumes saved checkpoints only.
- Container/process isolation beyond the already approved disposable-home run boundary.

### Testing

`tests/test_studio_targets.py` builds installed, release, branch and full-commit fixtures; proves a
dirty registered worktree becomes a new snapshot commit while its status and bytes stay unchanged;
builds a draft through the cloned target's canonical `bin/harness sync` while comparing every live-home
directory, symlink, mode and file byte before and after; asserts a real resolved/built target's version,
commit, draft and configuration digest survive the authoritative creation sidecar and index; and proves
an unsupported kind calls neither the profile builder nor process launcher. Security regressions prove
ambient credentials are absent from canonical sync, escaping committed/untracked symlinks are refused,
committed/untracked symlink loops fail with a bounded unsafe-target error, Linux either wraps sync in a
network namespace or fails closed, and a repeatedly changing worktree cannot produce a torn snapshot.
A release-target execution regression proves the suite observes target source rather than the run-state
directory. Paid regressions prove build/durable-write failure preserves confirmation and post-record crash
recovery consumes it exactly once. A concurrency regression proves two target builds overlap while
list/recovery remains responsive, dead reservations are removed, live ones survive and both records
finalize. Existing run-supervisor and run-store suites prove lifecycle, sidecar and rebuild compatibility.
`bin/harness lint`, sprint-status generation/check, audit, focused unit tests and `git diff --check` form
the local story gate.
