# AH-B109 — bmad_issue_sync.py new and apply fail with HTTP 307 since the repository rename

## Reproduction

On 2026-09-26, in a worktree of `main` at `13ed170`, filing this issue with
`python3 scripts/bmad_issue_sync.py new --title T --kind bug --body-file F --parent 875 --milestone 18`
printed `bmad issue sync: gh: HTTP 307`, exited 1 and filed nothing.

The same day, `echo '{}' | gh api --method POST repos/JakeSelby/agent-harness/issues --input -` returned
HTTP 307 with a "Moved Permanently" body, while the same POST to `repos/JakeSelby/model-citizen/issues`
reached the endpoint and was refused with 422 because the title was missing. A read of the old slug is
redirected: `gh api repos/JakeSelby/agent-harness --jq .full_name` prints `JakeSelby/model-citizen`.

## Root cause

`main()` passes the issue map's `repository` to `create_issue`, `reserve` and `fetch_issues`, and
`apply_manifest` and `verify_remote_artifacts` read it for their own calls. The map keeps the slug it was
bootstrapped with, `JakeSelby/agent-harness`, on purpose: `planning_block` renders it into every mapped
issue's body, so changing it would rewrite all of them (#880, acceptance criterion 3).

Since the rename, GitHub redirects a read of the old slug but answers a write to it with 307, and
`gh api` does not follow that 307. Every write the tool sends therefore fails: the POST in `create_issue`,
and in `apply_manifest` the issue PATCH and the sub-issue POST and DELETE. Reads go through the redirect,
which is why `plan`, `refresh` and `audit --live` kept working.

## Acceptance criteria

1. **Given** an issue map whose `repository` differs from the current slug, **when** `new`, `reserve`,
   `plan`, `refresh`, `audit --live` or `apply` runs, **then** every GitHub API call it makes names the
   current slug and none names the stored one.
2. **Given** the same map, **when** `apply` projects an item, **then** the planning block it writes links
   the stored `repository`, exactly as before, so no mapped issue's body changes.
3. **Given** the fix, **then** the issue map is unchanged and the current slug is defined in one place in
   the tool.
4. **Given** the regression tests, **then** they fail against the previous script and pass after the fix.

## Design

Add a module constant `API_REPOSITORY = "JakeSelby/model-citizen"`, the slug every API call goes to,
with a comment saying why it is separate from the map's `repository`. `main()` passes it to
`fetch_issues`, `create_issue`, `reserve` and `apply_manifest`. `apply_manifest(manifest, repo)` and
`verify_remote_artifacts(manifest, repo)` take the API slug as a parameter and use it for every call,
including `gh label create -R`, while `planning_block` keeps receiving `manifest["repository"]`.

Rejected:

- **Resolving the stored slug through GitHub at run time** (`gh api repos/<stored>` or
  `gh repo view <stored> --json nameWithOwner`, both of which print `JakeSelby/model-citizen` today). It
  would follow a future rename without a code change, but every write would depend on the old-name
  redirect, and a repository that later took the old name would receive the writes silently, the hazard
  #900 records. A constant fails loudly with a 307 on a future rename instead.
- **`gh repo view --json nameWithOwner` with no argument.** It resolves the checkout's remote, which can
  be a fork or still name the old slug, rather than the repository the map describes.
- **Changing the map's `repository`.** #880 keeps it, since `apply` would then rewrite the planning block
  of every mapped issue.

Must not change: the map's `repository`; the planning-block text of any mapped issue; `bootstrap`'s
`--repo` default, which #880 owns; and the order of `plan`, `refresh` and `audit --live`, which make no
API call before the local audit passes.

## Regression test

In `tests/test_bmad_issue_sync.py`:

- `apply_manifest` against a map stored as `owner/old`, given `owner/new`: every PATCH, sub-issue POST
  and DELETE, the label `-R` and the tree read name `owner/new`, and the PATCHed body's planning block
  links `owner/old`.
- The CLI wiring: for each of `new`, `reserve`, `plan`, `refresh`, `audit --live` and `apply`, with a map
  stored as `owner/old`, the slug that reaches `fetch_issues`, `create_issue`, `reserve` or
  `apply_manifest` is `sync.API_REPOSITORY`, never the stored one.

Both fail against the previous script, where `apply_manifest` takes no slug and `API_REPOSITORY` does not
exist.
