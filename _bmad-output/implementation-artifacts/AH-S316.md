## Story

As a maintainer, I want the end-to-end flows and performance budgets checked in CI, so that the Studio never regresses unnoticed.

## Context and value

Playwright flows run the Studio against a fixture home in CI: open, tune in a draft, run a free suite, compare, apply and roll back. Performance budgets fail the build when broken: first load, API latency and bundle size.

## Acceptance criteria

1. Given CI on Linux with the preinstalled Chromium, then the six flows pass end to end against a fixture home, with no network and no model calls.
2. Given a bundle over its size budget, or a first load over 1.5 seconds on the CI runner, then the job fails and names the budget.
3. Given API p95 latency over 100 ms on the fixture library of 500 modules, then the job fails.

## Design

### Approach

The flows drive the shipped bundle in headless Chrome over the DevTools protocol, the same driver
the Studio browser tests already use, not Playwright. Each test class serves one full-history
clone of the commit under test, and each test a fresh fixture home, so drafts (the first-run
guide's fixed `first-run` draft included) live in the clone's refs. Two seals end every flow: every
request the tab's documents and WebSockets made, read from the DevTools `Network` events, stayed
on the Studio's loopback origin, and stub `claude` and `codex` executables on the Studio's PATH
recorded no call beyond the offline version and config probes. Negative tests prove each seal
fails when breached. The browser is sealed, not the Studio's own subprocesses. The checks are
opt-in through `STUDIO_E2E=1`, which only the new `studio-e2e` workflow sets, so the plain unit
runs in `ci.yml` and `release.yml` skip them. That workflow runs on `ubuntu-latest` with the runner
image's preinstalled Chrome stable, and fails rather than skips when Chrome is missing.

Budgets live in `scripts/studio_budgets.py` and each failure names its budget: bundle size
(script and style gzip, raw total), first load (every one of five cold-cache reloads to the
rendered shell under 1.5 s) and API latency (p95 of 120 `GET /api/library` requests under 100 ms,
with 500 fixture modules beside the 90 core ones, 590 in all; each sample runs from request to last
body byte, excluding the client's TCP connect and JSON parse but including the server's accept and
per-connection thread start).

### Decisions and alternatives

- DevTools rather than Playwright: no new third-party dependency or browser download, and the
  existing harness already handles the isolated home and macOS keychain.
- The runner's preinstalled Chrome rather than a setup action or apt: nothing is downloaded, it is
  the browser `studio-lifecycle` already qualifies, and `google-chrome --version` fails the job
  when the image drops it.
- A clone of the commit rather than a one-commit copy: `harness lint`, which the draft review and
  the free check run, reads released qualification commits from history.
- The AC's figures are judged literally: the slowest first load and the p95 of all samples.
  Stability comes from running the checks in their own job, never inside the full unit suite,
  and from timing the served request rather than the client. Headroom on a GitHub runner is not
  yet shown: locally the library p95 read 52.6 ms on a quiet host and 110-137 ms at load average
  16, and a shared runner VM is not idle. The first `studio-e2e` run's printed p95 and slowest
  first load are the evidence to record before relying on these budgets.
- Bundle budgets, **pending the maintainer's confirmation**: script 360 KiB gzip, style 48 KiB
  gzip, 1500 KiB raw. The story names no figures; these sit about 25% above the bundle as built
  (script 284 KiB gzip, style 38 KiB, 1.17 MiB raw).
- Triggers: the workflow runs on pushes to `main` and `feature/v0.18.0-studio`, on pull requests
  and in the merge queue, the same events as `studio-qualification.yml`, so every Studio check
  reports on the same commits. The branch name follows the Studio's integration branch, not the
  delivery amendment's version number.
- Concurrency: one group per pull request or ref. A newer push to a pull request cancels the run
  it supersedes; pushes to a branch queue instead, so each commit on `main` keeps its result.

### Do not implement

- No fix to a flow's product code: a defect a flow finds is reported and marked, not repaired here.
- No paid run, model call or network access in any flow.
- No new frontend dependency and no change to the committed bundle.

### Completion notes

Done as designed, with two findings the flows surfaced:

- The served compare route returns 404 `compare_not_found` for any real run. `_runs_compare`
  reads the supervisor off the mutation thread, and the supervisor's run index refuses a second
  thread ("run index update failed"); the route's unit tests use a stand-in supervisor. The
  compare flow first asks the route to compare the seeded runs. A 200 means the fix is present,
  and the flow asserts the engine's paired result in the panel. Exactly the known 404 means it is
  absent, and the flow asserts the panel's matching message. Any other answer fails. AC 1 is not
  met for compare until the fix merges; the fallback is removed then.
- A draft test cannot be planned for a configuration change (a replay builds the harness arm from
  the commit's defaults), and the Studio cannot make a measurable source change to a core module,
  so the draft-test flow proves the plan route's named refusal and that nothing starts, not a
  successful power and spend plan. Adding a personal module (#977) was tried as the alternative
  and is refused the same way, because it adds the personal root to the draft's configuration.
  No change the Studio can make is testable by a replay today, so AC 1 is not met for that step.
