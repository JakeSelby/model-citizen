## Reproduction

1. Work a session past `switches.session_handoff_at`, so the stop is blocked and `context-reset-handoff` is emitted.
2. Run `harness task save`, then keep working with no compaction or `/clear`.
3. Observed: the next session start writes a `followed` response at once. Session `cd4b28f2` was answered this way and then ran on to 893k tokens; nothing in the ledger shows the context never came down.

## Root cause

`policy/hooks/adherence.py` `respond()` returns `followed` on the first `TaskSave` after the emission, and `settle()` writes any followed or not-followed reading as final. The rule's close events (`PreCompact`, `SessionEnd`) are read only when they come before a save, and nothing asks whether a reset happened at all. The observation ledger also records `SessionEnd` without its `reason`, so a `/clear` could not be told from an exit.

## Acceptance criteria

1. **Given** a save and then a `PreCompact`, **when** the emission is settled, **then** the response is `followed` with `context_reset: compacted`.
2. **Given** a save and then a `/clear`, **then** `context_reset` is `cleared`, whichever side of its `SessionEnd` the `Clear` row lands.
3. **Given** a save and then an exit, **then** the response is `followed` with `context_reset: not_reset`.
4. **Given** a save and a session that runs on, **then** no response is written before `UNKNOWN_AFTER`, and after it the response is `followed` with `context_reset: unknown`.
5. **Given** a `SessionEnd` with `reason: clear`, **when** the dispatcher notes it, **then** `Clear` is noted before it; an exit notes `SessionEnd` alone.
6. `rates()` counts each `context_reset` reading under `resets` for a kind with a reset rule, and no other kind gains the key.

## Design

A kind may carry a `reset` rule, a map from event to reading. `context_reset()` reads the session's rows from the emission on, as `respond()` does: the first reset event answers it, and a session end first is `cleared` when a `Clear` row is stamped within two seconds of it, else `not_reset`. `settle()` holds a reset kind's response until that reading exists or the emission is a day old, then writes `context_reset` beside the unchanged `outcome`. The lifecycle notes `Clear` (a `NOTED_ONLY` event) before a `/clear`'s `SessionEnd`.

Rejected: redefining `outcome` as "reset happened", which would break the rate's comparability with rows already written and conflate two questions; and reading the context size from the feed's state, which a `/clear` never shows in the old session. Unchanged: `respond()`, the other kinds, and the soft estimate, which prices `not_followed` only.
