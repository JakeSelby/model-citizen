## Story

As a developer running parallel builders, I want each builder to claim the paths it will write and a pre-write check to catch a live sibling's overlapping edit, so that conflicting edits surface at write time instead of at merge.

## Context and value

Two builders in separate worktrees still land conflicting edits on the same file, and the harness only finds out at merge. The builder role's advice to prefer a new file is guidance only [Source: primitives/roles/builder.md]. The issue cites the field's measured fix as write-time conflict detection over shared state rather than messaging between agents: cross-agent pull-request pairs conflict 41.7% of the time against 19.8% (arXiv 2607.04697), and write-time detection beats a worktree baseline by 18.7 points on Commit0-Lite (arXiv 2605.20563) ([#542](https://github.com/JakeSelby/agent-harness/issues/542)).

The issue is open on the v0.14.0 milestone. Before this story, nothing of it was on `main`: `bin/harness` had no `intent` command and no hook wrote an `intent-overlap` row.

## Acceptance criteria

1. **Given** two live sessions claiming overlapping paths, **when** the second edits a claimed path, **then** it is warned once and denied on the second attempt, and both events are logged; **given** non-overlapping paths, **then** no row is written.
2. **Given** a claim whose pid is dead, **when** a check runs, **then** the claim is ignored and swept; a claim outside the current repository never matches.
3. **Given** logged overlaps, **when** `harness usage --by decision` runs, **then** it shows `intent-overlap` counts, and `harness usage --conflicts` reports landing merge conflicts per week from the same ledger.
4. **Given** this story, **when** it lands, **then** it realises the first acceptance criterion of #120, and #120 keeps depth and topology.
5. **Given** the unit suite, **when** it runs, **then** it covers claim, release, sweep, overlap on a glob and on an exact path, and the Codex gap row.

## Design

### Approach

From the issue ([#542](https://github.com/JakeSelby/agent-harness/issues/542)):
- `harness intent claim <path>...` writes a per-session claim file under the harness state directory holding repo, branch, worktree, claimed paths or globs, pid and `started_at`. `harness intent release` removes it, and the periodic sweep the issue says already clears `feed/` and `sessions/` clears stale claims by dead pid.
- The `builder` role claims the paths its plan names before its first edit, and re-claims when it touches a file outside them.
- A PreToolUse check on `Edit`, `Write`, `MultiEdit` and `NotebookEdit` warns on the first hit against a live sibling's claim in the same repository and denies the second in the same session.
- Every warn or deny writes a `decisions.jsonl` row with point `intent-overlap`, and the landing workflow records whether merging `main` conflicted, so before and after are measurable from one log.
- Codex raises no PreToolUse on edits, so there the builder brief carries the claim step and the gate runs `harness intent check` before commit; the capabilities file names the gap.

### Decisions and alternatives

- Write-time detection over shared state was chosen over messaging between agents, on the cited measurements ([#542](https://github.com/JakeSelby/agent-harness/issues/542)); #539 records the no-peer-messaging rule this builds on.
- Shell-mediated writes stay the job of `grade-bash`; this story does not grade shell.
- No model judgment anywhere.

### Recorded contradiction

The issue fixes the policy as warn on the first overlap and deny on the second. The 2026-09-23 PRD makes it a variant: "Whether a repeated overlap is denied is a policy variant. It is chosen from decision-log counts of denials against abandoned turns" (FR-63), and AD-16 says "Whether an overlap warns or denies is a policy variant." The issue has not been changed to match.

*Resolved 2026-09-25:* the policy is a variant, which honours both. `coordination.repeat_overlap` in the user config, read the way `decisions.py` reads its `telemetry` block, selects it. `deny` is the default and is the issue's behaviour: warn on the first hit on a path, deny the second in the same session. `warn` never denies. A value the hook cannot honour, a block that is not an object and a config that does not parse all mean warn only, because a setting nobody can read must never be what blocks an edit. Every warn or deny writes an `intent-overlap` row that carries the variant in force, which is the count FR-63 chooses the variant from.

### Decisions taken in the build

- **Claims cover planned paths and globs** (FR-63). `claim` accepts paths that do not exist yet; a plain path also covers everything under it.
- **Repository identity is the git common directory,** so sibling worktrees match each other, and paths compare repository-relative. A claim from another repository never matches.
- **The pid is the runtime's,** `CLAUDE_PID` where the runtime exports it and otherwise the first ancestor that is not a shell or an interpreter. The session registry records no pid, so it could not be reused.
- **A claim is keyed and owned by session and worktree.** Subagents share their parent's session id and pid, both in hook input and in the shell, so a claim file and its hit counter are `<session>--<worktree hash>.json`, and a claim is the editor's own only when the edited file is in the claim's worktree and the session id or the pid matches. `release` drops only that one claim. Found in review on PR #856: keyed by session alone, two sibling builders from one session wrote one file, and the session match hid the sibling's overlap.
- **A claim also ends when its worktree is removed.** A subagent's pid is its runtime's and outlives it, so landing, which removes the worktree, is what retires a builder's claim; the builder role needs no release step.
- **Warn-then-deny counts per path** within the session: the warning names a path, and a second edit to that path is the repeat.
- **A warning is context, not a permission decision.** It reaches the agent as `additionalContext` and the user as a notice, and the user's own permission flow still answers for the edit; the coordinator now passes a policy's `additionalContext` through on Claude Code.
- **`harness intent check` denies any overlap under `deny`.** It runs before commit on the runtime with no edit event, where there is no earlier warning to count from; under `warn` it warns and exits 0.
- **The landing record is `harness intent merge [clean|conflicted] [--base REF]`,** a `landing-merge` row. With no result given it probes with `git merge-tree --write-tree`, which touches neither the tree nor the index. `harness usage --conflicts` groups landing merges and overlaps by ISO week.
- **`intent-overlap` and `landing-merge` stay out of `decisions.POINTS`,** as `decision-provider` does: that tuple also sets the decision-provider controls, and `usage --by decision` groups every point it finds in the log.

### Do not implement

- No shell-write grading.
- No messaging between sibling agents.

## Review findings

- CodeRabbit on PR #856 (major): subagents share their parent's session id, so claims keyed by session alone collided between sibling builders and the session-only ownership shortcut hid their overlaps. Fixed: claims and hit counters are keyed by session and worktree, ownership requires the worktree, and `tests/test_intents.py` covers one session with two worktrees.
- CodeRabbit on PR #856 (major): an edit run in worktree A that targets an absolute path in sibling worktree B took B's root as the editor's, so B's claim under the same session or process read as the editor's own, and the hit counted under B's slot. Fixed: `editor_root` takes the editor's worktree from the event's `cwd` for ownership and the hit counter, while the target still decides repository and relative path; `tests/test_intents.py` covers a cross-worktree absolute target.
