# AH-B105 — grade-bash's confirm marker is refused as a bypass in auto mode, so an approved irreversible command can never run

## Reproduction

Claude Code in auto mode, autonomy stance `execute`:

1. The agent runs a grade-3 command, for example `gh api -X DELETE repos/<owner>/<fork>/git/refs/heads/<branch>`. `grade-bash` denies it and tells the agent to rerun it with `HARNESS_CONFIRMED=1` once the user agrees.
2. The user replies "Run it".
3. The agent runs `HARNESS_CONFIRMED=1 gh api -X DELETE ...`. The auto-mode classifier refuses it: `Permission for this action was denied by the Claude Code auto mode classifier. Reason: [Auto-Mode Bypass].`

Result: in auto mode no command the hook gates can ever run, whatever the user says. The governance binding that follows this story would hit the same wall for every level-1 or level-2 action.

## Root cause

In `auto` and `bypassPermissions` the hooks reference says an `ask` decision is ignored, so `grade-bash` has to deny, and its only confirmation channel is a marker the agent adds to its own command (`policy/hooks/grade-bash.py`, module docstring and `MARKER`). The auto-mode classifier judges each call on its own. It reads a prefix that switches off a safety hook as an attempt to bypass it, so the channel is closed by design. `bypassPermissions` has no classifier, so the marker still works there.

## Acceptance criteria

1. **Given** auto mode and a gated command denied with approval code `C`, **when** the user's next prompt contains `approve C`, **then** that exact command, with no marker, passes `grade-bash` once.
2. **Given** that approval has been used, **when** the same command runs again, **then** it is denied again.
3. **Given** an approval for `C`, **when** a different command runs, or the same command runs in another session, **then** it is denied.
4. **Given** an approval older than thirty minutes, **when** its command runs, **then** it is denied.
5. **Given** a prompt that is not solely one or more `approve <code>` tokens separated by whitespace or commas, such as a code without the keyword, a token wrapped in other words, or one inside a task-notification or cross-session-message envelope, **when** it is submitted, **then** nothing is recorded.
6. **Given** a Bash command that writes to the approval store, **then** it grades 3; **given** a file-tool write to the store, **then** it is denied. Only a user prompt can create an approval.
7. **Given** `bypassPermissions`, **then** `HARNESS_CONFIRMED=1` works as before; **given** a prompting mode, **then** the hook still asks natively and nothing about grading changes.

## Design

**Fix.** Give the auto-mode deny a user-typed approval channel, and make it reusable by the governance binding that follows.

- **The code binds a session to an exact command.** It is the first six base32 characters of `sha256(session_id + "\n" + command)`, over the raw command text. The same command in the same session always gets the same code, and no pending store is needed.
- **The auto-mode deny reason** tells the agent to stop and ask the user to reply with exactly `approve <code>` as the whole message. It replaces the marker instruction in that mode only.
- **A `UserPromptSubmit` module records approvals.** It accepts a prompt only when the stripped prompt, matched whole and case-insensitively, is one or more `approve <code>` tokens separated by whitespace or commas, and writes them to a per-session file under the harness state directory (`approvals/<session_id>.json`), each with its creation time.
- **`grade-bash` consumes an approval** at the point it would deny. It computes the code, looks for an unused approval younger than thirty minutes in this session's file, marks it used and lets the command through with no output.
- **Only a whole-prompt approval counts.** `UserPromptSubmit` also fires on turns the user never typed: background-task notifications, subagent hand-backs and cross-session messages. Those carry agent-controlled text, such as a background command's description echoed in its notification, so a token found anywhere in the prompt would let the agent approve its own command. Any other text in the prompt records nothing.
- **The store is an interlock, not containment.** Any process running as the user can forge any local state, this store and the governance policy files included. The guards stop a cooperating agent's mistakes; an opaque writer such as `python3 -c` that builds the path at run time is out of reach by design and is not graded, and containing a hostile agent is the sandbox's job. `SECURITY.md` states the same.
- **The store is locked.** `record` and `consume` each hold an exclusive `flock` on `<session_id>.lock` beside the file for the whole read-modify-write, and a lock that cannot be taken fails closed.
- **One small module** holds `code_for`, `record` and `consume`, so the governance binding can reuse the channel unchanged.
- **The store is protected.** A Bash write to the approvals directory grades 3. A file-tool write to it is denied, in whichever PreToolUse module already handles file tools once hook manifests land.

**Rejected alternatives:**
- Reading the transcript for the user's "yes": fragile, and text the agent quoted could forge it.
- A random nonce kept in a pending store: that is a second store the agent must not write, and the hash needs none.
- Approving the command for the rest of the session: the issue asks for one use.

**Must not change:** grading, the native `ask` in prompting modes, and the marker in `bypassPermissions`.

**Unverified until checked by hand:** whether a prompt sent through Remote Control reaches `UserPromptSubmit`. The completion notes must record the result.

## Dev notes

- The code is `base32(sha256(session_id + "\n" + raw command))[:6]`, over the text the agent sent, so no pending store exists. [Source: _bmad-output/implementation-artifacts/AH-B105.md#Design]
- Approvals live in `~/.local/state/agent-harness/approvals/<session_id>.json` (0600 file, 0700 directory), each with `created` and `used`; a session id that is not a safe file name records and consumes nothing. Expiry is thirty minutes; the file keeps at most 64 entries.
- The channel exists only on Claude Code in `auto` mode: Codex raises no `UserPromptSubmit`, `bypassPermissions` keeps the marker, prompting modes ask natively. [Source: lib/harness_core/lifecycle.py#EVENTS]
- The recorder is its own hook id, `approvals`, dispatched on `UserPromptSubmit` beside `usage-feed`, per the id conventions. [Source: docs/runtime-controls.md#Hook ids]
- The store guard belongs to `grade-bash`, the consumer: no PreToolUse module handled file tools, so the dispatcher denies a Write, Edit, MultiEdit, NotebookEdit or `apply_patch` into the store while `grade-bash` is on. A Bash command that is not read-only and names the store grades 3 in `grade_text`.

## Review findings

Pull request #886, first review:

1. **CI `test` failed on the full BMad audit:** `sprint-status.yaml` differed from the issue map and story files. Regenerated with `bmad_issue_sync.py sprint-status`; the full `audit` reports 0 findings.
2. **A broken or missing `approvals.py` denied every file-tool write** (CodeRabbit, `lifecycle.py`). The dispatcher now catches the load failure and falls back to `store_write_deny`, which resolves the approvals directory itself and refuses only a write under it; other writes pass. `tests/test_approvals.py::BrokenModule` covers both.
3. **Race in `record` and `consume`** (CodeRabbit, `approvals.py`): two consumers could both use one approval, and a consume could drop a record's new approval. Both now take an exclusive `fcntl.flock` on a sibling lock file around the read-modify-write; pruning no longer drops an approval created a moment after the caller read the clock. `Concurrency` tests: twelve parallel consumers get exactly one True, and interleaved records and consumes lose nothing; both fail without the lock.
4. **Opaque Bash writers** such as `python3 -c` building the store path at run time (CodeRabbit, `grade-bash.py`). Answered rather than graded: the store is an interlock against a cooperating agent's mistakes, not containment against a hostile one, which is the sandbox's job. Stated in `SECURITY.md` and in the design above.
