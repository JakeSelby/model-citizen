## Story

As a developer, I want to test a draft that changes configuration, so that the Studio's verdict covers the modes, stances, switches, identity and personal modules you actually edit.

## Context and value

The Studio refuses to replay a draft whose configuration was edited after it was created (`replay_target_config_unsupported` in the replay target), because the harness arm could not apply it. Once the engine builds the arm from the draft's configuration (#1269), the refusal can go.

## Acceptance criteria

1. Given a configuration-edited draft, testing it from the Studio or `citizen runs draft-test` starts a replay instead of refusing, and the run shows the configuration digest the engine measured.
2. A configuration the engine refuses shows the engine's reason; the Studio adds no check of its own.
3. Draft pre-registration (#1211) and staleness keep using the configuration digest, so editing the configuration after registering marks the registration stale.
4. Tests cover the lifted refusal, the engine's refusal and staleness after a configuration edit.

## Design

### Approach

Once #1269 lands and the Studio branch takes a merge of main that includes it, remove the `replay_target_config_unsupported` refusal, pass the draft's configuration and digest to the engine through the replay target, and show the digest the engine reports.

### Decisions and alternatives

- The engine decides whether a configuration is admissible; the Studio relays its reason and adds no check of its own.

### Do not implement

- Configuration validation beyond what drafts already do.

## Tasks

- [ ] Relay the engine's refusal unchanged (AC: 2)
- [ ] Keep registration staleness on the configuration digest (AC: 3)
- [ ] Tests for each criterion (AC: 4)
