## Story

As a developer, I want every Studio screen to share one frame, one set of design tokens and one component kit, so that the UI is consistent, accessible and quick to extend.

## Context and value

The frame every screen sits in: navigation, a header with the version and health, routing, light and dark themes from the design tokens, and the shared components later stories reuse. Those are the data table, code and diff views, the status badge, the interval display, the empty, loading, error and refused states, toasts, and the command chip that shows and copies an action's `citizen` equivalent.

## Acceptance criteria

1. Every component renders from the design tokens only, with no hard-coded colour, size or spacing.
2. Given keyboard-only use, when a developer moves through the frame, then focus is visible and in order, and every control is reachable.
3. Given any mutating action, then its command chip shows the exact CLI command that does the same thing.
4. The design loop's judge scores the frame at or above its bar, with the scores recorded in the story file.

## Design

### Approach

Extend the existing Mantine frame using the approved Clear palette and Briefing layout. Centralize
shell spacing, typography, surfaces, controls, and semantic status colors as CSS tokens; bridge the
same semantic colors into Mantine button variants. The frame exposes its bundle version, explicit
system/light/dark preference, navigation, workspace, drafts entry point, and a health-unavailable
state until the authoritative health endpoint is delivered.

The reusable kit exports StatusBadge, EvidenceState, DataTable, CodeView, DiffView, IntervalDisplay,
CommandChip, SectionHeading, and ToastProvider. CommandChip copies exactly the string supplied by
the core descriptor; Configure reuses it for its existing CLI equivalents. Tables have captions and
column headings; code and overflowing tables are keyboard focusable. Diff signs and visible state
labels preserve meaning without color. Interval text retains its uncertainty and rejects malformed
numeric inputs.

### Decisions and alternatives

- Keep the approved desktop composition and responsive flow. No invented health measurements or
  generated model assessment fills the still-unavailable endpoints.
- Use a native theme selector so all three choices remain keyboard reachable. Persist the choice
  in Studio's private state through an authenticated, CSRF-protected UI-only route because every
  server restart deliberately uses a new random origin and origin storage cannot survive it.
- Clipboard failure preserves selectable command text and exposes a dismissible error toast.
  Toasts remain until dismissed, capped at three, rather than disappearing before they can be read.
- The diff is a bounded common-prefix/suffix line comparison, avoiding quadratic work for large
  configuration documents. It may show a larger changed block than a minimal edit-distance diff.
- Component visual fixtures live under tests and are rendered into the authenticated shell only
  during capture; no demonstration route or fabricated operational data ships to users.

### Do not implement

Do not implement Hub aggregation, live health, alerts, AI assessments, experiments, provider calls,
spend management, or changes to the draft/core command contracts. Those remain separate stories.

  choice survives a stop and restart with a different origin.
