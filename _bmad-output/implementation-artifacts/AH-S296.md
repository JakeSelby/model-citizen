## Story

As a developer, I want to roll back an applied draft in one step, so that trying a change is never a risk.

## Context and value

Every apply records the state it replaced (the config keys, the root's previous commit and the projections) in the ownership journal. Rollback previews the reverse diff and restores that state through the same governed path, and it is recorded in turn, so a rollback can itself be rolled back.

## Acceptance criteria

1. Given an applied draft, when it is rolled back, then the config, the root and the projections equal their state before the apply, byte for byte.
2. Given a later apply that touched the same keys, then rolling back the earlier one is refused, naming the later apply.
3. Given a rollback, then the activity timeline shows it, linked to the apply it reversed.

## Design

### Approach

A new `lib/harness_core/studio/rollback.py` previews and runs the rollback of one journalled apply;
`citizen draft rollback <apply-id> [--preview]` and two authenticated routes expose it, and each
completed apply or rollback in Activity gains a preview, confirm and roll-back panel.

- **The apply journal is the record.** Every apply already journals, before its first write, the
  configuration bytes it replaced, each key it wrote with its applied value, and each root file's
  prior bytes, mode and applied digest (#978). Rollback reads that intent row; it never needs the
  draft, which may have been discarded since. (AC 1)
- **Restore only what still holds the applied value.** Each key must still equal what the apply
  wrote and each file must still hash to what it wrote; a key or file already back at its prior value
  is skipped. Anything else is a later edit, named, and the rollback is refused with nothing written.
  When no other key moved, the prior configuration bytes are written back whole (byte for byte);
  otherwise only the applied keys are set back to their prior values. Root files return with their
  permission bits, and the directories the apply made are dropped when empty. Then `citizen sync`
  re-projects and the doctor runs. (AC 1)
- **Later changes refuse by name.** The journal is replayed into the applies and rollbacks still in
  effect (a completed rollback cancels the entry it reversed). One after the target that touched any
  of the same keys or files refuses the rollback, naming its id, draft and time; rolling that one
  back first clears the way. A later file written into a personal root the target registered counts
  too, since un-registering the root would orphan it. (AC 2)
- **Recorded in turn.** A rollback journals an intent and a terminal row in the apply's own shape
  (`kind: rollback`, `reverses: <apply-id>`), so `citizen draft recover` restores an interrupted
  rollback and a completed rollback can itself be rolled back. A failed sync undoes the rollback
  through apply's `_restore`. A `studio.rollback` decision-log event names the draft, the actor and
  the apply it reverses; Activity titles it "Apply rolled back" and links it to that apply's entry
  with `/activity?apply=<apply-id>`, which the page highlights, scrolls to and focuses. (AC 3)
- **Same locks, same path.** Rollback takes the sync lock, then the configuration lock, refusing at
  once and naming a holder. `POST /api/configure/apply/rollback/preview` runs the read-only preview;
  `POST /api/configure/apply/rollback` requires the applied draft's name typed back and runs
  `citizen draft rollback --via-studio --json` as a subprocess on the mutation lane.

### Decisions and alternatives

1. **Rollback takes the sync and configuration locks, not the draft's writer lock.** It reads and
   writes nothing in the draft, and a discarded draft must still roll back. Rejected: taking the
   writer lock too, which would refuse every rollback whose draft was discarded.
2. **Refuse rather than merge** when a later change is in the way, per AD-29 and AD-3. Rejected:
   restoring the untouched keys and skipping the conflicted ones, which leaves a half-reversed apply.
3. **A rollback is an apply-shaped journal entry.** Rejected: a separate journal, which would need
   its own recovery path; this way `citizen draft recover` covers both.
4. **An interrupted apply or rollback refuses a rollback** and points at `citizen draft recover`.
   Rejected: recovering it automatically first, as apply does, which would make one confirmation
   cover two different restores.
5. **The confirmation is the applied draft's name typed back,** checked by the CLI, as for recover.
6. **The rollback panel lives on the Activity entry,** per Studio Flow 3 ("opens the applied change
   from Activity"). The Configure apply panel is unchanged.
7. **Applies and rollbacks are addressed by their journal id,** which `citizen draft apply` prints
   and Activity carries. Rejected: a listing command, left for later if it is wanted.

### Do not implement

Partial rollbacks, merging a rollback across a later conflicting change, a listing of applies,
rolling back a failed or abandoned apply, and the product.json feature line.

## Review findings

Round 1, all fixed:

1. An abandoned entry blocked forever. It no longer counts as in effect; only its keys and files that
   still hold its written value (and are not the target's prior value) refuse the rollback.
2. An edit made during the dry-run sync could be overwritten. Rollback now plans again after the
   dry run, so an edit to an applied key is refused by name and any other edit is kept, and
   compares the configuration and files once more just before journalling. The undo after a failed
   sync puts back only what still holds the rollback's writes and otherwise leaves the intent open.
3. An interrupted rollback was recovered and reported as an apply. Recovery now says a rollback was
   undone, with `error_code` `interrupted-rollback`, and records a `studio.rollback` event that
   Activity titles "Rollback undone".
4. Rollback could remove directories the apply never made. Apply and rollback now journal exactly
   the directories they will create (`apply.missing_directories`); restores remove only those.
5. "Already rolled back" now names the change in effect at the end of the rollback chain.
6. Unreadable journal rows and live-file errors are refused by name instead of raising.
7. Activity entries carry `apply_id` and `rollback_target`; the Studio no longer parses ids.
8. A linked entry takes focus; a link to one not loaded says so and offers older activity.
9. Tests added for 1-3, for 4, and for the late-edit refusal.
