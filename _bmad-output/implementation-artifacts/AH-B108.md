# AH-B108 — Governance attributes a piped push after a literal cd to an unknown repository

## Reproduction

With `governance.provider` set to `local` and a level-3 push grant for the repository, pipe to the live PreToolUse dispatcher, in auto mode, a Bash line `cd <literal worktree path> && git push origin HEAD 2>&1 | tail -1`. It is refused, attributed to `repo:unknown/local` at the class default level 2. The same line without `| tail -1` is allowed, and so is `git -C <literal worktree path> push origin HEAD 2>&1 | tail -1`.

## Root cause

`governed_text` in `policy/hooks/grade-bash.py` computed one line-wide flag, `isolated = isolated or _isolating(stripped)` (grade-bash.py:1214 before the fix), and `_isolating` (grade-bash.py:1049) returns true for any `|`, `|&`, `&` or parenthesis anywhere in the line. The `cd` branch of the walk then set the directory to unknown for every `cd` on such a line (`if isolated or head == "popd" ...`, grade-bash.py:1237), so a pipe after the `cd`, not around it, discarded a literal directory. Bash's grammar decides otherwise: a pipeline binds tighter than `&&`, `||` and `;`, so `cd d && git push | tail` runs `cd d` as its own pipeline in the current shell and the push pipeline starts in `d`. `git -C d` passed because it never goes through the `cd` branch.

## Acceptance criteria

1. **Given** `cd <literal> && <governed command> | <anything>`, **when** it is attributed, **then** the governed command resolves to the repository at `<literal>`, the same as without the pipe.
2. **Given** a `cd` inside a pipeline element (`cd <literal> | cat && git push`), a subshell (`(cd <literal>) && git push`) or a background job, **then** the later governed command's directory stays the one before that `cd`, or unknown where the walk cannot tell. It never becomes `<literal>`.
3. **Given** the existing governance-binding and operator-spacing tests, **then** they all pass unchanged.

## Design

Follow Bash's precedence in the directory walk: a pipeline binds tighter than `&&`, `||` and `;`, so every element of a pipeline starts in the directory in effect when the pipeline begins. Only a `cd` executed inside a pipeline element, a subshell or a background job is confined to it. Fix the walk that attributes segments, not the tokenizer.

Rejected: treating any line that contains a pipe as unknown, which is today's behaviour and refuses a common, safe spelling of a granted push.

Must not change: the unknown-directory rule for `cd -`, variables, `pushd`/`popd`, `env -C` and `--git-dir`, or any grade.

## Regression test

`tests/test_governance_pipeline_cd.py`, `test_regression_a_piped_push_after_a_literal_cd_resolves_to_that_repository`: `cd <repo> && git push origin HEAD 2>&1 | tail -1`, with `;`, newline and `|&` spellings and a quoted `|` in a commit message, resolves to `<repo>` and passes in auto mode under a level-3 pair. Against the previous walk it and four sibling tests (every pipeline element, a literal `pushd`, a substitution in the pipeline, a quoted `|`) fail; the confinement and unknown-directory tests in the same file pass before and after, and `tests/test_governance_binding.py` and `tests/test_readonly_operator_spacing.py` pass unchanged.

## Dev notes

- `_confined(text)` walks the same tokens and the same segment rules as `segments`, returning per segment `True` (confined), `False` (carries over) or `None` (use the line-wide `_isolating` rule). A list operator (`&&`, `||`, `;`, `;;`, `&`) at paren and compound depth 0 ends a pipeline, and `|` or `|&` there marks it confined. `;`, `;;`, `&` and newline also end the AND-OR list; `&` backgrounds the whole list, so every segment of it is confined (`cd d && true & git push` pushes from the starting directory). A governed command inside a backgrounded list after its own `cd` is therefore unknown, which fails closed. The tokenizer is untouched, as the design requires.
- A confined `cd` leaves the directory unknown rather than unchanged, because zsh runs a pipeline's last element in the current shell, so `x | cd d` does move it there.
- A `cd` inside `{ }`, `if`, `while`, `until`, `for`, `select` or `case` keeps the old line-wide rule, since the construct may itself be a pipeline element. An unbalanced structure, such as a `case` pattern's lone `)`, or a segment count that disagrees with `segments`, falls back to the line-wide rule for the whole line.
- The tokenizer reads a quoted `|` as a word spelled like the operator, so `_unquoted_structure` masks quoted and escaped operator characters before `_confined` tokenizes. Word boundaries do not move.
- Substitution text is still governed with `isolated=True`, so every `cd` inside one stays confined. No grade changes.

## Review findings

- CodeRabbit, Major, `policy/hooks/grade-bash.py` `_confined`: `&` backgrounds the whole AND-OR list, not only its last pipeline, so `cd X && true & git push` was judged against `repo:X` while the push runs in the starting directory. Fixed: `_confined` tracks each pipeline's AND-OR list and confines every segment of a list that `&` ends; `;` and newline end a list without confining it. Covered by `test_regression_a_background_job_confines_its_whole_and_or_list` and `test_a_list_ended_by_a_separator_is_not_confined`.
