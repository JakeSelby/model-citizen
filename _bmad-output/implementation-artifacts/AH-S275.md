## Story

As the repository owner, I want the burndown bot held to a hard budget with a pause switch and a clean
stop, so that its runs never lock me out of my own subscription for the rest of a week.

## Context and value

On the subscription token the bot draws on the same five-hour and weekly limits as the owner's own
sessions, so an unbounded bot can lock the owner out for days. claude-code-action caps turns with
`claude_args: --max-turns`, and "Claude will stop execution gracefully" at the limit; what it does on a
usage limit is not documented [Source: https://github.com/anthropics/claude-code-action]. The bot
therefore treats any other unexpected stop as a limit and defers the bug rather than retrying at once.

Every lane (#948, #950, #951) runs inside this budget. The turn cap is fixed in the pre-registration
(#947), so the same value applies in every arm. Traces to FR-71
([#946](https://github.com/JakeSelby/model-citizen/issues/946)).

## Acceptance criteria

1. **Given** the pause switch set, **then** no workflow starts an agent.
2. **Given** the daily or weekly attempt cap reached, **then** the run exits before starting an agent.
3. **Given** any agent run, **then** it passes the same `--max-turns` value, in every arm.
4. **Given** a scheduled run, **then** it starts only inside an off-hours window in America/New_York,
   and only one runs at a time.
5. **Given** an agent result that is neither success nor the turn cap, **then** the issue gets
   `bot::deferred`, the run exits 0 and the next scheduled run retries it; **given** three deferrals in a
   row, **then** attempts stop until the owner clears them.
6. **Given** `docs/burndown-bot.md`, **then** it says when to pause the bot, including benchmark and
   qualification rounds.

## Design

### Approach

- A budget gate is the first step of every bot workflow, before any agent step. It reads repository
  variables: the pause switch, the daily and weekly attempt caps, and the turn cap. It counts attempts
  from the study record's assignment comments (#947), so the count survives a crashed run.
- Defaults: two attempts a night and eight a week; the turn cap comes from the pre-registration. All
  three are variables, tunable without a code change.
- The schedule's cron sits inside the off-hours window, and the gate re-checks the window in
  America/New_York so a daylight-saving shift cannot move a run into working hours. A workflow
  `concurrency` group allows one run at a time.
- The agent step passes `--max-turns` from the variable in every arm. Its result is classified as
  success, turn cap, or other; other means `bot::deferred` and a zero exit.
- A consecutive-deferral counter in the gate stops attempts after three until the owner removes the
  stop.

### Decisions and alternatives

- **Treat an unknown stop as a limit.** Usage-limit behaviour is undocumented, so the conservative
  reading avoids hammering a limit. Rejected: parsing error text, which is unstable across versions.
- **Count from the recorded assignments,** not from a counter variable: the Actions token cannot write
  repository variables, and a crashed run would otherwise go uncounted.
- **Exit 0 on a deferral,** so a limit does not turn the workflow red and page the owner.

### Do not implement

- Reading the owner's usage bar or any live limit API; the caps are the protection.
- The lanes themselves (#948, #950) or the vuln scan (#951), beyond calling the gate.

### Bound decisions and requirements

- FR-71 Unattended bug-fix lanes: "with the pause switch set or a cap reached no agent starts, and an
  unexpected stop defers the bug to the next run."

- AD-14 For cost, hooks only route and refuse frontier: the budget lives in the workflow, not in a hook.
- The autonomy stance: unattended loops are fenced.
