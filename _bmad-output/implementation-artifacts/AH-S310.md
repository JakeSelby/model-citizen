## Story

As a developer, I want every rule's measurement status, adherence and cost in one table, so that I can prune dead rules and fix weak ones.

## Context and value

One table of every rule: measured, dark or unmeasured with the reason (#647), how often it is followed and its trend, its detector's precision, its context cost (#514), and when it last fired. A rule that costs tokens and never fires can be switched off in a new draft from its row, and the developer decides whether to apply it; nothing is switched off for them.

## Acceptance criteria

1. Given `citizen usage --rules`, then the table shows the same status and reason for every rule.
2. Given a dark rule, then "Try without it" opens a draft with the rule switched off and its test ready to run.
3. Given a detector under the precision floor, then its adherence figure is marked unreliable.

## Design

### Approach

A read-only report, `lib/harness_core/studio/rule_health.py`, joins what five engines already say
about each loaded rule, and the Studio shows it at `/reports/rules`, linked from the Library.
Nothing in it measures anything:

- status and reason: `classified_rules` in `bin/harness`, the function `citizen usage --rules`
  prints its coverage block from, called in process through the Studio's existing loader;
- detector hits: `citizen usage --rules --json --days N` for 7, 30 and 90 days, per detector,
  labelled exploratory (host sessions, evidence standard item 11); last fired is the narrowest of
  those windows in which a detector fired, and the 7- and 30-day figures sit side by side as the trend;
- precision: `scripts/detector_corpus.py --json`; a rule whose detector is under its floor, or has
  no measured precision, has its hit figures marked unreliable with the reason;
- advice followed (#798): `citizen usage --by adherence --json`, requested only when a kind in
  `adherence.KINDS` names a rule module; today none does, so every rule reads not measured;
- context cost and effect (#514): `citizen scorecard --json`, its soft token estimate and its
  ablation effect, `unmeasured` until an ablation run removed the module.

The engine commands run concurrently; one that fails leaves its column "not measured" with the
reason and marks the report partial. `POST /api/rules/health` serves the document and
`POST /api/rules/try-without` runs `citizen draft create` for a new `without-<rule>-<id>` draft and
saves `rules.<rule>: off` through the draft selection save, returning both CLI steps. The page
then shows that draft's draft test (#991), ready to run.

### Decisions and alternatives

1. **Status in process, not parsed.** Taken: call `classified_rules`, the same function behind
   `usage --rules`, and prove equality against the CLI's printed block in a test. Rejected: parsing
   the coverage lines in `usage --rules --json`, which are display text.
2. **Hits are shown as fired, never as followed.** A detector fires on what its rule names, often
   the breach, so inverting a share into adherence would invent a reading no engine makes. The
   adherence figure proper is #798's, which today covers no rule.
3. **Trend and last fired from the engine's own windows.** Taken: three `usage --rules` windows.
   Rejected: reading ledger timestamps in the Studio, which would re-implement the measured-session
   filter `rule_report` owns.
4. **AC3's "adherence figure" is the detector hit figure.** No engine measures adherence for any
   rule (#798 covers only the fresh-session nudge), so the figure AC3 marks unreliable is the hit
   figure, the only per-rule rate there is. The floor verdict is the engine's own `below_floor`
   list (precision or recall under the floor), never a comparison made in the Studio; a corpus that
   cannot be read reads "precision unavailable (read failed)", reliability unknown.
5. **Unscored precision is unreliable too.** Default taken: a detector with no labelled score marks
   its rule's hits unreliable, with a distinct reason, as well as one under the floor (AC3 names only
   the floor).
6. **"Try without it" for every switched-on rule.** Default taken: offered on any rule module
   switched on in the selection, dark or not; a stance is a variant, not a switch, and is explained
   instead. The page shows the draft's draft test (#991) as "its test", rather than the rule's unit
   eval (#988), because the draft against its base is exactly with the rule against without it.
7. **No new CLI command.** The read route names `citizen usage --rules --json`, the status's source;
   try-without names `citizen draft create` and returns both CLI steps.
8. **A kept draft is always named.** Once `citizen draft create` succeeds, a failed read or switch
   save answers 200 with `status` `switch-failed` or `draft-unreadable`, the draft's name and how to
   discard it, rather than an error that hides it. The CLI steps carry the real revision and key.
9. **Working directory.** Statuses and hit windows read from the Studio's own directory, as
   `usage --rules` run there would; the page names it. Picking another workspace is not offered.
10. **Placement.** A dedicated `/reports/rules` route, linked from the Library, leaving the Reports
   placeholder for the stories that own the Reports page.

### Do not implement

- Any new measurement, ledger read or estimator; wiring a stored ablation run into the effect column.
- Applying the draft, or discarding it when its switch save fails (it is kept and named).
- A product.json line, and the Reports landing page itself.

## Review findings

Round 1 (quality and scope reviews), all fixed in one commit:

- Blocking: the corpus script's exit 1 (a detector failing, unscored or stale) was read as a failed
  read; exit 1 with JSON is now a result, and only a crash or non-JSON output fails.
- A failed corpus read said "has no measured precision"; it now says "precision unavailable (read failed)".
- "Not in 90 days" was claimed when the 90-day window failed; each window shows its own state and
  "not in N days" names the widest window read.
- A switch-save failure or an unreadable draft after create hid the kept draft; both now name it.
- A shadowed rule collided with its owner's row key and borrowed its cost and switch; rows are keyed
  by module and root, and a shadowed row borrows nothing.
- The working directory is named on the page.
- The floor verdict is the engine's `below_floor` list, which covers recall too.
- Tests added for each path above, the server's partial-create cleanup and a corpus exit 1.
- The button's accessible name contains its visible text; the outcome takes focus in a live region.
- Nits: detector ids in each cell, "at or above floor", the real revision and key in the CLI step,
  and a failed adherence read named in the sources.
- Scope: AC3's wording and AC2's "its test" are recorded in decisions 4 and 6; the frontend test
  now asserts the draft test renders and that a measured rule is offered.

Round 2, all fixed in one commit:

- The floor field is `below_floor`, which `ruleprobe.validity.scores_as_dict` emits; a test reads
  the real script's output at an unreachable floor, where it exits 1.
- Exit 1 is a result only with the script's own document; an uncaught exception (also exit 1) is a
  failed read carrying its last error line.
- Last fired says which of fired, not fired in a fully reported window, a detector missing from
  every report, no measured sessions, or every window unreadable.
- Shadowing is the engine's verdict (`rule_coverage.SHADOWED`), tested through the real `classify`;
  rows are keyed by file path and joined to the scorecard by the selection module (`rules/<stem>`).
- Only a one-line status is live; the tried draft and its test are not announced.
- CLI steps substitute whole placeholder words; floor and scores print to two places, and a
  missing floor reads "the engine's floor".
