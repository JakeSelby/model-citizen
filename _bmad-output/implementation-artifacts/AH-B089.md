# AH-B089 — The confinement refusal names a harness command that no documented install puts on PATH

## Reproduction

1. In a session running under the harness with the `tiered` delegation stance, spawn `reviewer` or `gatherer` natively.
2. The spawn guard refuses with `Use harness role run <role> --runtime <runtime> ...`.
3. In a login shell, `command -v harness` finds nothing: neither `README.md` nor `docs/getting-started.md` puts the CLI on `PATH`, so the command the refusal names does not run outside the checkout.

## Root cause

`role_instruction` in `lib/harness_core/lifecycle.py` built the refusal around the bare word `harness`, assuming an install step that puts the CLI on `PATH`. No documented install has one; the CLI only exists as `bin/harness` inside the checkout the hooks run from.

## Acceptance criteria

1. **Given** a constrained role spawned natively on either runtime, **when** the guard refuses, **then** the refusal names the CLI by the absolute path of the checkout's `bin/harness`.
2. **Given** that refusal, **when** its named command is run with a `PATH` holding no `harness`, **then** it runs and exits 0.
3. **Given** a checkout path containing a space, **when** the refusal is built, **then** the path is shell-quoted so the command still splits to one argument.
4. **Given** the change, **then** the confinement sentence the stance and role descriptions share is unchanged.

## Design

A new `harness_command()` returns `shlex.quote(ROOT / "bin" / "harness")`, and `role_instruction` names it in place of the bare `harness`. `ROOT` resolves through the `~/.claude/hooks` symlink to the checkout that answered, so the path is the one that exists on this install.

Rejected: an install step that links `harness` onto `PATH` plus a `doctor` check. It edits the owner's shell environment, which the run's default forbids, and still leaves a client whose `PATH` differs from the login shell's with a command that does not resolve.

Must not change: `CONFINEMENT_SENTENCE`, which the `delegation` stance and the shared role descriptions carry word for word and which still names `harness role run <role>` as the concept.

## Regression test

`tests/test_role_refusal_command_resolves.py` takes the command out of the refusal text for `gatherer` and `reviewer` on both runtimes, asserts it is the checkout's executable `bin/harness` by absolute path, runs `role --help` through it with a `PATH` holding only the interpreter, and checks a spaced checkout path is quoted. Before the fix the refusal names bare `harness`, which is not absolute and does not resolve on that `PATH`.
