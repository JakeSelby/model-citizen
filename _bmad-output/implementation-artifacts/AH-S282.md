## Story

As a developer, I want the Studio to answer only the browser I launched it from, so that no web page or local process can use it to change my harness or spend my usage.

## Context and value

The Studio can write live configuration and launch runs that spend usage and execute commands, so a web page, a local process or a DNS-rebinding attack that reaches its port must get nothing. The launch URL carries a per-launch token, exchanged once for an HttpOnly, SameSite=Strict cookie, and the state file that holds the token is mode 0600.

## Acceptance criteria

1. Given a request without the cookie or the token, when it reaches any `/api` route, then it gets 401, tested anonymously with redirects not followed.
2. Given a Host header other than the bound loopback address and port, then the server answers 403.
3. Given a mutating request whose Origin is not the Studio's own, or that lacks the CSRF token, then it gets 403 and nothing is written.
4. Every response carries a content security policy with no inline script, `frame-ancestors 'none'`, `nosniff` and `no-referrer`, and no response carries a CORS header.
5. Given a config holding a secret or a keychain reference, then no API response carries its value, and every file API refuses a path outside the Studio's known roots.

## Design

### Approach

Put the browser, process-control and filesystem boundaries in `harness_core.studio`, leaving the
CLI as a launcher. Each server instance binds 127.0.0.1 but advertises a random
`<nonce>.localhost:<port>` origin. The CLI obtains a one-shot bootstrap secret over the separate
Bearer-authenticated control channel, writes it only into a mode-0600 local form, and opens that
file; the POST consumes the secret, deletes the form and creates a host-only HttpOnly Strict cookie.

All later application requests require the exact Host and session. Non-safe API requests additionally
require the exact Origin and session-bound CSRF token. One response path supplies the complete CSP and
hardening headers without CORS. Shared serialization redacts secret values while retaining explicitly
typed environment, keychain, profile and secret-store reference names, and descriptor-retained roots
confine future file routes to checkout, config, state, draft and registered primitive roots.

### Decisions and alternatives

- Use a local POST form rather than putting the bootstrap secret in the URL, browser history, logs or
  process arguments. The form has a hash-pinned auto-submit script and is deleted after exchange.
- Keep the lifecycle control Bearer credential, one-shot bootstrap secrets and browser cookies separate.
  Reusing one credential would let a browser session stop or re-key the process.
- Authenticate application HTML and static content as well as `/api`; publishing the shell anonymously
  would disclose state and create a second, weaker entry path.
- Validate Host before route disclosure, then session before API route lookup. Anonymous callers learn
  only `unauthorized`, while DNS-rebinding hosts receive a generic refusal.
- Retain canonical root descriptors and traverse relative descriptors with `O_NOFOLLOW` plus post-open
  inode checks. Prefix checks and pathname re-resolution remain vulnerable to links and rename races.
- Treat secret reference provider/name as display metadata, but replace every resolved or literal secret
  with configured/unconfigured state. Unknown reference forms are redacted rather than guessed safe.

### Do not implement

- Front-end source, assets, session-expiry screens and design-system components (AH-S283/AH-S284).
- Domain configuration/file routes, drafts, run APIs and SSE. This story supplies the boundary those
  registered routes must use; it does not introduce a browser-only domain action.
- Protection from malicious same-UID code, HTTPS or remote/phone access, per AD-27's local boundary.

## Review findings

- Quality review: a Strict cookie set on the cross-site local-file POST could be unavailable on an
  immediate redirect. Bootstrap now returns a CSP-safe same-origin success document whose meta refresh
  performs the navigation after that document commits; an actual headless Chrome flow reached the shell.
- Quality review: camelCase secret keys and malformed nested references could evade or leak through the
  first redactor. Key normalization now covers camelCase/compact forms and only a typed, validated exact
  reference shape may retain provider/name display metadata; adversarial values fail closed.
- Quality review: static serving used pathname resolution after startup. The server now retains a
  descriptor for the approved static root and uses no-follow reads with post-open identity verification;
  symlink and re-resolution-race regressions prove refusal.
