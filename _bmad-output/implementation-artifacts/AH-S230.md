## Story

As a harness maintainer, I want to replay two arms that differ in one policy and compare their cost
per passed task, decision calls included, so that a routing or decision-layer change is judged on what
the whole task costs rather than on agreement with today's rule.

## Context and value

The four-arm set (#559, #560) reports cost per passed task for four fixed arms. #145, the band
recommendation, can only report agreement with the current routing heuristic, which shows imitation
rather than improvement, and it has no promotion criterion. A one-policy pair, default routing against
the recommendation, is the comparison a criterion can rest on. A selector's own calls count in the arm
that makes them, since a cheaper worker bought with an expensive decision saves nothing. keel 0.2.0
([codejunkie99/keel](https://github.com/codejunkie99/keel)) names the same comparison, selector time, worker time, retries and review effort, but ships
no implementation of it.

## Acceptance criteria

1. **Given** two profiles that differ in one named policy, **when** the pair is replayed, **then** the
   parity check passes only when nothing else differs.
2. **Given** a finished pair, **when** it is summarised, **then** each arm reports passes, cost per
   passed task, wall time and re-spawns at a higher band.
3. **Given** decision-provider calls during an arm, **when** the arm is costed, **then** their ledger cost
   and latency count in that arm, and an unpriced call is named, never counted as zero.
4. **Given** a fake launcher, **when** the unit tests run, **then** they cover the parity refusal, the
   re-spawn count and the decision-call roll-up.
5. (Added 2026-09-29 from the approved plan, decision 2.) **Given** a pair, **when** it is replayed,
   **then** the schedule holds bare, reference and treatment, with the lead arm rotating across all three.
6. (Added 2026-09-29 from the approved plan, decision 5.) **Given** a finished pair, **then** the
   treatment-over-reference Cost-of-Pass ratio and the pass-rate difference carry the paired,
   task-clustered 95% intervals of #795, and each harness arm's ratio to bare is reported beside them. No
   SM-2 verdict is printed, since SM-2's decision rule is defined for harness against bare only.

AC3 is read as: decision calls' ledger cost adds to the arm's cost, and their latency is reported as the
share of the arm's wall time it already contains, so latency is never counted twice. "Higher band" in AC2
is read as a stronger model class.

## Design

### Approach

Built on #559's container arms (AH-S202), which deferred pair parity, so this story builds parity for two
harness arms itself. A committed ablation manifest (`benchmarks/ablations/<name>.json`, schema 1, AD-12)
names one tag, one factor and a reference and a treatment value. `replay --pair` builds the tag's one
harness image and runs it twice, the factor set by value, beside the bare arm:

- **Before launch,** `replay_pair.parity` compares the two harness arms' launch specs (image id,
  declaration and manifest digests, commit, model, run cap, command line, environment, network, proxy,
  credential name, protocol stamp, task-file and price-table digests) and refuses any difference but the
  factor; `effective_difference` refuses a pair whose two selections resolve to one profile fingerprint.
- **Schedule:** `schedule(tasks, reps, arms)` rotates the lead arm across bare, reference and treatment;
  for two arms it is the old alternation.
- **Stream:** `parse_result` adds `session_ids`, `respawns_up` and `spawns_unranked`. A re-spawn up is a
  later spawn whose brief is `lifecycle.same_work` with an earlier one's and whose thread model ranks in
  a stronger class of `adapters/claude-code/bindings.json`; an unmatched model is unranked, never ranked.
- **Ledger:** each harness arm's container runs without `--rm`; its usage ledger is copied out with
  `docker cp`, then the container is removed (stopped first on a timeout). Only decision rows are kept,
  in `decisions/`. `decision_ledger` is `read`, `absent` (bare) or `unknown: <reason>`.
- **Summary:** `summarise` detects a pair by its three arm names and reports, per arm, passes with a
  Wilson interval, pooled Cost-of-Pass for workers alone and with priced decision calls, wall time,
  re-spawns, and the decision roll-up (calls, priced cost, unpriced and unmatched rows named, latency as
  a share of wall time). `replay_stats` takes an `arms` pair, so the intervals cover treatment over
  reference and each harness arm over bare. Post-run parity compares each trial's loaded surface (#482)
  and exits 1 naming the trial.

Rows are keyed by arm name and carry `ablation` and `selection`, so #514's declared-arms runner can
generalise the pair to N arms without changing the row schema.

### Decisions and alternatives

- Score on cost per passed task, the four-arm set's own unit, so pairs and arms compare on one scale.
- Rejected as a criterion basis: agreement with the current heuristic (AH-S057 AC5 before its
  2026-09-23 amendment), which can only show imitation.
- Rejected: pricing an unpriced decision call at zero. The ledger names unpriced rows rather than
  zeroing them, and the pair follows that rule.
- Decisions taken from the approved plan (2026-09-29), each the recommended option:
  1. The one policy is one session-scoped selection variable on one shared image; a build-time
     selection (two images) is left to #797.
  2. Every pair runs the bare arm beside it, as point 5 of the evidence standard requires.
  3. Ledger rows leave the container by `docker cp` after exit; no writable host mount is added.
  4. No egress to a remote decision provider now: such a call cannot complete, and is unpriced.
  5. #795's paired intervals ship with the pair now.
- #754 lands its pair before #514's general declared-arms runner; rows carry `ablation` and `selection`
  rather than one-factor fields, so #797's second factor fits the same schema.

### Do not implement

- No new arms in the four-arm set, and no change to its threshold.
- No promotion of #145: the point stays in `shadow`, and this story only supplies the measurement.
- No live runs in the unit tests.

### Loaded-surface record (#482)

#482 is merged: each row carries `init_skills`, `init_agents`, `init_slash_commands`, `init_tools`,
`init_mcp_servers`, `init_memory_paths`, an `init_<name>_sha256` for each, `init_surface_source` and
`observed_effort` (`cost_bench.surface_of`). It refuses before launch on arm-record drift
(`replay_arms.admit`, `admit_pair`) and stops a set whose surface moves within one arm. Post-run pair
parity compares exactly those fields between reference and treatment; no field was invented.

### Testing

Unit tests with a fake launcher and fake ledger rows: a pair that differs in two keys is refused, a
re-spawn at a higher band is counted, and decision rows join by session id with an unpriced row named.
