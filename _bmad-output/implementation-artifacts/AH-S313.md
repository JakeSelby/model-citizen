## Story

As a new user, I want a guided first run from install to an applied setup, so that I reach a tuned harness in minutes.

## Context and value

A developer who has just installed Model Citizen runs `citizen studio` and is walked through setup (FR-69): the runtimes found, identity, a stance pick for each dimension with its preview, a free check run, and an apply, ending on the overview. The installer's last line and `citizen init` point at the Studio.

## Acceptance criteria

1. Given a fresh install, when the Studio opens, then setup starts, and it ends with an applied draft and green doctor checks.
2. Given setup abandoned halfway, then nothing live changed, and the draft is kept to resume.
3. Given setup done, then the same choices are reproducible from the CLI commands it shows.

## Design

### Approach

The first run composes the flows already on the branch and keeps no state of its own. A new core
module, `lib/harness_core/studio/first_run.py`, derives the run's state from two authorities: the
draft it creates (named `first-run` by default) and the apply journal. `not-started` means no such
draft, `in-progress` a kept draft with no completed apply, `interrupted` an open apply of it, and
`complete` a completed apply, whose recorded doctor result and `config` commands it reports. It
also reports `fresh` (no apply ever completed and no other draft exists) and the commands that
reproduce the choices: the draft's configuration keys against its base, as the same
`citizen config set|unset` lines apply runs, then `citizen sync` and `citizen doctor`.

Two routes expose it: `POST /api/first-run` (`citizen draft first-run NAME --json`) and
`POST /api/first-run/start`, which runs `citizen draft create NAME --json` itself, as Studio apply
runs `citizen draft apply`, and returns the existing draft when one is kept. The browser guide at
`/setup` walks health, draft, identity, preferences, a free check, review and apply, and done. Each
step reuses an existing component or route: the overview's doctor checks, the settings
preview/save routes for identity, `DraftSelectionEditor` for mode, stances and switches with their
previews, the free `lint` suite through `/api/runs/start`, and `DraftApply` for review, apply and
recovery. The Hub opens the guide once per page load on a fresh, unstarted install and otherwise
shows a resume banner until the run is complete. `citizen init` and the installer's last line
point at `citizen studio`.

### Decisions and alternatives

1. **State is derived, not recorded.** Rejected: a first-run progress file in the Studio state
   directory. It would be a second authority that can disagree with the draft and the journal,
   and it would need its own CLI parity. Deriving it makes AC2 hold by construction: only
   governed apply writes live configuration (AD-29).
2. **The draft name is a request field with a `first-run` default.** Rejected: a hard-coded
   name. Draft branches live in the shared repository, so tests and parallel sessions need
   distinct names, and a user who already has a `first-run` draft can still be served.
3. **Start creates the draft through the CLI.** Rejected: calling `drafts.create` in the server.
   The CLI owns the managed-worktree primitive, so the Studio runs it as it runs apply (AD-25).
4. **The free check is the installed `lint` suite.** The Studio run route accepts only the
   installed target, so the draft's own checks come from the apply review. A draft-targeted free
   run is left to the run stories.
5. **The guide opens itself only for a fresh install, once per page load.** Rejected: always
   redirecting until complete, which would trap a user who chose to leave. A kept draft shows a
   Hub banner instead.

### Do not implement

- No new apply, rollback or comparison behaviour; `apply.py` is read, not changed.
- No module authoring, comparison report or paid run inside the guide.
- No persisted "dismissed" flag and no `product.json` copy.

### Testing

- `tests/test_studio_first_run.py`: the state machine on synthetic journals; with a real draft in
  an isolated home, AC2 (choices saved, live configuration byte-identical, no journal, draft kept),
  AC3 (the shown commands run in a second home reproduce the draft's values), AC1 (apply finishes
  the run, its doctor result is reported); the CLI's invalid-name error; route parity; the
  `init --yes` and installer closing lines.
- `tests/test_studio_first_run_routes.py`: 401, 403 (missing Origin, missing CSRF, foreign
  Origin) and 400 for both routes; start creates the draft once and a second start resumes it.
- `studio/tests/first-run.test.ts`: guide opening, resume step, reachability, Hub copy, progress,
  the CLI sequence, the done summary, the route title, and the API calls with CSRF.
