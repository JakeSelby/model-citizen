## Story

As a developer, I want to add my own modules from templates or fork a core one, so that I extend the harness without a local edit that an update would clobber.

## Context and value

A developer adds a rule, skill, stance variant or mode to their own primitive root from a template, with its manifest fields filled and checked (AD-22). Or they fork a core module: the Studio copies it into their root with its provenance (the core module and the version it came from) and switches the core one off in the same draft, and after a later update it shows when the original changed.

## Acceptance criteria

1. Given no personal root, when a developer adds a module, then the Studio offers to create one and registers it in `primitive_roots` in the draft.
2. Given a new module, then its manifest passes the manifest checks before save.
3. Given a forked core rule, then the draft switches the core rule off, and the library shows the fork with its source and version.
4. Given an update that changes a forked module's original, then the fork's page shows the upstream diff.

## Design

### Approach

A new `lib/harness_core/studio/module_authoring.py` plans and checkpoints one new or forked module
through the existing draft transaction (`drafts.checkpoint` with files, configuration, a check
command, request identity and a canonical response), under the draft writer lock that
`module_editing.save` already takes. Nothing outside the draft checkout is written.

- **Personal root in a draft.** A draft writes only inside its checkout, so its personal root is the
  first registered root inside the draft (the draft-owned roots `module_editing` already edits).
  With none, read and plan say so and offer `personal-primitives`; a request carrying
  `create_root` registers `<checkout>/personal-primitives` in the draft's `primitive_roots`, which
  `_mapped_config` maps into the draft. (AC 1)
- **Templates.** A rule, skill, stance variant or mode, written from the name and a one-line
  description. Rules and skills get a manifest in the root's `manifests.json` whose claim is the
  description; stance variants and modes carry none, as AD-22 and `docs/primitive-authoring.md` say.
- **Manifest checks before save.** Plan runs the resolver's own `validate_manifest`, then strict
  `posture.selection` (missing-manifest, dependency, conflict and slot refusals) plus every mode's
  `validate_mode`, on a copy of the personal root carrying the planned files and the draft's
  planned configuration. Save plans again under the lock and refuses on any finding; the
  checkpoint's check command then runs `citizen lint` and the same strict resolution on the
  written draft, so the checkpoint cannot exist unless both pass. (AC 2)
- **Forks.** A core rule or skill is copied, every regular file of it, under a new name
  (`<name>-fork` by default), with the shipped manifest copied under that name. The draft switches
  the core unit off (`rules.<name>: off`) in the same checkpoint, and `forks.json` in the root
  records the source, the checkout's `VERSION`, the draft's base revision and a sha256 per file. (AC 3)
- **Upstream diff.** `module_library.inventory` reads `forks.json` for every non-core root and
  attaches `fork` to each forked module: source, version, revision, and a unified diff from the
  original as forked (read from git at the base revision) to the core module now, with `changed`,
  `missing` and `original_available`. The Library
  page renders it on the fork's row and detail; a draft's own library is served with draft paths
  rewritten to `<draft>/`. (AC 3, 4)
- **Surfaces.** `citizen draft module templates|plan|add|library`, and four authenticated POST routes
  under `/api/configure/authoring/` naming those commands. Configure gains an "Add or fork a module"
  panel with the root offer, an explicit Check, Save to draft, the planned files and configuration,
  and the draft's own modules through the Library component.

### Decisions and alternatives

1. **The draft's personal root lives in the draft checkout.** AD-29 lets only governed apply write
   primitive roots, and `module_editing` edits only draft-owned roots. Rejected: writing into an
   external root such as `~/.config/agent-harness/primitives` from a draft. Moving the root out
   of the checkout, or fast-forwarding a developer's own root repository, belongs to apply (#978).
2. **A fork takes a new name.** Switches are keyed by unit name across every root
   (`posture._units`), and one unit's manifest in two files is a refusal, so a same-named fork would
   be switched off with the core module. Rejected: same-name forks with shadowing.
3. **Forks cover rules and skills.** Stance variants are chosen, not switched, and a duplicate
   dimension/variant is an error, so there is no core variant to switch off; a new variant comes
   from the stance template. Roles, workflows, hooks and modes are out of AC 3's scope.
4. **A digest per file, not the original's text.** The original is read from git at the recorded base
   revision and trusted only when its digest matches; storing text hit the editor's size cap.
5. **Checks reuse the resolver.** The candidate check and the save's check command call the draft's
   own `posture.py`, loaded fresh, never a Studio copy of its rules (AD-2, AD-22).

### Do not implement

Apply, rollback, contribution branches, editing `manifests.json` or `forks.json` by hand in the
Studio, rebasing a fork onto a changed original, forking stance variants, roles, workflows, hooks
or modes, and the product.json feature line (#1062).

## Review findings

Round 1 quality review of 46cb8bec. Each fix carries a test that fails on 46cb8bec.

1. **Path traversal through a fork source (blocking).** Fixed. `_normalized` and `module_library._fork`
   accept only a forkable kind and an identifier name, and file keys that are safe relative paths;
   `module_files` also requires the resolved path to stay under `primitives`.
2. **forks.json held full originals under the 512 KiB editor cap.** Fixed by storing a sha256 per
   file with the version and the draft's base revision. The original is read from git at that
   revision and used only when its digest matches; otherwise the Library says the original is not
   in the checkout's history and shows no diff.
3. **Binary skill assets.** Fixed. Forks copy bytes, the upstream check compares digests, and the
   diff prints `Binary file ... differs`. Only forkable modules are listed.
4. **Route tests checked only the method.** Fixed: every route is exercised over HTTP for 401, 403
   with no CSRF, no Origin and a foreign Origin, and 400 on bad types, all asserted on the status.
   This is a test gap, so the new test passes on 46cb8bec as well.
5. **No skill fork test.** Fixed: a draft forks `workflow-status` and checks the frontmatter rename,
   the byte-identical multi-file copy and a two-file upstream diff.
6. **The AC1 render never ran effects.** Fixed: `RootOffer` is extracted and rendered from a read,
   and the offer gating is asserted through `needsRoot` and `canPreview`.
7. **Live region mounted already filled.** Fixed: `AuthoringStatus` is always mounted.
8. **Live region wrapped the file text.** Fixed: it holds only the message, verdict and findings;
   the planned files render outside it.
9. **forks.json duplicated originals in the preview.** Fixed by 2: the entry is digests only, under
   1 KiB for a rule.
10. **Unescaped description in skill frontmatter.** Fixed by validation: `---` and non-printable
    characters are refused.
