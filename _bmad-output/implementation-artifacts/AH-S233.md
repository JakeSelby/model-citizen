## Story

As a harness maintainer, I want every new ledger row to carry the fingerprint of the profile that produced it, so that any row traces to its exact profile and two profiles can be told apart by their rows alone.

## Context and value

#482 records the loaded surface on replay rows. AD-23 goes further: every new ledger row, from live sessions as well as replays, carries the profile fingerprint, a digest of the selected modules, stances, configuration and harness version (AD-22). With it, any row traces to the exact profile that produced it, and two profiles can be told apart by their rows alone.

Depends on #788 and #644. Extends #482. Traces to AD-22, AD-23 and FR-23.

## Acceptance criteria

1. Given any ledger writer, whether a session hook, a role worker or the replay, when it writes a row, then the row carries the fingerprint of the active profile.
2. Given two profiles that differ in one module, stance or setting, when their fingerprints are computed, then they differ; given identical inputs, then they match across runs.
3. Given a row written before this change, when a reader loads it, then it reads as unattributed and is never given a guessed fingerprint.
4. Given the row schema, then the new field ships under #644's schema version, and readers that predate it keep working.

## Design

### Approach

- One definition: `posture.fingerprint()` digests `posture.profile()`, which the one resolver
  builds from the non-strict selection: each switched-on module with the sha256 of its content in
  every primitive root, each stance with its variant and that variant's digest, the configuration
  keys that reach the model or a hook, and the harness version (AD-22).
- Each ledger's writer stamps it: `stamped()` in `usage-log.py` covers every usage row, provider
  rows included, and `_append()` in `decisions.py` covers decision and outcome rows. A record that
  already names its profile keeps it, null included.
- A role worker's status record is stamped at launch, and its ledger row copies that value.
- A replay row carries its arm's profile, resolved over the checkout the arm was synced from, or
  `bare` for the bare arm.
- Both ledgers stay on schema version 1, which ships in v0.14.0 with the field. `harness usage
  --by profile` is the reader that groups
  rows by fingerprint and shows a row without one as `(unattributed)`.

### Decisions and alternatives

- **Content digests, not versions, for modules:** a shipped module changes between releases under
  one `VERSION`, so a version alone would give two profiles one fingerprint. A skill is its whole
  directory; a stance is its variant and sidecar.
- **No path in the digest:** a root is labelled by position, and `primitive_roots` is left out of
  the configuration, so one profile matches on every machine.
- **Configuration keys:** `identity`, `permissions`, `permissions_bypass_acknowledged`,
  `plan_allow_tools`, `telemetry`, `governance`. Installer switches, remote control and
  integrations reach neither the model nor a hook. The mode name is left out; what it selects is in.
- **Schema version 1, not 2:** version 1 is unreleased until v0.14.0 and ships with every field
  that release adds, as decided for #577; criterion 4 names #644's schema version. #644's
  tolerant readers are what let an older reader carry the field.
- **Backfill never guesses:** a rescan keeps the fingerprint the ledger already holds for that
  session, which its subagents share, and stamps null otherwise. A worker record from before the
  field gives a null. A resolver that is missing or fails stamps null.
- **`bare`, not null, for the bare replay arm:** null means unattributed; the bare arm is
  attributable to the empty profile, and a named value says so.
- **Remembered per process:** a hook stamps the value on each row it writes, and the profile cannot
  change under a running hook; the key is the environment the ladder reads.

### Do not implement

- Per-module attribution of tokens or hook decisions (#790).
- The observation-only entry point or the bare-arm zero-footprint test (#791).
- Adherence events (#792).
- Rewriting any existing row, or backfilling a fingerprint onto one.
- Clearing AD-23's status tag in the architecture spine, which is a spine amendment.

## Review findings

CodeRabbit, round 1 on PR #861:

- `harness usage --by profile` could fail on a fingerprint that is not a string. Fixed: such a
  value groups as `(unattributed)`, with a test.
- The changelog said every new row names a fingerprint, though an unresolved one is `null`.
  Fixed: the fragment says so.
- The per-process fingerprint cache ignored a rewritten configuration or selection file. Fixed:
  the cache key carries each file's modification time and size, with a test that does not clear
  the cache. A module edited under a running process is still read by the next one: keying on
  every module file would walk the catalog on each call, which is the cost the cache avoids.
- The "Hit rate per rule" line implied `--rules` reports by profile. Fixed: the line names
  `--by profile` as the reader, in `product.json` and the README.

CodeRabbit, round 2, in the review body only:

- Relative paths inside a skill should leave the content digest. Declined: a file's place inside
  a skill is part of what the model is given, since the skill's text refers to its files by
  path, so a moved file is a different module. The label is relative to its root, so no
  machine path reaches the digest.
