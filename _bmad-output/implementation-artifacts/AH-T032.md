# AH-T032 — Add a merge driver for the BMad issue map so parallel reservations stop conflicting

## Goal

Two branches that each reserve a BMad ID both append to `items` in `_bmad-output/issue-map.json`
and bump `next_ids`, so whichever merges second conflicts; #786 hit it twice in one day. The fix
agents apply by hand is mechanical, so a git merge driver applies it instead, and the derived
sprint status merges into a fresh regeneration rather than a second conflict.

Decided by the owner on 2026-09-26: option 1, a git merge driver for `_bmad-output/issue-map.json`.
It takes main's map, appends the branch's entries in the tool's exact JSON format, keeps the larger
`next_ids`, and regenerates sprint status. `harness worktree create` registers it. The audit's
duplicate checks stay. When main re-mapped the same GitHub issue under another ID, main's entry
wins.

## Acceptance criteria

1. In a temporary repository, two branches that each reserve an issue merge, main into the branch,
   without an issue-map conflict; the merge commit holds both entries and the larger `next_ids`.
2. After that merge, `bmad_issue_sync.py audit` is clean and the committed sprint status equals a
   fresh regeneration.
3. When both sides mapped one GitHub issue under different IDs, main's entry wins; one ID reserved
   for two issues still conflicts and keeps both entries, so the audit's duplicate check fails.
4. `worktree create` registers the drivers idempotently, and only where the checkout ships them.
5. `.gitattributes` names both drivers, and `docs/bmad-governance.md` says how they work and how
   to register them in an existing checkout.

## Dev notes

- Files: `scripts/bmad_merge_driver.py` (new), `.gitattributes` (new), `bin/harness`
  (`register_bmad_merge_drivers`, called from `worktree create`), `tests/test_bmad_merge_driver.py`
  (new), `tests/test_worktree.py`, `docs/bmad-governance.md`, `changelog.d/819.added.md`.
- Why the sprint-status file has its own driver: merge-ort merges every path in memory and writes
  the tree at the end, so a driver cannot read another path's merged result, and a working-tree
  write outside the driver's `%A` never reaches the merge commit. A `pre-merge-commit` hook that
  regenerates and stages the file was tried first; git 2.50 had already written the merge tree, so
  the staged change was left out of the commit. The driver therefore rebuilds the merged tree for
  the inputs the render reads: the incoming commit from `git merge`'s `GITHEAD_<oid>` variable,
  `HEAD`, their single merge base, the map merged by the same function, and each story file taken
  from the side that changed it, or through `git merge-file` when both did.
- Main's side: the incoming side in a merge, the upstream (`HEAD`) side in a rebase, detected from
  `rebase-merge` or `rebase-apply` under the git directory.
- Registration is limited to the repository the running `bin/harness` belongs to, compared by
  resolved `git rev-parse --git-common-dir`, so another repository that ships a script of the same
  name never has its merges routed through it; a harness outside any checkout registers nothing.
- The driver command is relative, and git runs drivers from the worktree's top level, so each
  worktree merges with its own copy of the script. Git config is shared across worktrees.
- Default taken: in a rebase or cherry-pick the sprint-status driver reports a conflict and keeps
  your side's file, because git names no incoming commit there; you regenerate by hand as before.
- Default taken: a field both sides changed differently, or an item removed on one side and
  changed on the other, is a conflict with main's value kept, rather than a silent choice.
- Default taken: no `product.json` entry, because the drivers serve this repository's own BMad
  corpus rather than a capability the landing page advertises.
- Testing: `python3 -m unittest tests.test_bmad_merge_driver tests.test_worktree`.

## Review findings

CodeRabbit, round 1 on #895; all four held and were fixed.

1. An item the branch removed while main changed it was kept silently, though the reverse case
   conflicted. Fixed: both directions are now a conflict, with a test.
2. `parse_map` did not validate `next_ids`, so JSON `true` passed as an integer. Fixed: each
   counter must be `type(value) is int`, otherwise the driver exits as a conflict and leaves your
   side's file; regression test added.
3. A top-level key other than `items` and `next_ids` changed differently on both sides kept main's
   value and exited 0. Fixed: it is recorded as a conflict, with a test.
4. The temporary-repository test's `git` and `tool` wrappers inherited `GIT_DIR`, `GIT_WORK_TREE`
   and `GIT_INDEX_FILE` when the suite runs from a git hook. Fixed: both clear them.

CodeRabbit, round 2 on #895: the wrappers still passed `GIT_OBJECT_DIRECTORY` through. Fixed: they
drop every variable `git rev-parse --local-env-vars` lists, plus a fixed set if git cannot list
them, with a test.
