# AH-B110 — Policy-file guard gates commands that only mention a policy path

This work item was authored as part of the repository's committed BMad planning system.
<!-- bmad-sync:end -->

## Reproduction

With a decision provider configured (`governance.provider: local`), run any graded command whose
text names a policy path only as data, for example `gh issue create --body-file - <<'EOF'` with a
body naming `.agent-harness/governance.json`. The hook answers `ask` with "Governance: this
changes the governance policy file agent-harness/governance.json, which is level 1", though
nothing writes the file. Observed on `main` before this fix; the regression test reproduces it.

## Root cause

`_policy_hits` in `policy/hooks/grade-bash.py` first judged the paths the segment walk found
written, and when none was a policy file it fell back to searching the whole command text with
`POLICY_RE` and `CONFIG_RE`. That text includes quoted arguments and here-document bodies, so any
mention matched. The fallback exists to catch writes the walk cannot see: code run by a shell or
an interpreter, through `eval`, `xargs` or `find -exec`, or under a leading assignment, and lines
that do not decompose.

## Acceptance criteria

1. **Given** a configured provider, **when** a line is exactly one `gh issue|pr
   create|comment|edit|review` command and every policy path in it sits in a quoted `--body`,
   `--title`, `-b` or `-t` value or in a quoted here-document fed to `--body-file -` or `-F -`,
   **then** the policy-file guard does not gate it and the command is put to the provider as
   usual.
2. **Given** a configured provider, **when** a command writes a policy file through a redirect,
   `tee`, `sed -i`, `perl -i`, a `cp` or `mv` operand, or an unresolved operand ending in
   `governance.json` or `config.json`, **then** it is asked about as a level-1 action.
3. **Given** a configured provider, **when** any other line names a policy path, including
   `git`, `echo`, `printf` and `cat`, a shell or interpreter, a leading assignment, a
   substitution, an unquoted here-document, or a line that does not decompose, **then** it is
   level 1.

## Design

- Fail closed: `_policy_hits` searches the whole text, here-document bodies included, for a
  policy path by name unless the walk decomposed the line and `gh_text_only` holds for it.
- `gh_text_only` lexes the first line itself (`_plain_words`), keeping per-character quote
  state, since the shared tokenizer drops quotes. It refuses a backslash, a `$` or backtick
  outside single quotes, any unquoted `;`, `&`, `|`, `<`, `>`, `(` or `)` other than one `<<`
  that opens a word before a quoted delimiter, and an unclosed quote. The here-document must
  close on an exact delimiter line with nothing after it, and be fed to `--body-file -`/`-F -`.
- Only gh's built-in `issue` and `pr` text subcommands qualify, as aliases and extensions cannot
  shadow them, and `gh` must be the bare, unquoted first word.
- Rejected, after three review rounds: recognising writes inside code case by case, then an
  allowlist of data commands over the shared parser. Each missed a way in: an option before
  `-c`, an assignment carrying the path, a script piped into `sh`, a git alias, a substitution in
  an unquoted here-document, and a `<<` inside a quoted argument read as a here-document.
- Not changed: `grade_tokens`, redirect-only segment grading (#899), the provider decision loop,
  the `harness config set governance` text check and `govern_file`.
- Default taken: the exemption covers only issue and pull request text passed to gh's built-in
  create, comment, edit and review subcommands; every other mention of a policy path stays
  gated, including the issue's python note example, because each broader exemption tried in
  review let a policy write through.

## Regression test

`tests/test_policy_mentions.py`,
`PolicyMentions.test_regression_gh_text_mentioning_a_policy_path_is_not_gated`, fails on the
unfixed code (the `gh issue create` here-document is gated at level 1) and passes after it.
`test_every_other_line_naming_a_policy_path_is_gated` and the `GhTextOnly` near misses pin
criteria 2 and 3, including every review trigger.

## Review findings

- Review (major, security): an interpreter option with a separate value hid the code option
  after it, so a policy write through `python3 -W ignore -c` was not gated. Fixed in round 1, and
  covered by the fail-closed search since round 2.
- Review (major, security): `P=<policy path> python3 -c ...` was not gated because the leading
  assignment was stripped before the interpreter was scanned. Fixed: a line with a leading
  assignment is never exempt.
- Review (major, security): `printf '... > <policy path>' | sh` was not gated because only
  here-documents were read as shell input. Fixed: a shell anywhere on the line keeps the search.
- Review (major, security): `git -c alias.x='!printf x > <policy path>' x` was exempt as a data
  command. Fixed: only gh's built-in text subcommands are exempt.
- Review (critical, security): a `$(...)` in an unquoted here-document body runs at expansion,
  but the body was stripped before the exemption check. Fixed: only a quoted here-document fed
  to `--body-file -` qualifies.
- Review (critical, security): the heredoc regex matched `<<sh` inside a quoted argument, so a
  real `sh` segment was skipped as a terminator. Fixed: the exemption lexes quotes itself and
  reads no raw regex for here-documents.
