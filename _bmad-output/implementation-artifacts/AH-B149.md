# AH-B149 — grade-bash size-ratio timing test still fails about 1 run in 14

## Reproduction

Run `test_grading_a_hundred_kilobyte_command_stays_well_inside_the_hook_timeout` in a fresh
process 200 times on a machine with five performance and ten efficiency cores. As of #1122 it
failed 20 of 200 runs alone (other agents' suites running, load average about 4) and 32 of 200
beside three `python3 -c 'while 1: pass'` burners (load average 6 to 8). The full-to-quarter
ratio had a median of 3.9 but spread from 1.4 to 11.3; the other grade-bash scaling ratios never
passed 4.6.

## Root cause

The helper took the best of five batches for the full-size call and, separately, the best of five
for the quarter-size call. On a machine whose cores differ in speed, the scheduler moves the
process between a performance and an efficiency core, and the same work costs more CPU time on
the slower core. When every full-size batch landed on a slow core and one quarter-size batch on a
fast one, the ratio read about 10; the opposite case read about 1.5. Of 800 baseline ratios, 24
fell between 10 and 11 and 16 between 1 and 2, clusters a factor of about 2.5 either side of the
median, which is what a core-speed difference predicts and a growing grader does not. The 100 KB
test's calls last tens of microseconds, the shortest of the timed calls, so its batches are the
easiest to split. The grader did not change between runs.

## Acceptance criteria

1. **Given** three CPU-bound processes running, **when** the grade-bash timing tests run 200 times
   in a row, **then** all pass.
2. **Given** a grader with an injected quadratic loop, **when** the tests run, **then** the growth
   check fails every run, loaded or not.
3. **Given** the existing limits (a tenth of the tightest PreToolUse timeout, a quarter-size run
   growing less than eightfold), **then** they are unchanged.

## Design

`cpu_growth(large, small)` in `tests/test_grade_bash.py` replaces `cpu_seconds`. It times eleven
pairs of CPU-time batches of about 10 ms, the large call and the small call back to back in
alternating order, and returns the best large per-call time for the budget check and the median
of the per-pair ratios for the growth check. Both calls in a pair usually run on the same core, so
a migration moves both costs together; the median drops the few pairs a migration splits. The
scaling tests in `tests/test_grade_bash_quoting.py` and the standard-input timing tests in
`tests/test_grade_bash_stdin_text.py` (added by #1134) use it too, with seven pairs because one
here-document case costs about 0.2 s a call, and keep their `1e-4` floor on the small call. The
sizes are built once, outside the timed calls.

Rejected: larger inputs (they lengthen each call, but a slow-core batch still skews one side by the
same factor); more batches of the old best-of-each (it narrows the tail but a full set of slow-core
batches still reads 10); an operation count (the grader exposes none, and adding one changes
production code for a test).

No production code changes.

Also in this story, test hygiene: since #1133, grade-bash treats an inherited `CDPATH` as making a
relative `cd` unknown, so three `tests/test_governance_binding.py` tests failed when the
developer's shell exported one. The shared `Home` fixture now clears `CDPATH` after saving the
environment it restores, as `tests/test_governance_cd_forms.py` already does. With
`CDPATH=/nowhere` the module failed 3 of 75 tests before and passes after.

## Regression test

The changed tests are the regression tests. With the new helper, 0 of 200 probe runs failed alone
and 0 of 200 beside three burners; the full-to-quarter ratio stayed between 2.5 and 5.9. The timing
tests of all three files then passed 200 consecutive fresh-process runs beside three burners. In a
scratch copy, a quadratic `find` loop in `_grade_text` failed the 100 KB growth check at about 13
and the standard-input checks at about 9 to 10, and one in `_sql` failed the scaling test at about
10, each in 20 of 20 runs beside three burners.
