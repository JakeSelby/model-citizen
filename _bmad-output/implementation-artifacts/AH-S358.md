## Story

As a developer who forks a core rule, I want the context-cap lint to count only the rules that load, so that forking a long rule such as `secrets` does not fail the cap.

## Context and value

Forking a core module (#977) switches the original off and adds the fork to your root. The context-cap lint still counts the switched-off original, so a fork of a long core rule is counted twice and fails the cap even though only the fork loads.

## Acceptance criteria

1. The context-cap lint counts the always-loaded context a sync would project for the effective configuration, so a switched-off rule is not counted.
2. Forking a long core rule and switching the original off passes the cap when the fork alone fits, and fails it when the fork alone does not.
3. With nothing switched off, the cap's line and token figures are unchanged.
4. Tests cover a switched-off original, a fork that alone exceeds the cap and the unchanged default.

## Design

### Approach

`check_context_cap` measures the always-loaded set that a sync would project for the effective configuration, instead of every rule file in the tree, so a rule switched off by a switch or replaced by a fork is excluded.

### Decisions and alternatives

- Count what loads rather than special-case forks, so any switched-off rule is excluded the same way.

### Do not implement

- A change to the cap's limits.

## Tasks

- [ ] Count the projected set, not the tree (AC: 1)
- [ ] Pass a fork whose original is off when the fork fits (AC: 2)
- [ ] Keep the default figures unchanged (AC: 3)
- [ ] Tests for each criterion (AC: 4)
