## Story

As the maintainer running agents across many repositories, I want the `local` decision provider to hold levels for merges, for every repository at once and for whole repositories, so that it can carry the autonomy levels an external trust service holds today without a policy file committed to each repository.

## Context and value

The decision seam (AH-S172) ships a deterministic `local` provider that reads `.agent-harness/governance.json`, but it has three gaps that stop it replacing an external trust service for coding work:

- There is no action class for merging a pull request, so a merge is judged as a generic shell command.
- Policy is per repository only. Levels that apply everywhere, and levels for repositories the user cannot commit a policy file to, have nowhere to live.
- Pairs are keyed by `repo:<name>/<branch>`, and agents push from short-lived task branches, so a level granted to a repository never reaches the branch that asks.

The evidence for moving the check local: over thirty days of the maintainer's own sessions, a trust check that the model had to remember to call over MCP was absent before the first push in about a quarter of the sessions that pushed. A hook that consults a local provider cannot be skipped. That binding is the next story; this one gives the provider a policy shape able to carry the existing levels.

## Acceptance criteria

1. **Given** provider `local` and no policy file at either level, **when** any action is decided, **then** the level is the one the autonomy stance implies, exactly as before.
2. **Given** a user-level policy with `defaults.coding.git_push` of 2 and no repository file, **when** a grade-2 push is decided, **then** the outcome is `ask` at level 2 and the reason names the user-level file as the source.
3. **Given** both files set a default or a pair entry for the same class, **when** it is decided, **then** the repository file's value wins; **given** both set a cap for the same class, **then** the lower cap applies, and the built-in `coding.deploy` cap still applies on top.
4. **Given** a pair for `repo:x` and none for `repo:x/feat-y`, **when** `repo:x/feat-y` is decided, **then** the repository-wide level applies; **given** an exact pair for `repo:x/feat-y` as well, **then** the exact pair wins.
5. **Given** `coding.pr_merge` in a policy file, **when** it loads, **then** it parses, and `harness decide --action coding.pr_merge` answers.
6. **Given** a user-level policy file that cannot be honoured, **when** an action is decided, **then** a `PolicyError` names that file, never a silent empty policy.
7. **Given** provider `none`, **when** anything is decided, **then** nothing changes.
8. **Given** the change, **when** a reader opens `docs/runtime-controls.md`, **then** it describes both files, the override and cap rules and the lookup order; `harness decide` and `harness doctor` name the policy files they read.

## Design

### Approach

- Add `coding.pr_merge` to `ACTION_CLASSES`, with no built-in cap.
- Resolve a user-level `governance.json` in the harness configuration directory, found the way the harness already finds `config.json`, and let `LocalProvider` take its path so tests never touch the real one.
- Load both files with the existing `load_policy` and merge them: `defaults` and each pair's classes take the repository value over the user value; `caps` take the lower value per class.
- Resolve in this order: the exact `repo:<name>/<branch>` pair, then a `repo:<name>` pair, then the class default, then the stance level, then any cap. A slug's repository name is the text between `repo:` and the first `/`, since branch names may contain slashes.
- Name the file and layer that supplied the level in the decision's reason and rule matches.

### Decisions and alternatives

1. **The user-level policy is its own `governance.json`, in the repository file's schema.** One schema and one parser for both levels, and a later hook can protect policy by path without guarding all of `config.json`, which keeps only `governance.provider`. Rejected: a policy block inside `config.json`, which would be a second schema for the same thing.
2. **The repository file overrides the user file for `defaults` and `pairs`; `caps` combine by the lower value.** A repository's own reviewed file is the natural place to raise or lower that repository's level. Rejected: user always wins, which makes the repository file useless for graduation. Rejected: repository caps override, because a ceiling that a repository file can lift is not a ceiling.
3. **Whole-repository pairs use the key `repo:<name>`.** It says what it means and needs no knowledge of the default branch. Rejected: falling back from a task branch to `repo:<name>/main`, which guesses the default branch's name offline and makes a grant on `main` apply to every branch without saying so.

### Do not implement

- No hook changes: binding the provider into command grading, and guarding writes to policy files, are the next story.
- No import from any external service, and no network access.
- No `learn` behaviour, and no change to the `jev` provider beyond what keeps it working over the changed `LocalProvider`.
- No new configuration keys beyond what locating the user-level file needs.
