## Goal

Let `bmad-code-review` run straight through when an approved plan invokes it. The installed skill
(BMad 6.12.0) halts for human input at four checkpoints: the step 1 summary, "Resolve decision-needed
findings", "Handle `patch` findings" and "Next steps". Inside an approved `/build` those halts
contradict the rule not to re-ask within an approved plan, and the #786 session overrode each one
by hand.

Decided on 2026-09-26 for v0.14.0: a team customization in `_bmad/custom/bmad-code-review.toml`
carries the mode, the run applies every patch, records every finding in the story, and surfaces only
the decision-needed findings at the end.

## Acceptance criteria

1. Given the team customization, when `resolve_customization.py` resolves `workflow.persistent_facts`
   for `bmad-code-review`, then it returns the governance file followed by one approved-plan mode fact.
2. Given that fact, when it is read, then it gives a standing answer at each of the four checkpoints:
   proceed after the summary, leave decision-needed findings unresolved in the story, apply every
   patch, and finish.
3. Given a review not invoked by an approved plan or with `unattended`, then every checkpoint halts
   as the skill is written, and in either mode a blocking halt (no target, no active layers, missing
   subagents) still stops the run.
4. Given an approved-plan run, then every finding is written to the story's review findings section
   and the final message lists only the counts and the decision-needed findings as numbered questions.
5. Given the shipped template, then it does not repeat the fact, since `persistent_facts` append
   across team and user files.

## Dev notes

- **Mechanism.** The skill has no mode flag: its `customize.toml` exposes only
  `activation_steps_prepend`, `activation_steps_append`, `persistent_facts`, `on_complete` and
  `review_layers`. `persistent_facts` is the key SKILL.md says to carry "for the rest of the workflow
  run", so it reaches the checkpoints in step 4; an activation step runs once, before the steps load.
  The fact frames the approval as the user's standing answer at a checkpoint, rather than telling the
  run to skip one, so it does not contradict SKILL.md's "always halt at checkpoints" rule.
- **Trigger.** The mode applies when the conversation shows a plan approved with "build" or "go with
  N", or the invocation says `unattended`. Anything else keeps every halt.
- **Template.** `templates/bmad/custom/bmad-code-review.user.toml` is unchanged. Default taken: the
  mode stays team-only, because `persistent_facts` append across the team and user files and a copy
  in both would load the fact twice here. A repository that wants the mode adds the same fact to its
  own team file.
- **`/build`.** `primitives/workflows/build.md` is not edited here; it is owned by #822 in this
  release and at its line cap.
- **Testing.** `tests/test_bmad_code_review_mode.py` parses the file with the vendored `tomlkit`,
  checks the declared key surface with `toml_surface`, and pins each checkpoint's answer by the
  heading it sits under. [Source: docs/bmad.md#shared-roles-and-explicit-installation]
