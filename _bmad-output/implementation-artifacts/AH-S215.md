## Story

As the harness maintainer, I want the two repository-specific detectors that fall under the precision
floor tightened, so that a rule's hit rate is not inflated by false positives a stranger's session can
trigger, and the corpus job holds the floor without exceptions.

## Context and value

PR #601 [Source: PR #601] scored all seventeen detectors against a labelled corpus in CI and kept the 0.9 precision floor
rather than lowering it. Two detectors measured precision 0.83 at recall 1.00, and the PR recorded both
in `known_below_floor` with their measured pair, filing the fix separately as this issue:

- `secrets/git-add-secret-file`: any basename containing `id_rsa` is a hit, so
  `git add docs/id_rsa-rotation.md` fires.
- `autonomy/denied-by-grade`: the hook's signature `(grade-bash hook,` matches anywhere in a Bash
  result, so a grep over a test file that prints it fires.

Both behaviours are confirmed in `policy/hooks/rule-detectors.py` on `main`: the secret-file check tests
`"id_rsa" in base`, and the grade check tests `GRADE_SIGNATURE in` the event text.
[Source: https://github.com/JakeSelby/agent-harness/issues/602]

## Acceptance criteria

1. **Given** the committed corpus, **when** it is scored, **then** both detectors clear the 0.9 floor
   with the false-positive cases still labelled negative.
2. **Given** the fix, **when** the corpus job runs, **then** both `known_below_floor` records are removed
   and the job stays green.

## Design

### Approach

Narrow each detector's match so the labelled near-misses stop firing while the positives still do.
The job itself enforces the second criterion: PR #601 made it fail on a stale below-floor record, so a
record left behind after a detector clears the floor turns it red.

### Decisions and alternatives

- **Keep the floor; fix the detector** (issue "Why"): the floor is not lowered, and each detector stays
  listed until it is fixed and its record removed.
- `secrets/git-add-secret-file` matches the default private-key names whole: a basename equal to
  `id_rsa` or `id_ed25519`. A name that merely holds one (`id_rsa-rotation.md`, `id_ed25519.pub`) is
  not a key. No other key family was added, so the detector only narrows.
- `autonomy/denied-by-grade` matches the hook's whole deny and nothing else: the reason
  `grade N, <label>: ... (grade-bash hook, autonomy=<variant>)` opens the result, behind at most the
  literal `PreToolUse:Bash hook error:` prefix Claude Code writes, and only what `grade-bash.py`
  appends may follow it: a `Governance:` sentence, then its deny tail or its approval tail, then
  whitespace. The tails are copied into the detector and a test holds them to the hook's. A
  signature quoted after a file and line, another hook event's prefix, or a denial-shaped line
  followed by other output is not a denial. The unresolved-stance label
  (`autonomy=execute, unresolved: ...`) is accepted, which the first narrowing missed.
- Where the two readings trade recall for precision, the detector under-counts: a missed hit is a
  quieter report, a false hit a wrong one.

### Do not implement

- Relabelling the false-positive cases as positive to raise precision (criterion 1 forbids it).
- Changes to the floor.
