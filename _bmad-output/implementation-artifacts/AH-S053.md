## Story

As a harness developer, I want decision points bound in `shadow` to the shared Claude Code and Codex
runtime events, so that a provider's answers can be measured on real traffic from both runtimes
without a second policy definition per runtime and without changing any decision.

## Context and value

The foundation (#136 to #139) gives a provider, controls, packs and ledger rows, but no hook consults a
provider yet; every earlier pull request says so. This story is the binding, and it is on the epic's
critical path before the first consumers (#141, #372). The 2026-09-21 re-scope made it shadow first: a
point is bound in `shadow`, measured, and only then considered for `advise`. Semantic checks must
consume shared events without separate Claude and Codex policy definitions or overstated native
support.
[Source: https://github.com/JakeSelby/agent-harness/issues/140]

## Acceptance criteria

1. **Given** a bound point, **when** a request is about to execute, **then** it is classified last in
   the hook chain, after any hook that rewrites the input has run.
2. **Given** a bound point in `shadow`, **when** measured over 200 live decisions, **then** the hook's
   added latency p95 is under 1 s, and a 2 s timeout falls through silently.
3. **Given** a provider, **when** it runs, **then** it runs beside a deterministic check and never
   between that check and its consumer.
4. **Given** a point on an event only Claude Code offers (`UserPromptSubmit`, `SubagentStart`,
   `SubagentStop`), **when** it is documented, **then** the Codex gap is named per point rather than
   emulated.
5. **Given** equivalent normalized events from both runtimes, **when** one pack judges them, **then** it
   behaves consistently and keeps the original evidence provenance.
6. **Given** disabled, observation-only and advisory modes, **when** each is tested, **then** no hook
   recurses and no notice repeats for unchanged evidence.
7. **Given** a timeout, cancellation or provider failure, **when** it occurs, **then** the deterministic
   behaviour is preserved and the result is visible as unverified.
8. **Given** a runtime, client or platform claimed as supported, **when** the claim is made, **then**
   actual invocation and delivery have been demonstrated for it, with #98 compatibility evidence.
9. **Given** a bound point, **when** it writes a decision row, **then** the row names the cause of its
   final outcome, `deterministic` or `provider`, so a later label is never credited to the wrong path.
   In `shadow` the cause is always `deterministic`; the field exists before any point can promote.

## Design

### Approach

Bind points to the shared events `PreToolUse`, `PostToolUse`, `SessionStart`, `Stop` and `SessionEnd`,
positioned last in each chain, in `shadow`. The provider call writes the decision row #139 defined and
returns the deterministic decision unchanged.
[ASSUMPTION: the binding reuses #139's decision row and #137's per-point mode; the issue names both
as blockers but does not spell out the reuse.]

### Decisions and alternatives

- **Shadow first,** then `advise` only after measurement (re-scope).
- **Last in the chain:** classify the input that will actually execute, after rewriting hooks.
- **Beside, never between:** the provider does not sit between a deterministic verifier and the
  decision that consumes it.
- **Name runtime gaps rather than emulate them.** Explicit or replay support does not imply
  automatic-hook support.

### Do not implement

- `advise` or `act` at any point; those are per-consumer stories (#141, #372).
- Emulation of Claude Code-only events on Codex.
- Separate per-runtime policy definitions.
