## Story

As a developer, I want the result of a rollback to stay on screen until I dismiss it, so that I can read what was restored while the refreshed Activity list shows behind it.

## Context and value

When a rollback (#979) completes, Activity reloads and replaces the result before it can be read. For the same reason the #999 accessibility audit cannot reach the completed rollback result, so that state is unaudited.

## Acceptance criteria

1. After a rollback completes, its result stays visible until you dismiss it, and the Activity list refreshes behind it.
2. The result is announced once to assistive technology; its dismiss control is reachable and operable by keyboard, and focus returns to the Activity list.
3. A failed rollback keeps its error on screen the same way.
4. The #999 accessibility suite audits the completed rollback result: contrast, focus and 320 and 390 px reflow.
5. Tests cover each criterion.

## Design

### Approach

Keep the rollback result in Activity's own state, outside the list the refresh replaces, as a dismissible status region above the list; the refresh updates the list behind it.

### Decisions and alternatives

- Decided 2026-10-06: the result stays until dismissed, rather than a timed toast or a reload that replaces it.
- The status region is always mounted and empty until a result arrives, so it is announced once, and not again when the list behind it refreshes. The dismiss button sits outside the live region, so its label is not part of what is announced.
- The refresh after a completed rollback reloads the first page in place: the old list stays until the new one replaces it, so rows and their panels are not unmounted.
- Dismissing focuses the Activity list (a `tabindex="-1"` section), or the page heading when no list is loaded. When completing the rollback removes the focused Roll back button, focus moves to the dismiss control.
- A rollback that throws instead of answering is kept the same way as a failed one, with its error and a "no result" badge.

### Do not implement

- Changes to rollback itself (#979).

## Review findings

Round 1, no blockers:

- The refresh read the filters of the render the rollback started in: it now reads the applied filters from a ref, and a browser test applies a filter while the rollback is held and asserts the refresh loads it (fails on the old code).
- A refresh that cancelled a filter load left the loading flag set: the refresh now clears it. No current path shows the stale flag on screen, so no test observes it.
- The panel test was vacuous: the browser audit now asserts the panel's live region is empty after a completed rollback, and the vacuous unit test is gone.
- Focus moving to Dismiss was unasserted: the audit now rolls back by Enter on a focused button and asserts focus lands on Dismiss.
- Dismiss was reached by script outside the 320 px walk: every width, both themes and the refused result now Tab to it.
- The served completed result now carries `nothing_changed: false`, as the engine sets it.
- `onResult` is required, and the unused `RollbackOutcome` is removed.
