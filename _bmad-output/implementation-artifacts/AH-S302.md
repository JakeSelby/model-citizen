## Story

As a developer, I want to see and confirm what a run will spend, with caps that stop it cleanly, so that measurement never surprises me on cost or limits.

## Context and value

A run that spends usage shows, before it starts, an estimate from past runs of the same suite and scale, the caps it will run under (`--max-budget-usd` per run and `--spend-cap` for the set), and whether it spends API credit or a subscription plan's limits. The developer confirms each such run. At a cap or a usage-limit error the run stops cleanly, keeps what it finished, and says why.

## Acceptance criteria

1. Given a suite that spends usage, then no process starts until the developer confirms the shown estimate and caps.
2. Given a run that reaches its cap, then it stops, records the finished cases and marks the rest as not run.
3. Given a usage-limit error from the client, then the run stops and reports the limit, not a failure.
4. The run's spend appears in the usage ledger under the run's ID.

## Design

### Approach

Treat spend admission as immutable run identity. A paid suite declares its case identities, then
the supervisor derives a median estimate from completed runs of that exact suite and case count,
binds the per-process and whole-set caps plus pricing source into the run digest, and appends the
two cap flags to the allowlisted command only after the developer returns the random, durable,
single-use token from that exact displayed preview. Preview and admission compute history under
the supervisor lock, and cap strings retain the exact confirmed decimal text. The allowlisted runner
writes one bounded result file; the worker validates it, preserves completed and not-run cases,
then durably records terminal actuals before idempotently settling spend into the existing usage
ledger under the run UUID.

### Decisions and alternatives

- Estimate only complete, successful runs at the exact case count. Partial capped data would
  systematically understate the next full set.
- Record API credit and subscription limits as different pricing sources. Subscription spend is a
  list-price equivalent against a plan limit, not a claim that dollars were charged.
- Use the existing runner's `--max-budget-usd` and `--spend-cap` controls, then validate its result.
- Store a private random confirmation token bound to the complete immutable request, consume it
  once under the supervisor lock, and keep only its hash on disk. A reusable digest or boolean
  flag could replay a paid request without a fresh preview.
  Killing a process from ledger polling cannot preserve case boundaries reliably.
- Represent provider exhaustion as `limited` and the whole-set cap as `capped`, both terminal but
  neither a test failure.

### Do not implement

Suite-specific native acceptance, replay, evaluation and four-arm runner adapters remain in their
own stories. This story does not infer prices, buy usage, or turn a subscription-plan equivalent
into an invoice amount.

## Review findings

- Replaced the reusable confirmation digest with a private random token bound to the full request;
  consumption is atomic under the supervisor lock, including concurrent replay coverage.
- Preserved canonical decimal cap strings from preview through stored run state and runner argv.
- Moved history reads and plan calculation under the supervisor lock for preview and admission.
- Rejected every explicit or synthesized `not_run` case unless the result names its stop reason.
- Corrected run-store normalization to retain actual spend and index `case_results`.
- Added `studio_run` schema, usage-report and telemetry handling keyed by run UUID.
- Persisted terminal run actuals with a pending marker before idempotent usage upsert, then durably
  marked settlement recorded so recovery can retry without duplicating or leading run authority.
