## Story

As a developer, I want to run factorial switch screens from Studio, so that the Studio supports the engines delivered in its milestone.

## Context and value

Split the factorial portion of #989 into its own v0.18.0 delivery. #989 retains four-arm and layer-swap Studio support in v0.17.0.

## Acceptance criteria

1. Switch selection uses the core design authority and previews arms, trials and spend before confirmation.
2. Results display each main effect with its interval, trial count and declared design limitations, using the engine's analysis without a second browser estimator.
3. The recorded run preserves target, treatment, design and source-result identities; missing engines are unavailable rather than broken catalog entries.
4. CLI parity, spend admission/cancellation and fixed-result integration tests cover the same design.

## Design

### Approach

Adapt the existing Studio core and CLI contracts after the listed engine dependencies land. Preserve native result files as authority, keep UI actions on the same governed path as the CLI, and record capability availability explicitly. Detailed file-level design belongs to the future implementation session.

### Decisions and alternatives

Deliver this integration in the engine's milestone rather than postponing it to an unspecified UI release. Keep feature ownership separate from the cross-cutting post-Measured integration gate.

### Do not implement

Do not duplicate engine analysis or change live configuration outside governed apply. This roadmap filing does not implement the capability or authorize a release.
