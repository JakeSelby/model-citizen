# AH-S274 — Give the burndown bot its own GitHub App identity and an owner-label gate

## Story

As the repository owner, I want the burndown bot to act under its own GitHub App, held to the same
ruleset as any contributor, and only on issues I labelled, so that an unattended agent on a public
repository can open pull requests without holding my bypass or taking instructions from strangers.

## Context and value

The `main-review` ruleset is squash-only with zero approvals, required thread resolution and strict
required checks (lint, test, issue-ownership, landing-copy), and it lets the admin role bypass it. A bot
acting with the owner's token is therefore bound by nothing. A GitHub App that is not a bypass actor is
held to the required checks and thread resolution like any contributor; GitHub Apps are eligible bypass
actors, so the App must stay off that list
[Source: https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets].

The repository is public, so anyone can file or comment on a bug. Today the owner is the only
collaborator, so only the owner can label, but the gate must not rest on that. Every other lane (#948,
#950, #951) depends on this identity and gate. Traces to FR-71
([#945](https://github.com/JakeSelby/model-citizen/issues/945)).

## Acceptance criteria

1. **Given** the App's registration, **then** it holds contents, pull requests and issues write, and
   checks and statuses read; no administration, no workflows and no ruleset bypass; and the owner's
   setup steps are in `docs/burndown-bot.md`.
2. **Given** an issue labelled `bot::ready` by anyone but the owner, **then** the bot takes no action
   and says why in the run summary.
3. **Given** an eligible issue, **then** the agent job runs with a read-only token and no App token, and
   a separate job with no agent validates the patch and pushes it.
4. **Given** a patch that touches `.github/` or targets any base but `main`, **then** the writer job
   refuses it.
5. **Given** comments from anyone but the owner, **then** the agent never receives them; the issue body
   and the owner's comments reach it as quoted data.

## Design

### Approach

- **Owner-only setup,** handed over as exact steps in `docs/burndown-bot.md` and never run by an agent:
  register the App and install it on this repository only (and the spike's scratch repository, #943);
  store its ID and private key as repository secrets; run `claude setup-token` and store the token as
  `CLAUDE_CODE_OAUTH_TOKEN`; connect Codex (#950).
- **App permissions:** contents, pull requests and issues write; checks, commit statuses and metadata
  read; repository security advisories write for the vuln lane (#951). No administration and no
  workflows, so GitHub itself rejects a push touching `.github/workflows/`. Never a ruleset bypass actor.
- **Labels:** `bot::ready` (owner: eligible), `bot::claimed`, `bot::deferred`, `bot::needs-owner`,
  `bot::ready-to-merge`, and `bot::authored` on every bot pull request.
- **Variables:** a pause switch, a merge switch, daily and weekly attempt caps, the turn cap (#946).
- **Two jobs.** The agent job gets a read-only `GITHUB_TOKEN` and no App token, and emits a patch and a
  structured result. A second job with no agent mints the App token with create-github-app-token, checks
  the patch against a path allowlist and the base, pushes `burndown/<issue>` and opens the pull request.
  This is the split gh-aw uses for its safe outputs.
- **Triggers:** schedule, `workflow_dispatch`, and CodeRabbit's status on `burndown/*` heads. Never
  `pull_request_target`.
- **Trust.** The owner gate checks the `labeled` event's actor, not just the label's presence. The agent
  sees the issue body and the owner's comments inside a quoted data block, and nothing else.
- The two-job boundary is a new invariant, so the delivery pull request amends the architecture spine
  through `bmad-architecture`'s update intent.

### Decisions and alternatives

- **An App, not the owner's token.** The owner's token inherits the admin bypass. Rejected: a
  fine-grained personal token, which acts as the owner and so as an admin on the ruleset.
- **No workflows permission.** The bot can never rewrite its own guard rails; a fix that needs a
  workflow change goes to the owner.
- **Actor check on the label event.** Rejected: trusting the label's presence, which a future
  collaborator or a compromised integration could add.
- **Separate writer job.** Rejected: giving the agent the App token with instructions not to misuse it;
  prompt text is not a boundary.

### Do not implement

- Registering the App, storing secrets or creating labels; those are the owner's steps.
- The lanes themselves (#948, #950, #951) and the budget (#946).
- Any `pull_request_target` trigger.

## Dev notes

### Bound decisions and requirements

- FR-71 Unattended bug-fix lanes: the App "holds no ruleset bypass, administration or workflow
  permission"; an issue labelled by anyone but the owner gets no action; a patch touching `.github/` or
  aimed at any base but `main` is refused.
- AD-9 Checks bind subagents; decisions flow up: the bot inherits every check a session is bound by.
- AD-21 Dependencies: each new action is pinned and passes licensing review.
- The autonomy stance: deploys and production changes are never autonomous; the App's setup is the
  owner's.

### Files to touch

- `docs/burndown-bot.md` (new)
- `.github/workflows/burndown.yml` (new), written by a session under the owner's identity, since the App
  itself holds no workflows permission
- the writer job's patch validator and its test under `tests/`
- `_bmad-output/planning-artifacts/architecture-spines/architecture-agent-harness-2026-09-23/ARCHITECTURE-SPINE.md`
- `changelog.d/945.added.md`

### Testing

- Unit tests for the patch validator: a `.github/` path, a base other than `main`, and a clean patch
  (AC 4).
- Unit tests for the owner gate on recorded `labeled` event payloads, one from the owner and one from
  another actor (AC 2).
- Unit tests for the input builder: a stranger's comment is absent, the owner's is quoted (AC 5).
- AC 1 and AC 3 are checked against the App's settings page and a run log, recorded on #945.
