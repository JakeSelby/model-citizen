# AH-S346 — Pre-register a draft test so it can say whether the change helped

## Story

As a developer, I want to pre-register a test of a draft before running it, so that a draft test can say whether my change helped or made things worse, not only that it was exploratory.

## Context and value

#991 runs a draft against its base and reports the engine's comparison, but a draft test is always exploratory: only a release can run pre-registered, and the evidence standard lets only a pre-registered, adequately powered run support a claim. So the Studio can never answer its own question with "helped". Decided 2026-10-03: let a draft checkpoint be pre-registered, opt-in, with exploratory runs staying the default.

## Acceptance criteria

1. **Given** a draft checkpoint, **when** the developer registers a test before running it, **then** the registration names the draft's commit, its base commit, the task set and pack, the trial count, the model and the minimum effect it should detect, in the engine's registration format and from the engine's power figure.
2. **Given** a registration whose trial count can't detect the named effect, **then** registration is refused with the engine's minimum detectable effect and the fewest trials that would.
3. **Given** a run that matches its registration exactly, **then** the verdict may read "helped" or "worse" under the evidence standard's decision rule (SM-2), and otherwise "inconclusive".
4. **Given** any deviation from the registration (another commit, task set, pack, trial count or model), **then** the run is labelled exploratory and its verdict carries no direction.
5. **Given** a draft edit after registration, **then** the registration goes stale and a new one is required; the stale one stays in history.
6. **Given** a registration, **then** it is written before the run starts and can't be edited afterwards; the CLI (`citizen draft test --register`) and the Studio share one path.

## Design

### Approach

`lib/harness_core/studio/draft_registration.py` holds the one `register` path the CLI and the new `POST /api/configure/test/register` route share (AC 6). It reads the draft through `draft_tests.identity` (the snapshot read), validates the sample (model, trials per task, the whole task set of the pack or repository, a pack resolved by name and digest), refuses an effect above SM-2's 15% cap and a caller-stated coefficient of variation, and runs `draft_tests.power` (the engine's `replay_stats.minimum_detectable_effect`) on the repository's declared variance: a sample that cannot detect the effect, or fewer than the engine's five trials, is refused with the engine's figure and the fewest trials that would (AC 2).

The plan is `docs/pre-registration-template.md` itself, read section by section with `experiment_protocol`'s readers: each field the Studio states replaces the template's, every other field keeps the template's text, and a placeholder left anywhere fails the registration. It also states the compared values (commits, configuration digest, task set, task manifest digest, pack digest, model) as Run fields, and it is written as `benchmarks/preregistrations/<date>-draft-<id>.md`, and committed to a private Git registry under the supervisor's state root (`draft-tests/registry`); `experiment_protocol.check` must pass on it there, unchanged (AC 1). A structured record (`draft-tests/registrations/<id>.json`) indexes the plan, its commit and its SHA-256; both files are written once (`O_EXCL`, linked into place, mode 0400) under one cross-process lock. Every read re-runs the protocol check and the digest, and every compared value is read back from the plan at its registry commit, so an edit to either file is found and a rewritten record changes nothing (AC 6).

Starting a test may name a registration. A stale one (the draft has another checkpoint or configuration) is refused with `draft_test_registration_stale` (AC 5), and a used one with `draft_test_registration_used`: a registration backs one run, claimed atomically by an exclusively created `<id>.used` file before the run is admitted. A claim that exists or cannot be written refuses the start, a run that is then not admitted releases the claim, and the admitted run is recorded as `<id>.run`. The panel reads the start response's `record.deviations` to say whether the run counts. Any other departure from it, a changed task manifest included, starts the test exploratory with each deviation recorded in the test record (AC 4). The plan route returns the same deviations for the registration it names, and the panel shows that list, never its own. At verdict time `draft_registration.evidence` re-checks the registration: intact, written before the run started, claimed by this run, and matching what the run measured (base and draft commits, configuration digest, tasks, trials, model, pack digest, read from #990's comparison). Only then does `draft_tests.registered_claim` count both sides as pre-registered for `compare.direction_withheld`, leaving the engine's exploratory marks and the run-window note in force, and `draft_tests.claim` applies SM-2's decision rule and its mirror (AC 3). Anything else is exploratory with every reason (AC 4).

`citizen draft test NAME --register --model M --repetitions N --task T ... [--pack P --pack-digest D] --effect E [--json]` (every task of the set; no `--cv`, since power comes from the declared variance) and the "Pre-register this test" opt-in on the "Test this draft" panel call the same function. The verdicts payload lists every registration newest first with its stale flag and any problems; a stale one stays listed (AC 5). Each verdict carries `evidence`, `registration` and `deviations`.

### Decisions and alternatives

- **A private registry repository, not the installed checkout or the draft.** The engine's check needs a committed, dated plan in a Git repository. Committing to the installed checkout would write into the user's live harness; committing to the draft would change its checkpoint and make the registration stale at once. A Git repository under the state root lets `experiment_protocol.check` run verbatim. Rejected: a new Studio-only format (the brief forbids it), and skipping the commit checks (they are what make the plan immutable).
- **The native run stays `--exploratory`.** A registered draft target is not passed `--pre-registration` to `cost_bench.py`, because that would demand a plan committed in the installed checkout and write a benchmark history row for a draft. The registration lets the Studio apply the decision rule to the draft test; it never becomes a citable history row.
- **SM-2's 15% cap is enforced at registration.** The evidence standard says the minimum detectable effect is stated before the run and is at most 15%, so a larger named effect is refused rather than registered.
- **A stale registration is refused at start; other deviations run exploratory.** A changed draft is AC 5's "a new one is required"; a different task set, trial count, model or pack is AC 4's exploratory run, so the developer can still run it.
- **Single use, claimed before admission.** The claim is an exclusive create written before the run starts, so two racing starts admit one run and a claim that cannot be written starts nothing; a run that is not admitted releases the claim, and a claim whose run is recorded is never undone. A developer cannot rerun a registered test until it reads helped.
- **Declared variance only.** A caller-chosen coefficient of variation could make any sample look powered, so registration plans from `benchmarks/ablations.json` and refuses a stated one. With none declared, registration is refused with the way forward: an exploratory pilot, `scripts/replay_power.py --pilot`, and a `planning` entry in `benchmarks/ablations.json`. A registered pilot as a variance source is not built.
- **Whole set only.** As `replay.label_evidence` does for a release, a task subset cannot be registered, so a favourable subset cannot be chosen.
- **The task catalog's real source.** Without a pack, the catalog is the installed checkout's `benchmarks/tasks.json`, not the base commit's; the plan says so and pins its SHA-256, and a change by the time the test starts is a deviation.
- **The register route refuses with a code.** Studio error responses carry only a code, so an underpowered registration is `409 draft_test_underpowered`; the panel enables "Register this test" only after a plan whose power check passed, and that plan already shows the engine's figure and the trials needed. The CLI prints the full sentence.

### Do not implement

- No benchmark history row for a draft test, and no `--pre-registration` passed to the native benchmark for a draft target.
- No change to how releases are registered (`replay.label_evidence`).
- No edit, amendment or deletion of a registration; a deviation log entry after the first trial is out of scope.
- No `product.json` line.

## Review findings

- Round 1, blocking: a registration could back any number of runs. Fixed: single use, claimed atomically when the run is admitted; a reuse is refused, a racing start runs exploratory, and only the claiming run can count.
- Round 1: a caller-chosen cv bypassed the power refusal. Fixed: registration plans from the declared variance and refuses a stated cv.
- Round 1: a task subset could be registered. Fixed: whole set only, as for a release.
- Round 1: deviations were compared against the record JSON. Fixed: compared values are read back from the committed plan; a record that disagrees is a problem.
- Round 1: "Confirm and test" stayed enabled with pre-register ticked and no registration. Fixed.
- Round 1: the panel recomputed deviations. Fixed: the plan route returns the server's list and the panel shows it.
- Round 1: the plan misnamed the catalog's source. Fixed: it names the installed checkout's file and pins its digest; a change at start is a deviation.
- Round 1: the engine check inherited `GIT_DIR`. Fixed: its Git calls run without repository variables.
- Round 3: a failed claim after admission left the registration reusable. Fixed: claimed before the run starts; a failed claim refuses the start.
- Round 3: the panel assumed a started run was registered. Fixed: it reads the start response's deviations.
- Round 3: no way forward without a declared variance. Fixed: the refusal names the pilot, the power command and the manifest entry.
- Round 3: a model with outer spaces never matched its plan. Fixed: stripped at registration.
- Round 3: tests named a race without racing. Fixed: two real concurrent starts, a failed-claim test and a not-admitted release test.
- Round 3: the blocked-start live region mounted with its text. Fixed: always mounted.
- Round 3: each verdicts refresh reloaded every registration several times. Fixed: loaded once per request, and the engine module once per process.
- Round 3 (spec): the plan replaced the decision rule and deviation log wholesale. Fixed: the template's lines are kept and only the harness and bare wording is rewritten; pack and draft-commit departures are tested through the full verdict.
- Round 1 (spec): the plan mirrored the template instead of reading it. Fixed: filled from the template section by section. AC 4, AC 6 and the real-pack path gained the tests the review named.
