# AH-B117 — Adherence emissions are never settled in a live session, so no response row is written

## Reproduction

With the usage feed's fresh-session threshold set, let a session cross it: `adherence.jsonl`
gains an `emitted` row. Start any number of later sessions, a day or more after it. The ledger
still holds the one `emitted` row and no `response` row. `git grep -n 'settle(' -- bin lib policy
claude` finds only the definition. Called by hand, `adherence.settle()` writes `unknown` with
reason `unobserved`, as designed.

## Root cause

#792 (AH-S236) shipped both halves of the ledger, `emit` wired into the usage feed and `settle`
and `rates` in `policy/hooks/adherence.py`, but wired only the first into a hook path. The
second acceptance criterion of AH-S236 held only in `tests/test_adherence.py`, which calls
`settle()` directly. [Source: policy/hooks/adherence.py#settle]

## Acceptance criteria

1. **Given** an `emitted` row whose window has passed, **when** the hooks next run in a session,
   **then** exactly one `response` row is written for it, carrying no message text; running them
   again writes no second row.
2. **Given** no due emission, **when** the hooks run, **then** settling writes nothing and adds
   nothing to model context (#791's zero-footprint test).
3. **Given** the regression test, **then** it drives the live entry point, not `settle()`.

## Design

`lib/harness_core/lifecycle.py` calls `adherence.settle()` on SessionStart, before
`harness-session`, through a `settle_adherence()` helper that drops the result and swallows every
failure, so the start-up answer is byte-identical either way.

Session start fits the design: `settle` is idempotent (it skips an `adherence_id` already
answered), an `unknown` answer is only due a day after the emission, and the one outcome that
counts as following the fresh-session line, `SessionEnd`, is in an earlier session by then. It runs
once per session, not per prompt, so the full ledger read is not paid on every turn.

Rejected: settling in the usage feed's `UserPromptSubmit` path, which pays two ledger reads per
prompt and never runs once the feed is off; settling at SessionEnd, whose 1.5-second budget
already carries the decision log and the usage worker.

Settling is not gated on the `usage-feed` id: `adherence` is a library, not a hook id, and an
emission recorded before the feed was switched off still deserves its answer. No rate report is
added; that is #798.

## Regression test

`tests/test_adherence_settle.py` runs `adapters/<runtime>/hook.py` as its own process with a
SessionStart payload, on both runtimes, in a temporary home. It fails before the fix (`0 != 1`
response rows) and passes after. It also checks that a second start adds no row, that a
not-yet-due emission and an empty home leave the ledger untouched, and that the start-up stdout is
the same with a due emission, an open one, no ledger, and an unreadable ledger.

## Review findings

- CodeRabbit (major), PR #1016: two session starts could both read one unanswered emission and
  both append a response. Resolved: `settle` now reads, checks and appends under `ledger_lock`,
  an exclusive `flock` on the ledger polled for at most `LOCK_BUDGET` (1 s). Out of budget or on
  any error it writes nothing and leaves the answer to a later start, since skipping is safe and
  an unlocked append is not. `ConcurrentSettleTests` holds two threaded settlers inside their
  reading together; it writes two rows without the lock and one with it.
- CodeRabbit second pass (major): with no `fcntl`, `ledger_lock` settled unlocked. Resolved: it
  yields False, so the emission waits for a later start; every supported platform has `fcntl`.
- CodeRabbit second pass (nitpick): the locked assertion could pass without contention.
  Resolved: the first settler now waits inside its reading until a wrapped `flock` records the
  second settler's refusal, and the test asserts that refusal and one row.
