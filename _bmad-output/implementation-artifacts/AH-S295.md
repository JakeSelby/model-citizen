## Story

As a developer, I want to review a draft and apply it through the same checks and locks as the CLI, so that a Studio change is as safe and auditable as a command.

## Context and value

A draft's review page shows every file and configuration key it changes against its base, with its lint status, the budget delta and the equivalent CLI commands. Apply runs through the governed path (`config_set` for keys, a fast-forward of the developer's own root for module files, then `citizen sync`) under the same lock as the CLI, with ownership journal and decision log rows that name the Studio and the draft.

## Acceptance criteria

1. Given a draft with lint findings, then apply is refused with the findings.
2. Given another writer holding the sync lock, then apply waits or refuses and names the holder, and never interleaves.
3. Given a draft that changes a core module in place, then apply refuses and offers a fork, or a branch holding the draft's commits with the commands to open a pull request.
4. Given an apply, then the doctor checks run and the overview shows the result, and the applied state equals running the CLI commands shown, in tests.

## Design

### Approach

A new `lib/harness_core/studio/apply.py` reviews a draft and applies it; `citizen draft review|apply`
and two authenticated routes expose it, and the Configure page gains a review-and-apply panel.

- **Review** (read-only, through `drafts.read_snapshot`, the recovering seqlock read): every file the
  draft changes against its base, scoped `personal` (inside the draft's registered
  `personal-primitives`) or `core`; every configuration key that differs between the draft's base
  copy and its configuration, with its base, draft and live values; the checks (`citizen lint` run in
  the draft with its configuration, then strict resolution); the always-loaded line delta; and the
  exact commands in order. (AC 1, 3, 4)
- **Personal root moves out.** The draft registers `<checkout>/personal-primitives` (#977). Apply
  writes its changed files to `~/.config/agent-harness/personal-primitives` and rewrites that
  `primitive_roots` entry. It is a fast-forward: a file is written only when the live copy equals the
  draft's base, or already equals the draft; otherwise apply refuses and names the file.
- **Configuration through `config set`.** Each changed key is written by `config set`'s own locked
  body (split out of `config_set` as `config_set_locked`, and `config_unset_locked`). The order is
  found by running the commands with the installed CLI against a copy of the live configuration and
  root, retrying a refused key after each success, and the result must hold the draft's value for
  every key. A key the live configuration changed since the draft was made is refused, never
  overwritten. (AC 4)
- **Apply** takes the sync lock, then the configuration lock, then the draft's writer lock, re-plans
  under them, refuses on any finding, journals intent, writes the root and the keys, runs sync
  in-process without its lock, then doctor. A failed write or a non-zero sync restores the
  configuration bytes and root files, and re-runs sync. The apply journal
  (`~/.local/state/agent-harness/applies.jsonl`) records prior and applied values per key and file;
  a `studio.apply` event in `decisions.jsonl` names the draft and the actor, which Activity shows.
  (AC 2, 4)
- **Holder naming.** `reconcile.lock` takes an optional holder, recorded beside the lock while held
  and named in the refusal another caller sees; `sync`, `uninstall`, `config set|unset` and apply
  name themselves. (AC 2)
- **Core edits.** A change outside the personal root refuses apply and offers a fork of each touched
  core rule or skill (`citizen draft module plan`), or the draft branch with the push and
  `gh pr create` commands. (AC 3)
- **Studio.** `POST /api/configure/apply/review` runs review; `POST /api/configure/apply` requires the
  draft name typed back as `confirm`, then runs `citizen draft apply --json` as a subprocess on the
  mutation lane, so the Studio takes exactly the CLI's locks. The panel invalidates the overview
  query after an apply, and shows the doctor checks that need attention.

### Decisions and alternatives

1. **A held lock refuses at once, naming the holder.** Rejected: waiting, which would let a Studio
   request hang behind a long sync; the AC allows either.
2. **The personal root lands beside the configuration**, like `citizen import`'s roots. Rejected:
   leaving it in the installed checkout (a core-tree write), or making it a Git repository, which no
   other command creates.
3. **The Studio runs the CLI.** Rejected: an in-process adapter like the overview's, which would let
   a Studio apply drift from the command.
4. **Apply refuses** a draft behind the installed revision (rebase first), any other root inside
   the checkout, a non-regular file in the root, a symlinked live configuration, and a draft with
   nothing left to apply.
5. **A non-zero sync, including sync's "needs your attention", fails the apply and restores.**
   Rejected: keeping a configuration whose projection did not complete.
6. **The confirmation is the draft's name typed back**, checked by the server, per the UX
   specification's destructive-confirmation rule.

### Do not implement

Rollback (#979), merging a later draft's root into an already applied root, applying in-place core
edits, opening the pull request, and the product.json feature line (#1062).

### Testing

`tests/test_studio_draft_apply.py` drives real drafts through the CLI in temporary homes. AC1: a
checkpointed secret makes review fail its checks and apply refuse with the finding, writing nothing.
AC2: a sync lock or configuration lock held by the test refuses apply naming the holder and pid;
while apply holds the lock, `citizen sync` is refused naming the apply, and the failed apply restores
the configuration and root. AC3: an in-place core edit is refused with the fork module, the draft
branch and the PR commands. AC4: one home applies, a second identical home runs the review's
commands through `/bin/sh`; configuration, root, ownership journal, manifest and projected files
agree, the decision log and apply journal name the draft, and a second review has nothing to apply.
Live and root divergence, stale revisions, key flattening, root rewriting and the lock holder record
are covered too. `tests/test_studio_draft_apply_routes.py` asserts 401, 403 (no CSRF, no Origin,
foreign Origin), 400 (bad types, extra field, missing confirmation) on both routes, and a confirmed
Studio apply that Activity records with the Studio as actor. `studio/tests/draft-apply.test.ts`
covers the review, refusal, lock, core-offer and outcome views, the confirmation gate and the API.
