## Story

As a harness maintainer, I want each row to say which module put which tokens into the model's context and which module's hook made which decision, so that a module's cost and effect can be reported per module.

## Context and value

A module's cost and effect can be reported only if each row says which module put which tokens into the model's context, and which module's hook made which decision. AD-23 requires both: per-module token attribution, carrying the soft-estimate label because context is shared, and a module name on every decision-log row.

Depends on #788 and #789. Traces to AD-23 and AD-12.

## Acceptance criteria

1. Given a session, when its context is assembled, then the ledger records the tokens each selected module contributed, labelled as a soft estimate with its method named (AD-12).
2. Given a hook decision (allow, deny, ask or injected context), when it is logged, then the decision-log row names the module that owns the hook.
3. Given one module switched off and everything else unchanged, when the same task is replayed, then only that module's attributed rows change, and the profile fingerprint differs.
4. Given the unit tests, then they cover every switch kind in the selection document.

## Design

### Approach

- One definition: `posture.context_attribution()` resolves the selection non-strict, from the
  ladder `profile()` reads, and gives every switched-on module and every stance with resident
  text an entry `kind/unit: tokens`, beside `estimand: "soft estimate"` and the `method` (AD-12).
- Resident text is what loads before the first prompt: a rule or a stance's selected variant
  whole; a skill, role or workflow its listing entry, `name: description`, since its body loads on
  demand. Tokens are characters over four, the approximation `harness lint` already uses.
- The usage ledger's session rows carry it as `context_attribution`, Claude Code and Codex alike,
  through `attributed()` in `usage-log.py`. A replay row carries its arm's, through
  `arm_attribution()` in `scripts/cost_bench.py`, with no module for the bare arm.
- Every decision-log row names `module`, the `hooks/<id>` owning its point, stamped in
  `decisions._append()` from `POINT_MODULES`, outcome and sampled-allow rows included.

### Decisions and alternatives

- **A field on the session row, not a row per module:** a new row kind would be summed by every
  reader that groups rows today. An entry per module in one map still changes alone when that
  module is switched off, which is what criterion 3 reads.
- **Resident text only:** a listed kind's body and a hook's per-event context depend on what the
  session does, which a SessionEnd read of the selection cannot see. Counting them would pass a
  guess off as an estimate; they stay out and the docs say so.
- **Point ownership follows the dispatch split #555 proposes:** Bash grading to `grade-bash`, and
  role confinement, framework and evasion refusals, the Workflow launch guard and the integration
  notice, all on the spawn path, to `tier-agent-spawns`. `decision-provider` rows come from no
  hook and name `null` rather than an invented owner.
- **A rescan never guesses:** it keeps the attribution the ledger holds for that session and
  otherwise leaves the field out, the rule the fingerprint follows.
- **Schema version 1 stays:** it is unreleased until v0.14.0 and ships with every field that
  release adds.

### Do not implement

- A soft-estimate report or `harness usage --by module` (AD-12 places the report in v0.15.0).
- Attribution on subagent, worker or provider rows; the session row is where context is assembled.
- Estimating a hook's injected context or a skill body loaded on demand.
- Switching hooks in the dispatcher (#555), the observation entry point (#791), adherence events
  (#792), or any change to `lib/harness_core/lifecycle.py`.
