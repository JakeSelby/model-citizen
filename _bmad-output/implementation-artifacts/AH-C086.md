## Goal

Open 0.14.0 as a release candidate so the native qualification round can run against it. The
catalog read 0.13.1 as released, and `citizen compatibility` reported that the current runtime
source differs from it; evidence is bound to the harness version, so the round needs an open
candidate (release surface 5 in `docs/releasing.md`).

## Acceptance criteria

1. **Given** `VERSION` and `compatibility/catalog.json`, **when** they are read, **then** both say
   0.14.0, `release_state` is `candidate`, no `qualification_source_commit` is pinned, and
   `claude-code-cli-macos` and `claude-code-cli-linux` stay required, read `unqualified`, link no
   evidence and pin runtime and client `2.1.280`; every limitation is unchanged, and
   `scripts/linux-target.Dockerfile` defaults `CLAUDE_CODE_VERSION` to `2.1.280`.
2. **Given** `citizen compatibility --release-check`, **when** it runs, **then** it blocks on the
   two unqualified required clients and nothing else.
3. **Given** `compatibility/migration.json`, **when** it is read, **then** it describes the upgrade
   from 0.13.1 from the `changelog.d/` fragments, and its recovery says to remove
   `~/.claude/rules/harness` before a rollback sync.
4. **Given** `README.md`, `docs/compatibility.md` and `docs/releasing.md`, **when** they are read,
   **then** each states 0.14.0 as a candidate and 0.13.1 as the current qualified release, and
   `tests/test_docs.py` and `tests/test_compatibility.py` pin that state.
5. **Given** `benchmarks/static.json`, **when** `cost_bench.py static --check` runs, **then** it
   passes for 0.14.0. The gate is green.

## Dev notes

Mirrors the 0.13.1 opening, `52bdee3` (#766), with one difference the issue asks for: the two
required clients keep `runtime_version` and `client_version`, now `2.1.280`, because the macOS
client and the rebuilt Linux image both run it; an unqualified row's versions are not validated.
`CODEX_VERSION` stays `0.155.1`. The compatibility blocks in `README.md` and
`docs/compatibility.md` are written by `citizen generate`. The changelog is not folded
(`release_notes.py --changelog` belongs to the release pull request) and `compatibility/evidence/`
is untouched. The concise-voice note in `docs/compatibility.md` called `2.1.278` "the pinned
Linux client"; it now says that version was pinned before 0.14.0.

`tests/test_release.py` pinned the literal `harness sync --dry-run` in the rendered notes; the
0.14.0 migration names the command `citizen`, so the pin now accepts either name.
