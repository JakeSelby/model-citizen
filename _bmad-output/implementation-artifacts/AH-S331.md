## Story

As a Codex user, I want Model Citizen's skills installable as a Codex plugin, so that I can use
them without a synced checkout and Codex plugin catalogs can list the project.

## Context and value

`.claude-plugin/plugin.json` already packages the skills for Claude Code. Two Codex catalogs,
hashgraph-online/awesome-codex-plugins and codex-marketplace.com, require a
`.codex-plugin/plugin.json` before they list a plugin, and OpenAI's own directory refuses plugins
with lifecycle hooks. Without a Codex manifest, Codex falls back to the Claude Code one at the
plugin root and reads fields meant for Claude Code.

## Acceptance criteria

1. **Given** the repository root as a Codex plugin root, **when** Codex resolves its manifest,
   **then** it reads `.codex-plugin/plugin.json` in OpenAI's compatibility manifest format.
2. **Given** that manifest, **then** it packages the skills under `primitives/skills/` and
   declares no hooks, agents, commands, MCP servers or apps.
3. **Given** the two manifests, **then** name, version, description, author, licence, homepage,
   repository and keywords are equal, and both versions equal `VERSION`.
4. **Given** a drift in any shared field, a version off `VERSION`, or a hook declaration, **when**
   the suite runs, **then** a test fails.
5. **Given** the pinned HOL plugin scanner, **when** it scans the repository, **then** the score and
   any critical or high finding are recorded on the pull request.
6. **Given** `product.json`, **then** a feature line names the Codex plugin install.

## Design

### Approach

A hand-written `.codex-plugin/plugin.json` carries the shared metadata verbatim, `skills:
"./primitives/skills/"`, and an `interface` block (display name, descriptions, developer,
category, capabilities, website, support and privacy URLs, default prompts, brand colour, and the existing
`.claude-plugin/icon.svg` as composer icon and logo). `tests/test_codex_plugin_manifest.py`
enforces the shared fields, the version and the skills-only shape. The release procedure names
both manifests in the version step.

### Decisions and alternatives

- **Compatibility manifest, not the portable root `plugin.json`:** the catalogs and the scanner
  key on `.codex-plugin/plugin.json`, and OpenAI documents it as a supported fallback. A root
  `plugin.json` with the Agent Plugins schema would outrank it in Codex; rejected for now.
- **The description is shared verbatim,** as the issue requires, though it names roles, commands
  and an output style that the Codex install leaves out; the `interface` descriptions say
  skills only.
- **No scanner config or `.codexignore` in this change:** the scanner's high findings are fake
  secrets in test fixtures and the sandbox skill's deny list for `~/.ssh`; suppressing them is a
  separate call.
- **Version kept in step by test, not by a bump script:** no release script bumps the Claude
  manifest; the release procedure edits it by hand, so the test ties both to `VERSION`.

### Do not implement

- Submitting to either catalog.
- A compatibility catalog client surface for the Codex plugin.
- Subagent roles, commands or the output style for Codex.

### Bound decisions and requirements

The Claude Code plugin ships no hooks because a synced home already registers them
(`tests/test_plugin_manifests.py`); the Codex manifest follows the same rule.

### Testing

`tests/test_codex_plugin_manifest.py` checks each shared field against the Claude Code manifest,
both versions against `VERSION`, the absence of hooks (top level, the OpenAI extension, and a
root `hooks/hooks.json` that Codex would load by default), the skills-only component set, that
interface paths and links resolve, and that the listing text fits the submission limits.

### Completion notes

Manifest format checked against OpenAI's packaging guide, its submission field reference and
Codex's manifest discovery order (`DISCOVERABLE_PLUGIN_MANIFEST_PATHS` in
`codex-rs/exec-server-protocol/src/capabilities.rs`), which reads `.codex-plugin/plugin.json`
before `.claude-plugin/plugin.json`. The pinned scanner (`plugin-scanner==3.12.2`, reviewed wheel
hash matched, run from a throwaway virtualenv) scored the repository 83/100 with no critical
findings and seven high ones, four distinct and all false positives: three placeholder secrets in
test fixtures, each reported once per ecosystem, and the sandbox skill's `denyRead` entry for
`~/.ssh`. The scanner now scores out of 100, not the 130 the catalog's guide still quotes. A
`.codexignore` changes none of the findings.
