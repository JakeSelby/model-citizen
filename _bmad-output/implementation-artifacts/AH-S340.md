## Story

As a harness maintainer, I want a replay arm built from a named stance selection beside bare and the shipped default, so that the configuration I actually run, and alternatives such as frugal cost tiering, are measured with the same parity guarantees as the default.

## Context and value

The shipped default is not the configuration the maintainer runs: the maintainer uses the concise voice in place of the default scannable one. #1191 also needs a frugal cost-tiering arm measured against the balanced default before that default is changed. Replay arms could already declare a selection into an image (ablation runs, the unit-economy grid), but a plain replay ran only bare and harness.

## Acceptance criteria

1. **Given** an arm config `{"schema": 1, "description": ..., "stances": {dimension: variant}}`, **when** it is loaded, **then** any other key, a wrong schema or a non-identifier value is refused with its reason.
2. **Given** a config naming a stance dimension or variant the tag does not ship, or one that is the tag's default throughout, **when** a replay names it, **then** it is refused before anything is planned, naming what exists.
3. **Given** a config, **then** its digest is the sha256 of its canonical JSON, unchanged by formatting or key order, and its selection is the arm's declared `selection` component.
4. **Given** a run with config arms, **when** it is admitted, **then** each config arm passes the bare pair parity check every harness arm passes, its declaration equals the harness arm's less its selection, and its profile differs from the harness arm's; a config arm holding anything more is refused before any launch.
5. **Given** a run with config arms, **then** every row records `arm_config`: null for bare and harness, and the name, schema, stances and digest for a config arm.
6. **Given** `replay --arm-config NAME=PATH` (repeatable) with `--dry-run`, **then** each config arm is listed with its digest and image name and scheduled beside bare and harness.
7. **Given** the change, **then** `benchmarks/arms/maintainer.json` (concise voice) and `benchmarks/arms/frugal.json` (frugal cost) ship and validate against the checkout.

## Design

### Approach

`scripts/replay_arms.py` gains the arm-config reader: `arm_config_problem` and `load_arm_config` check the shape, `arm_config_errors` checks each dimension and variant against the checkout's own stance primitives through its resolver with an empty home, `arm_config_selection` turns the stances into the user-config selection `declaration(selection=...)` already accepts, and `arm_config_stamp` is the row record. `scripts/cost_bench.py` parses `--arm-config`, validates each config against a clone of every tag before the plan is printed, adds the config names to the schedule, lists them in the dry run, builds one declared-selection image per config per tag, and passes them to `replay_tag`, which sets `arm_names`, `arm_configs` and the declared selections. `_replay` admits them with the existing per-arm and bare pair checks plus `admit_config_arms` (`ablations.admit_arms` with the harness arm as control) [Source: scripts/replay_arms.py#arm_config_errors; Source: scripts/cost_bench.py#arm_configs].

### Decisions and alternatives

- Reuse the declared-selection image path of ablation runs instead of passing the selection by value: the image then holds exactly what the sync rendered, and the existing parity check applies unchanged.
- Validate against the tag's own primitives, not this checkout's, since a variant can be added or removed between releases.
- Digest the config's canonical JSON rather than its file bytes, so reformatting never moves the digest; the image name already moves with the selection itself.
- Write no history row for a run with config arms, as for pairs and ablation runs: the history series is harness against bare.
- Refuse `--stance-cost`, `--pair`, `--ablations` and `--design` beside `--arm-config`: each would override or replace the declared arms.
- Restrict a config to stances. Switch kinds (rules, skills) stay the ablation manifest's job.

### Do not implement

- `summarise` reporting of the config arms; it is edited in another branch, so a config run's rows are written but not yet summarised.
- Any paid run, pre-registration, or the #1178 and #1193 wiring of the frugal arm.
