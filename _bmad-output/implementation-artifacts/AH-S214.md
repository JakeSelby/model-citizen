## Story

As the maintainer running a qualification round, I want the acceptance runner's disposable
`CODEX_HOME` to use the Codex session login when I ask for it, so that a Codex target can be driven by
`scripts/native_acceptance.py` rather than by hand.

## Context and value

The issue says #408 records that every Codex round so far used the ChatGPT-session login that
`codex login` writes to `~/.codex/auth.json`. `docs/compatibility.md` and
`docs/qualification-runbook.md` ("Before a run", step 2) describe that login at `origin/main`.

The runner's disposable home never receives that file. So the credential probe can prove the login
exists, but the runner cannot use it, and the Codex targets stay hand-qualified. The issue says the next
verification round needs this to script the Codex cases #336 committed.

At `origin/main`:

- `adapters/codex/worker.py` `prepare` symlinks `auth.json` from the caller's `CODEX_HOME`, or
  `~/.codex`, into each role worker's disposable Codex home;
- `scripts/native_acceptance.py` sets `CODEX_HOME` to the run's own client directory and passes through
  only the variables in `AUTH_PASSTHROUGH`, which are Anthropic and cloud settings. Nothing gives that
  home a Codex login;
- its Codex surface says "no round has been run through it", and keeps every verdict `unverified`
  until `--home-confirmed` records that an operator compared one against a hand run.

PR #651, which opened the 0.13.0 candidate, says `codex-cli-linux` "ships as a stated limitation until
#612 lets the acceptance runner drive it". The issue's own scope names the owner's Mac. [ASSUMPTION: the
two are compatible, since a scripted login serves both hosts; neither record says so.]

## Acceptance criteria

From the issue's "Done when" section:

1. **Given** an explicit flag, **when** the runner prepares its disposable `CODEX_HOME`, **then** the
   home has the session login, copied or pointed to.
2. **Given** no flag, **when** the runner prepares the home, **then** it receives no login.
3. **Given** any run, **when** records and logs are written, **then** none contains the credential.
4. **Given** the owner's Mac, **when** one Codex case runs end to end through the runner, **then** its
   observation is compared against the hand run, per the runbook.

## Design

### Approach

From the issue: give the disposable home a working login "the way `adapters/codex/worker.py` already
does for role workers", behind an explicit flag that is never on by default.

### Decisions and alternatives

- Opt-in only: the issue requires "an explicit flag, never by default".
- Copy or point: the issue allows either, and the runner points, with a symlink, as the worker
  adapter does. A kept home (`--keep-home`) then holds no credential of its own, and a token the
  client refreshes lands in the operator's one login file rather than forking it. The alternative,
  a copy, would keep the client from ever writing to the operator's file, at the cost of a second
  credential on disk for a kept home and a refresh-token fork that can leave the operator's login
  stale.
- Flag name and source: `--codex-session-login` reads the login from the caller's `CODEX_HOME`, else
  `~/.codex`, before the disposable home replaces either, matching `adapters/codex/worker.py`.
- Fail closed: the flag is refused before any case runs for a Claude Code target, which passes its
  credential by name, and when no `auth.json` exists.
- Redaction: every string of eight or more characters in the login file is removed literally from
  each observation, ahead of the path and shape rules, because a token need not match any shape in
  `SECRET_SHAPES`. The progress log and the record are built only from those observations.

### Do not implement

- Any default that exposes the login without the flag (AC 2).
- Writing the credential into a record or log (AC 3).

**Hand comparison, 2026-09-26 (AC 4).** The same case run by hand in a disposable home, with
`--model gpt-6-luna`, agreed on four of five readings: `sync complete`, `drift: none`, the rendered
identity and `YES` for the spike-contract skill. It disagreed on roles: asked the case's own roles
prompt, Codex 0.155.0 listed all eleven harness roles plus its own `default` and `explorer`, while
the runner never asks because `native_only()` assumes Codex keeps no role list. A
`--home-confirmed codex-cli-macos` rerun still read `unverified` with the same observation, so no
Codex verdict is recorded as passed. The role-list gap is #923.

## Review findings

CodeRabbit, round 1 on PR #842:

- Major: the login's values were read once, before the case, so a token the client refreshed
  mid-case could reach an observation unredacted. Fixed: each observation re-reads the operator's
  login file and the home's own `auth.json`, in case the client replaced the link, and redacts
  both; two regression tests cover a write through the link and a file written over it.
- Minor: `--from-progress --codex-session-login` exited when no login file existed, though a
  rebuild runs no case. Fixed: the login is checked only when cases will run; the progress-log
  test now rebuilds its record with the login removed.

CodeRabbit, round 2 on PR #842:

- Minor: validate the Codex target even under `--from-progress`, and let `--dry-plan` run without a
  login file. Answered, not changed: a rebuild runs no case, so the flag has nothing to link on any
  client, and the dry plan previews a run that would fail, so refusing a missing login before any
  case is the intended behaviour.
