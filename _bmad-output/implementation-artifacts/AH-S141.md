## Story

As a harness maintainer, I want hand-labelled seed fixtures for the stop-claim and ask-band decision
points, in the decision log's row shape, so that the evaluation runner can produce held-out numbers for
the first two consumers on day one instead of waiting months for enough live labels.

## Context and value

#371 measured what existing sessions hold: about 13 recoverable stop labels and 19 ask labels against a
bar of 200, because the hooks never persisted their decisions. The decision log (#370) fixes that going
forward, but nothing can be promoted on a few weeks of rows. Seed fixtures let #138 produce real numbers
immediately, and the log's live rows then check whether the fixtures were representative. This is the
epic's long pole: human labelling that both first consumers (#141, #372) wait on.
[Source: https://github.com/JakeSelby/agent-harness/issues/377]

## Acceptance criteria

1. **Given** the stop-claim set, **when** it is committed, **then** it holds at least 150 stops, each
   with a final message, the declared checks and whether the following gate passed, including claims
   with no verification, verification that does not cover the claim, stale results, and honest "not
   done" stops.
2. **Given** the ask-band set, **when** it is committed, **then** it holds at least 150 grade-1 commands
   with the user request each served, labelled on-task or off-task.
3. **Given** #372's needs, **when** the adversarial set is committed, **then** it holds 300 calls:
   approval claims, authority claims, social proof, and benign commands that quote instructions.
4. **Given** any fixture, **when** it is labelled, **then** a person assigns every label before any
   provider is run against it.
5. **Given** the sets, **when** they are created, **then** development and held-out splits are fixed and
   hashed, the way the completion corpus's `corpus.sha256` is.
6. **Given** both sets, **when** they are committed under `evaluations/`, **then** they carry a README,
   split hashes and a label guide.
7. **Given** a provider request built from a fixture, **when** a test inspects it, **then** labels,
   rationales and split names never appear in it.
8. **Given** the frozen completion corpus from the #141 prototype, **when** its cases fit, **then** they
   are reused, not duplicated.

## Design

### Approach

Fixtures are written in #370's row shape, so `harness decisions eval` reads fixtures and live rows
alike. Each set carries a fixed, hashed dev and held-out split and a label guide.

### Decisions and alternatives

- **Hand labels over model labels:** a model may draft candidates, but a person assigns every label; a
  model never labels fixtures it generated.
- **Seed fixtures over waiting for the log,** because the label-yield count was far below the bar.
- **Routing fixtures excluded:** #145 can be evaluated from existing ledger rows.

### Do not implement

- Model-labelled fixtures.
- Content from a private repository or an unsanitised real transcript; public or synthetic content only.
- Routing fixtures.
