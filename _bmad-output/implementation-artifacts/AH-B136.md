# AH-B136 — Studio draft lookup fails when another session removes a worktree mid-scan

## Reproduction

Run any Studio test that calls `drafts.find` or `drafts.list_drafts` on the shared repository while another session removes one of its worktrees. Observed 2026-09-29: `tests/test_studio_selection_editing_browser.py` `test_core_refusal_writes_nothing_then_acknowledged_change_checkpoints` failed at `drafts.find(...)` with `DraftError: fatal: not a git repository`, then passed on rerun.

## Root cause

`_registered_worktrees` filters prunable entries and missing directories when it lists them, but `find` and `list_drafts` then run `git rev-parse --git-dir` in each worktree through `_paths` and `_admin_dir`. A worktree removed between the listing and that call makes `_git` raise `git-failed`, which aborts the scan for every draft. [Source: lib/harness_core/studio/drafts.py#find]

## Acceptance criteria

1. **Given** a registered worktree that vanishes after listing, **when** `find` looks up an unrelated draft, **then** it returns that draft.
2. **Given** the same vanished worktree, **when** `list_drafts` runs, **then** it lists the real drafts.
3. **Given** a worktree that still exists but whose git call fails, **when** `find` scans it, **then** the `git-failed` error still raises.

## Design

A `_draft_worktrees` scan wraps the state lookup and skips a worktree only when its `.git` entry is gone after the failure; `find` applies the same check to `_read_state` and `list_drafts` to `describe`. Any other failure re-raises, so a broken but present worktree stays visible. Retrying the listing was rejected: it narrows the window without closing it.

## Regression test

`tests/test_drafts.py`: `test_worktree_removed_after_listing_does_not_break_draft_lookup` yields a vanished path ahead of the real worktrees and fails with `git-failed` before the fix; `test_git_failure_in_a_present_worktree_still_raises_during_lookup` pins criterion 3.
