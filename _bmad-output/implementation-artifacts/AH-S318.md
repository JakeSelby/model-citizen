## Story

As a maintainer, I want the Studio qualified in every release like the CLI, so that its claims match its evidence.

## Context and value

The Studio ships under the same qualification as the CLI: a lifecycle case that starts `citizen studio`, loads the UI, proves the loopback-only bind and the token and host refusals, and stops it cleanly; the committed bundle checked against its source in the release preflight; and the Studio listed in the compatibility matrix with its supported browsers and platforms.

## Acceptance criteria

1. Given a release candidate, then the Studio's lifecycle case passes on macOS and Linux, and a failure blocks the round.
2. Given a bundle that does not match its source, then `scripts/release_preflight.py` fails.
3. Given `docs/compatibility.md`, then it lists the Studio's supported browsers and platforms with their evidence.

## Design

### Approach

Put one host-native Studio acceptance command in the release path. It launches the committed
bundle through `citizen studio`, exercises the launcher-only HTTP boundary and clean shutdown,
then runs the rendered Chrome flows. The qualification round's existing smoke gate runs it before
paid targets. A two-platform workflow exercises the same command on macOS and Linux, while release
preflight requires exact-source platform records and independently rebuilds the committed bundle.

### Decisions and alternatives

- Keep Studio qualification separate from agent-client rows: the browser is not an agent runtime.
- Support Chrome current stable on macOS and Linux first because those tuples have executable flows;
  Safari and Firefox remain explicitly unqualified rather than inheriting support from build output.
- Reuse the round's fail-closed smoke gate instead of adding a second round coordinator.
- Rebuild from source in release preflight; a manifest of the committed bundle alone cannot detect
  stale generated output.

### Do not implement

Safari, Firefox, native Windows, separate-phone reach, UI changes, and native agent-client cases.

## Review findings

- Provisioned the exact Node/npm pins in the tag release job before bundle reconstruction.
- Made release evidence reject malformed, failed, skipped, duplicate and unknown cases.
- Restricted discovery and evidence to Google Chrome at the matrix's pinned stable major, which is
  advanced deliberately with release evidence rather than inferred from a plausible version string.
- Moved cleanup around all post-launch parsing and added PID fallback for malformed state.
- Required non-zero discovery and every named browser-flow case before recording a pass.
- The first cross-platform run exposed hosted-runner startup races: macOS could take more than five
  seconds to schedule the detached interpreter, and Linux exposed DevToolsActivePort before the
  endpoint accepted a target. Startup now has bounded 15/20-second budgets and DevTools target
  creation retries within a bounded window.
- The next run showed macOS can exceed 15 seconds under hosted load, while the Linux fixture lacked
  the Git identity required to checkpoint its draft. Startup now validates the server's authenticated
  readiness without a redundant process probe and uses bounded 30/45-second budgets. Browser tests
  carry a fixture-only Git identity and disable background throttling.
- The following run isolated two remaining fixture boundaries: Chrome can need more than five
  seconds to publish DevToolsActivePort on Linux, and opaque detached stderr hid the macOS child
  failure. Qualification now waits up to 20 seconds for Chrome, reuses the server's recorded process
  token for health, and reports at most 4 KiB of private startup diagnostics on failure.
- Ubuntu then passed the complete qualification. Both macOS runner architectures left Python's
  `start_new_session` child alive before exec. Darwin detach now uses `/usr/bin/nohup` without that
  fork path, then the exec'd child creates its own session and closes inherited non-standard file
  descriptors before opening Studio state or sockets.
- The subsequent run showed macOS reached the child but stalled when its first `ps` probe re-entered
  the same fork path. macOS Studio now pairs PID liveness with a private per-instance handshake token
  and never spawns `ps`; Linux keeps the OS start-time check. Chrome readiness also requires a valid
  port line rather than treating a partially written DevToolsActivePort file as complete.
- The next macOS run exposed a second pre-publication stall: its descriptor ceiling exceeded one
  million, and closing every possible descriptor could not finish inside the startup budget. The
  detached child now closes only descriptors actually present in `/dev/fd` before serving; it
  tolerates only the expected already-closed enumeration race and fails closed on other errors.
- Because the hosted macOS child still failed before publishing state after that bound, the
  qualification fixture enables credential-free startup stage breadcrumbs that remain captured
  unless launch fails. The normal Studio launch path emits none.
- Those breadcrumbs isolated the remaining stall to `HTTPServer.server_bind`, whose default
  implementation performs an unnecessary FQDN lookup after binding the literal loopback address.
  Studio now uses the underlying TCP bind directly and assigns the unused display name locally.
- The first complete hosted macOS lifecycle then reached the browser gate and proved its stable
  channel was still major 152 while Linux had rolled to 153. The compatibility tuples now pin the
  independently deployed stable majors instead of assuming both runner images advance together.
