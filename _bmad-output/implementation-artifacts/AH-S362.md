## Story

As a developer, I want the Touch ID or password dialog that guards a spend or an apply to say it comes from Model Citizen, so I know what is asking and why before I approve it.

## Context and value

#1271 asks for the Mac owner's presence through LocalAuthentication, called from `osascript`. macOS names the requesting program in the dialog, so it reads "osascript" today, which tells a person nothing. The reason line is ours and now names the app and the action; the app name and icon come from the calling process and need a small helper application named Model Citizen.

## Acceptance criteria

1. Given a spend or apply from the CLI or the Studio, when the presence dialog opens, then it names Model Citizen (or Model Citizen Studio) as the requester, with its icon, and the reason line says what will happen and why.
2. The helper is built and ad-hoc signed locally at install or first use from source in this repository, with no prebuilt binary checked in; where the developer tools are missing, presence falls back to the current `osascript` path with no loss of the check.
3. The helper cannot be made to answer yes without the person: it only relays LocalAuthentication's result, and the bypass scan from #1271 covers it.
4. Tests cover the fallback, the relay of a refusal, and the reason text; a manual check script proves the named dialog on a Mac.

## Design

### Approach

Two parts. Every caller passes `presence.confirm` a requester, an action and a purpose (`presence.Reason`). The helper's dialog, which macOS titles with the app's name, is given the verb phrase "<action>, so <purpose>"; the `osascript` fallback, titled "osascript", is given "<Model Citizen | Model Citizen Studio> wants to <action>, so <purpose>.". Both fit `REASON_LIMIT`, shortening only the action. A refusal reads "<requester> did not <action>: it needs a person's confirmation ...". The second part is a Swift app bundle named Model Citizen (`lib/harness_core/presence_app/`) that `presence.confirm` runs in place of `osascript`, so macOS names it and shows its icon.

### Decisions and alternatives

- The requester is the Studio when the request came through the Studio server (its HTTP route, or a `citizen draft` child it ran with `--via-studio`) and plain Model Citizen from the CLI, including `citizen runs GROUP start`, whose handler face is `citizen`.
- Each spend names the cap, suite, case count, targets, estimate, spend cap and pricing; a replay with a draft target says it measures whether that draft helped. An apply names the draft and revision; a rollback names the apply, draft, revision and how many settings and files it restores; recover and an apply over an interrupted change name the undo or the abandon that will actually run.
- Built at first use, not shipped: `presence_helper.build` compiles `main.swift` with `swiftc`, embeds `Info.plist` in the binary and the bundle, draws a plain icon in Python (no image asset is checked in), ad-hoc signs the bundle and records its CDHash with a digest of the source.
- Verified before each use: `codesign --verify --strict` and the CDHash against the record; a mismatch, a changed source or a missing record rebuilds, and a failed rebuild falls back to `osascript`.
- The helper's directory is the account's home from the password database, keyed by the source digest so checkouts with different source keep their own, and the tools run with a fixed environment, so `HOME`, `HARNESS_HOME`, `DEVELOPER_DIR`, `SDKROOT` or `PATH` do not move it. That is not a boundary: same-user code can still steer the compile through the `swiftc` shim's user-writable caches, or replace the helper and its record, as part of the same-user limit.
- Verify and run under a shared file lock, build under an exclusive one, so no check runs a helper another process is replacing; the record is written through a temporary file of its own.
- A failed build is remembered with the toolchain's fingerprint and a timestamp and not retried for a day, or until the toolchain or source changes; `swiftc` is capped at 120 seconds.
- Each confirmation row names the program that answered and the helper's signature hash, in its detail and in the words Activity shows, since a planted helper lives outside git.
- A helper's decline, timeout or unavailable answer is a refusal; the check never asks again another way.
- Conservative default taken where the story was open: the helper is built at first use only, not by `install` or `sync`, so an install never needs the developer tools.

### Do not implement

- A prebuilt or notarized binary, or a Developer ID signature.
- Any change to what counts as a person's yes.

### Completion notes

- `presence.check(requester, action, purpose)` answers whether the owner authenticated, which program asked (`helper`, `osascript`, or `none` where presence cannot be checked) and the helper's signature hash; `confirm` is its answer alone, and `record` reads the rest from the same thread. Only a `present` answer with exit 0 passes, from either program.
- `presence_helper.ready()` yields the verified helper under its lock, or None; preparing it never raises, so any failure falls back.
- The bypass scan in `tests/test_cli_confirmation.py` now reads `.swift` files and asserts the helper's source is among those it read; `tests/test_presence_helper.py` checks that `present` and exit 0 come only from the policy's success reply and that the source reads no environment, file or defaults.
- `scripts/presence_check.py` prints which program asked, so the named dialog can be checked by hand on a Mac.

## Review findings

- Round 1, doubled wording if macOS titles the dialog "<app> is trying to": the helper gets a verb phrase, `osascript` the whole sentence; both tested.
- Round 1, refusal read as broken: built from the action; tested.
- Round 1, a planted helper is invisible to git: each confirmation row names the program and the helper's hash; docs softened.
- Round 1, build race and shared temporary name: file lock around build, verify and run, a unique temporary record, digest-keyed directories; two-builder test.
- Round 1, failed builds retried on every check: remembered for a day per toolchain; compile capped at 120 seconds.
- Round 1, toolchain claim overstated: restated as part of the same-user limit.
