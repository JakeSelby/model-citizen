# AH-B087 — An isolated worker launched from a token-only Claude Code session cannot authenticate

## Reproduction

1. Start Claude Code 2.1.280 with `CLAUDE_CODE_OAUTH_TOKEN` exported and no stored login (no
   keychain item, no `.claude/.credentials.json`).
2. From the session's Bash tool, run `harness role run reviewer --runtime claude-code --prompt-file brief.md`.
3. Observed: the worker launches and fails with "Not logged in · Please run /login"; the run
   record ends `failed` with only a non-zero exit to show for it. Seen in the 0.13.0 BMad
   integration suite. The same command from a keychain-logged-in session authenticates.

## Root cause

Claude Code strips `CLAUDE_CODE_OAUTH_TOKEN` from the environment of its tool subprocesses (it is
absent from `env` inside a Bash tool call, while `CLAUDECODE=1` is present). `workers.environment`
forwards the token when the caller has it, and the Claude adapter keeps the real `HOME` and `USER`
so a stored keychain or file login is found; a token-only session has neither, so the worker's
client has no credential and fails at its first request.
[Source: lib/harness_core/workers.py#environment] [Source: adapters/claude-code/worker.py#prepare]

## Acceptance criteria

1. **Given** a process inside a Claude Code session (`CLAUDECODE` set) whose worker environment
   carries no credential and no stored login, **when** `harness role run` targets `claude-code`,
   **then** it exits 1 before launching, with a message naming `CLAUDE_CODE_OAUTH_TOKEN` and the
   two fixes, and writes no worker record or state directory.
2. **Given** the same session with a stored login, or with the token exported, **when** the
   worker runs, **then** it launches as before.
3. **Given** a check that cannot run or cannot be parsed, **then** the run is refused (fails closed).
4. **Given** a process outside a session, a cloud provider flag, or the Codex runtime, **then** no
   check runs and behaviour is unchanged.
5. The token is never written to disk or a log, and the check's output (which names the account)
   is parsed for `loggedIn` only and never printed or kept.

## Design

The Claude adapter gains `refusal(executable, original, env, cwd)`, which `workers.run` calls right
after the client's `--version`, before the state directory or record exists. Inside a session it
runs the client's own `claude auth status --json` under the worker's credential set
(`workers.passthrough`, factored out of `environment`) plus the operator's `HOME`, `USER` and
`CLAUDE_CONFIG_DIR` (`identity`, now shared with `prepare`), and refuses unless it exits 0 with
`loggedIn: true`. `auth status` reports an exported token, an API key and a stored login alike,
and returned `loggedIn: false`, exit 1, under a home with an empty keychain on 2.1.280.

Default taken: refuse up front with a message naming the missing token; no token plumbing, because
this is a credential path and it fails closed.

Rejected: carrying the token to the worker through a file or the keychain (writes a credential);
probing the keychain for `Claude Code-credentials` directly (the service name varies with
`CLAUDE_CONFIG_DIR`, and a stored file login would be missed); checking outside sessions too
(adds a client launch to every run and changes every existing worker test for a path this issue
does not report). Must not change: the worker's environment, command line or authentication
when a login is present.

## Regression test

`tests/test_worker_token_only_session.py`: `CommandTests` drives `harness role run` end to end
with a stand-in `claude` on `PATH` that reports `loggedIn: false` without the token; before the
fix the stand-in was launched and the run failed late, after the fix it exits 1 with the message
and no state. `RefusalTests` covers criteria 2 to 5 through `workers.run`.

## Review findings

CodeRabbit, round 1 on PR #848:

- `adapters/claude-code/worker.py`: the preflight inherited the caller's working directory, so a
  project's settings could confirm a login the worker, launched from an empty directory with
  `--setting-sources ""`, never sees. Fixed: `workers.run` passes an empty temporary directory
  as the check's `cwd`, with a regression test.
- `tests/test_worker_token_only_session.py`: the exported-token test ignored the exit code, and
  the stand-in client failed its launch, so the test passed on a failed run. Fixed: the stand-in
  returns a success envelope and the test asserts exit 0.

CodeRabbit, round 2 on PR #848, review body only (no inline threads):

- Nitpick: the tests use a stand-in `claude` and mocked status answers, so the issue's native
  in-session acceptance item is not covered. Answered in a PR comment: that item moved to #857.
