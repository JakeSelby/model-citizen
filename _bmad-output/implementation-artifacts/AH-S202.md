## Story

As the harness maintainer, I want the replay runner to build each arm as a profile and refuse a pair
that differs by anything but the variable under test, so that a four-arm comparison measures the
harness and the library rather than drift in the profiles.

## Context and value

Epic #552 measures the `superpowers` mode against superpowers alone, which needs four arms rather than
two [Source: #552]. Two earlier issues feed this one. #482 recorded a 1,700-token drift in the harness arm's standing
prefix between two runs on the same profile, caught by the transcript's `init` event and invisible to the
size-hash fingerprint [Source: #482]. #428 recorded that the harness arm charged the user's personal layer to the
harness [Source: #428]. This issue folds #482 and closes #428.

On `main`, `ARMS` in `scripts/cost_bench.py` is `("bare", "harness")`. The harness arm uses the profile
`--harness-config` names, or with none named inherits the live home through `HOME`. There is no plugin
parity check, no `--arms` and no `--allow-plugin-drift`.
[Source: https://github.com/JakeSelby/agent-harness/issues/559]

## Acceptance criteria

1. **Given** four arms and the release task set, **when** `replay --dry-run` runs, **then** it prints a
   32-run schedule with the lead arm rotating across the four.
2. **Given** a fake launcher and fake plugin-list output, **when** the unit tests run, **then** they
   cover profile build, parity refusal, the drift stamp, rotation and the per-arm summary.
3. **Given** a finished set, **when** it is summarised, **then** it reports per-arm cost per passed task
   and passes, and a history row carries one entry per arm as a ratio to bare plus
   `harness_superpowers_over_superpowers`.
4. **Given** #482's acceptance list, **when** it is checked, **then** it passes as written; #428 closes
   because the harness arm no longer reads the real home.
5. **Given** the docs, **when** `docs/benchmarks.md` is read, **then** it describes the four arms and the
   parity rule.

## Design

### Decided by the owner on 2026-09-26

Decided by the owner on 2026-09-26, in comments on #559 and in #1010: the replay arms become fresh
Docker containers rather than profile directories.

1. Both arms are built from the Linux qualification image (`scripts/linux-target.Dockerfile`: its
   pinned base digest, `CLAUDE_CODE_VERSION` as a build argument) and authenticate with
   `CLAUDE_CODE_OAUTH_TOKEN` passed by name, as the Linux qualification target does.
2. The bare arm's image carries no harness. The harness arm's image carries the harness installed
   from a named git ref (a release tag, or a full commit for a pre-release candidate), so nothing
   from the host profile (the personal layer, #428; a workspace block; stray hooks) reaches either.
3. Every replay row records the image digest and the harness ref and commit.
4. #1010's protocol governs the design: fresh containers from pinned inputs; nothing from the host
   (no host HOME, profile, environment, hooks or settings); network egress only to the model API;
   each arm declares its components and its build writes a hashed manifest of every installed
   file, plugin, hook, rule and setting; rebuilding an arm from its recorded inputs yields the same
   manifest.
5. A macOS VM arm stays on v0.15.0 and is out of scope.

This supersedes the profile-directory design this file carried before, including its recorded
contradiction about how a built profile authenticates: a container authenticates with the token.

### Scope of this pull request (the orchestrator's scoping)

Delivered here: the container arms `bare` and `harness@<ref>` replacing the host-profile arms, and
removal of the live-profile fallback and the host-profile flags, which closes #428; the arm
declaration and the build-time manifest as JSON beside each image; image and manifest digests on
every row; the two-build check as a command with a dry run; runs as `docker run --rm` with the
snapshot as the only mount, the credential by name and egress limited to the model API; scoring in
a fresh container; the replay's other semantics kept (schedule, lead-arm alternation, caps,
pre-flight, scoring rules, history row).

Not here:

- The refusal of an arm whose manifest differs from its declaration, the pre-registration gate and
  the protocol docs: #1010, built next on this branch. Its seam is `replay_arms.ADMISSION_CHECKS`,
  run by `replay_arms.admit(record)`, which `cost_bench.replay` calls once per arm before any
  launch; `replay_arms.declaration` and `build_arm(...)["manifest"]` return the two as dicts.
- The four-arm superpowers parity in the issue body (`superpowers`, `harness-superpowers`, pair
  parity, `--allow-plugin-drift`): blocked by #558, which is on v0.16.0. A follow-up carries it.
- #482's loaded-surface record and effort pin (v0.15.0), and any change to
  `benchmarks/history.jsonl` or the task set.

### Approach

- `scripts/replay-arm.Dockerfile` has two stages. `bare` is the base plus Claude Code at the pinned
  version, with the base template's own Codex client uninstalled. `harness` copies a clone of the declared commit to `/opt/model-citizen`, checks the
  commit, runs `bin/harness sync` with no configuration and trusts `/work`, with no bytecode
  written. The runner reads the base digest and version out of `scripts/linux-target.Dockerfile`,
  which is unchanged.
- `scripts/replay_arms.py` declares an arm (components with versions, the Dockerfile's and the
  lister's hashes), names its image `model-citizen-arm-<arm>:<declaration digest>`, builds it from
  a context directory made for the build, lists it with `scripts/arm_manifest.py` piped into a
  container with no network and no mount, and writes `<image>.declaration.json` and
  `<image>.manifest.json`. `two_build_check` builds twice with `--no-cache` and compares entry by
  entry.
- The manifest lists the image user's home, `/etc/claude-code` and the harness checkout: files by
  mode, size and sha256, links by target, directories by mode, never a timestamp. Excluded, by an
  explicit list the manifest carries: `.npm`, `.cache` and the checkout's `.git`. Normalised: the
  sync's `synced_at`.
- A run is `docker run --rm --network <internal> --security-opt no-new-privileges --cap-drop ALL
  -v <snapshot>:/work -w /work -e CLAUDE_CODE_OAUTH_TOKEN -e <fixed variables> <image> claude -p
  ...`. Egress is an internal network plus `scripts/egress_proxy.py`, a standard-library CONNECT
  proxy run from the bare image and also joined to the bridge, allowing `api.anthropic.com:443`.
- The held-back check runs in a fresh bare container with the snapshot mounted, no network and no
  credential; an oracle is sent on stdin.

### Review fixes (CodeRabbit, first pass on #1020)

- The egress proxy no longer binds every interface. It binds the address its hostname resolves to
  while the internal network is the only one it is on, refuses to start on a loopback or empty
  answer, and the runner joins it to the bridge only after its log reports that address.
- Every check and gate container is named, and one that reaches `CHECK_TIMEOUT` is removed by name,
  as a run's is, so no container keeps running agent-written code after its client is killed.
- Snapshots are made writable for any user, since the image user's id can differ from the host
  user's; the images add `/work` to git's `safe.directory`; and before anything is measured each
  arm's container must write a mounted snapshot and have git read it, or the replay is refused
  with the reason.

### Decisions and alternatives

- **Default taken:** the container is the fence, so both arms run with
  `--permission-mode bypassPermissions` and settings that only deny the web tools. The command
  sandbox the profile arms used needs a namespace tool a container does not offer, and a headless
  run cannot answer a prompt.
- **Default taken:** the egress allowlist is `api.anthropic.com` alone, the model API in Claude
  Code's network requirements; sign-in hosts are left out because an arm uses a token.
- **Default taken:** `--tag` is required and `candidate` is refused, because the installed harness
  is a host profile; a pre-release is named by its full commit.
- **Scope addition from the orchestrator (2026-09-26):** `--verify-tasks`, each task's gate and
  every check run in a fresh bare container too. On the host they ran with a scrubbed environment
  that still carried the real HOME, so an older snapshot's code read the owner's live
  configuration: the orchestrator found all seven tasks' gates red at their parent sha on `main`,
  reproduced on `link-alias` as five errors, each `ValueError: stance 'voice' has no variant
  'concise'`. `--verify-tasks` builds the bare arm first unless `--check-image` names one, and a
  regression test shows the gate's container carries no host HOME.
- **Default taken:** the per-rule `profile_fingerprint` and `context_attribution` are resolved over
  a clone of the arm's commit with an empty home, standing in for the image's; the manifest digest
  is the complete record.
- **Default taken:** the arms uninstall the Codex client the base template ships, and the manifest
  lists every global npm package (`cli_packages`). With it on the path, four of the seven tasks'
  parent-sha suites failed in the container on one test that expects no Codex client, and an arm
  would carry an agent client it does not declare.
- **Default taken:** a run's series hash gains `|container`, so container rows never compare with
  profile rows.
- The harness arm's image holds the harness checkout at its ref, which may postdate a task. The
  profile arms had the same exposure (the pinned checkout was admitted for reading); it is recorded
  here and in `docs/benchmarks.md` rather than changed.

### Do not implement

- The live set itself (#560).
- Any change to the publish threshold.
