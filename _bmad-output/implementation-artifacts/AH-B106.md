# AH-B106 — Read-only grammar mis-tokenizes a closing parenthesis followed directly by a separator

## Reproduction

Pass a Bash line to the read-only grammar in which a subshell's closing parenthesis is followed directly by a separator. For example `(true); touch x`: `command_ok` in `policy/hooks/allow-readonly-bash.py` returns true, and `grade-bash` grades the line 0. The same line written `(true) ; touch x` is rejected by `command_ok` and graded 1, as it should be. Other separators (`&&`, `||`, `|`, `&`) and a closing brace are expected to behave the same way; the regression test establishes which do.

## Root cause

Both hooks tokenized with `shlex.shlex(..., posix=True, punctuation_chars=True)`: `command_ok` in `policy/hooks/allow-readonly-bash.py` (line 639 before the fix) and `segments` in `policy/hooks/grade-bash.py` (line 392 before the fix). With `punctuation_chars`, `shlex` returns a maximal unquoted run of the characters `();<>|&` as one token without splitting it into shell operators, so `(true);` yields the token `);`. That token is not in `ALWAYS_DELIM`, so it did not end the segment: it and every word after it became arguments of `true`, and the segment was judged read-only by its first word. `grade-bash` first asks `command_ok` and then splits with the same tokenization, so it graded the line 0.

The regression sweep shows which spellings were affected: every separator directly after `)`. A closing brace was not affected, because `}` is a word character to `shlex` and a following `;` or `|` already ended the word. The same run-merging also joined a separator directly before an opening parenthesis (`true;(touch x)` gave `;(`) and a redirect directly after a closing parenthesis (`(ls)>out.txt` gave `)>`, so the write was not seen by `strip_redirects`).

## Acceptance criteria

1. **Given** a line where `)` or `}` is followed directly by `;`, `&&`, `||`, `|` or `&`, **when** the read-only grammar judges it, **then** the verdict equals the verdict for the same line with a space before the separator.
2. **Given** the same lines, **when** `grade-bash` grades them, **then** the grade equals the spaced form's grade, so a command after the separator is graded on its own.
3. **Given** a genuinely read-only line in either spacing, such as `(git status);ls`, **then** it is still approved.
4. **Given** the sweep, **then** a test covers every separator in both spacings, each with a read-only and a non-read-only command after it.

## Design

Fix the tokenization at its source, so that a closing parenthesis or brace always ends a token and a separator immediately after it is recognized, whatever the spacing. Both hooks then inherit the fix through `command_ok`, with no special case in `grade-bash`.

Rejected: normalizing spacing with a regex before parsing. It would fix this spelling and leave the tokenizer wrong for the next one.

Must not change: the verdict or grade of any line that already parsed correctly with spaces, or the approval of genuinely read-only compound lines.

## Regression test

`tests/test_readonly_operator_spacing.py`. `SeparatorSweepTests` crosses `)` and `}` with `;`, `&&`, `||`, `|` and `&`, in the spaced form and two unspaced forms, each with a read-only (`ls`, `git status`) and a non-read-only (`touch x`, `git push origin HEAD`) command after it, and asserts identical `command_ok` verdicts and identical `grade-bash` grades across spellings. Against the previous grammar ten `)` cases differ, `(true); touch x` among them. `AdjacentOperatorTests` covers an opening parenthesis after a separator, a redirect after `)`, nested closers and genuinely read-only compound lines; `TokenizeTests` covers operator splitting, quoted and escaped operator characters, error parity, and a seeded differential sweep against `shlex` wherever `shlex` returns no multi-operator run. The tests only pass strings to the parser.

## Dev notes

- `tokenize(cmd)` in `policy/hooks/allow-readonly-bash.py` reproduces POSIX `shlex` word handling (single quotes, double quotes escaping only `"` and `\`, backslash outside quotes, `ValueError` on an unclosed quote or trailing backslash) and differs only in splitting an unquoted run of `();<>|&` into operators. The seeded differential test pins the parity.
- A quoted or escaped operator character stays part of a word, as `shlex` left it, so no quoted-data verdict changes. Splitting at the token level after `shlex` was rejected because it cannot tell `');'` from `);` and would split quoted data.
- `;&` and `;;&` are not in the operator table; they split into delimiters and fail closed.
- `grade-bash` reaches the tokenizer through its existing `ro` sibling module; its own `shlex` import is gone.
- A closing quote or a redirect target directly before a separator (`echo 'a';touch x`, `ls >/dev/null;touch x`) already tokenized correctly and needed nothing.
- Not changed, noted for follow-up: `grade-bash` grades a redirect attached to a subshell (`(ls) > f`) 0 in either spacing, because `grade_tokens` returns 0 for a segment that is only a redirect. `command_ok` rejects it.
