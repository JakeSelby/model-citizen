## Story

As a developer who has chosen a stance for each concern, I want a report of how each stance actually
behaves against what I declared, with a proposed promotion or demotion when the evidence passes a
threshold, so that I change a stance on measured evidence and the system never changes it for me.

## Context and value

FR-50, evidence-driven stance proposals, is planned for v0.15.0 under #135. No child issue covered it,
and the readiness report recorded it as a requirement with no open story (AH-E003)
([#692](https://github.com/JakeSelby/agent-harness/issues/692);
[Source: _bmad-output/implementation-artifacts/AH-E003.md];
[Source: _bmad-output/planning-artifacts/implementation-readiness-2026-09-23.md#Traceability]).
The issue is on the v0.15.0 milestone.

FR-50 reads: "The system must compare each declared stance with its measured behaviour and report the
drift. When the evidence passes a variant's threshold, it must propose a promotion or a demotion. The
developer applies a proposal; the system never applies one itself."
[Source: _bmad-output/planning-artifacts/prds/prd-agent-harness-2026-09-23/prd.md#FR-50: Evidence-driven stance proposals]

**What exists at HEAD.**
- The decision log, `decisions.jsonl`, records one row per judgment at five points: `grade-bash`,
  `stop-gate`, `tier-agent-spawns`, `brief-guard` and `evasion-deny`. An outcome is a second row joined
  by `decision_id` [Source: policy/hooks/decisions.py].
- `harness usage --by stance` groups usage-ledger sessions by the stances recorded on each row, and
  excludes rescanned sessions whose stance is not known
  [Source: bin/harness#rule_report].
- The nearest existing proposal is per rule, not per stance: the rule view marks a detector
  `promote?` when it trips in more than 30% of at least 20 sessions
  [Source: bin/harness#RULE_PROMOTE_SHARE].

No drift report, per-variant threshold or stance proposal exists.

## Acceptance criteria

From the issue's Acceptance section, which takes FR-50's two testable consequences
([#692](https://github.com/JakeSelby/agent-harness/issues/692)):

1. **Given** the decision log, **when** the drift report runs, **then** it has one entry per stance,
   naming the declared variant and the effective variant measured from the decision log.
2. **Given** ledger rows past a variant's threshold, **when** the report runs, **then** it proposes the
   promotion or demotion and names those rows.
3. **Given** a proposal, **when** the developer has not applied it, **then** no stored selection has
   changed, and a test proves it.

## Design

### Approach

From the issue's scope: a drift report with one entry per stance, declared against effective variant;
a proposal naming its rows when they pass a variant's threshold; and application by the developer only.
[ASSUMPTION: the report is a read-only view over `decisions.jsonl` beside the existing `harness usage`
views; the issue does not name a command.]

### Decisions and alternatives

None recorded. Two design questions the issue leaves open:
- **How an "effective variant" is measured from the decision log.** The five decision points map to
  some stances more directly than others, for example `tier-agent-spawns` to delegation. [ASSUMPTION:
  a stance with no decision point that observes it reports its effective variant as unmeasured.]
- **Where each variant's threshold is declared.** FR-50 says "a variant's threshold" without naming
  where it lives. [ASSUMPTION: beside the variant, so the threshold is reviewed with the stance text.]

### Do not implement

- Any code path that writes a stance selection. "The developer applies a proposal. The system never
  changes a stored selection itself" ([#692](https://github.com/JakeSelby/agent-harness/issues/692)).
- A decision provider judging the proposal; AD-15 keeps the deterministic answer authoritative.
