## Reproduction

At HEAD, with the delegation stance set to `off`:

1. Pipe a bare spawn to the hook, as its own header documents:
   `printf '%s' '{"tool_name":"Agent","tool_input":{"prompt":"x"}}' | HARNESS_STANCE_DELEGATION=off python3 policy/hooks/tier-agent-spawns.py`
2. Observed: the hook emits `permissionDecision: "ask"` with the reason "the delegation stance is off:
   confirm this spawn or do the work inline" [Source: policy/hooks/tier-agent-spawns.py#main].
3. Read `primitives/stances/delegation/off.md`: "A spawn attempted under this stance is denied outright,
   so changing the selected stance is the only way to delegate."
   [Source: primitives/stances/delegation/off.md]
4. Read the hook's header comment: `off            ask before every spawn, named or not`
   [Source: policy/hooks/tier-agent-spawns.py].

The stance says deny; the hook's decision and its comment say ask
([#687](https://github.com/JakeSelby/agent-harness/issues/687)).

## Root cause

PR #311, under #307, changed the stance text to say a spawn is denied, because the engine was observed
denying spawns in three disposable homes during 0.11.0 qualification. It was a documentation-only
change: it corrected a matching comment in `policy/hooks/brief-guard.py` but left the spawn hook's
logic and header comment unchanged
[Source: _bmad-output/implementation-artifacts/AH-C021.md].
So the stance now describes the observed engine outcome, not the hook's decision.

The record does not explain why an `ask` produced a denial (AH-C021). The spine records that ask
handling differs by runtime and mode: "Codex ... turns an ask into a deny, and Claude Code under `auto`
or `bypass` ... ignore an ask"
[Source: _bmad-output/planning-artifacts/architecture-spines/architecture-agent-harness-2026-09-23/ARCHITECTURE-SPINE.md#AD-15: Decision providers are subordinate [ADOPTED for the contract; act consumers planned]].
[ASSUMPTION: the qualification homes ran headless, where an ask has no user to reach and resolves as a
deny; the record does not say which mode the observation ran under.]

## Acceptance criteria

Criteria 1 and 2 are the issue's Acceptance section; criterion 3 is from its Scope
([#687](https://github.com/JakeSelby/agent-harness/issues/687)):

1. **Given** the `delegation: off` stance, **when** its text, the hook's decision and the hook's header
   comment are read together, **then** all three say the same thing about a spawn.
2. **Given** the tests that pin the hook's decision under `off`, **when** the suite runs, **then** they
   assert the decision the stance text describes.
3. **Given** the engine turns this hook's `ask` into a deny on some runtime or mode, **when** that is
   established, **then** it is recorded as a runtime capability rather than only in stance prose.

## Design

The issue's scope: establish what the hook should emit under `off`, then make the hook, its comment
and the stance agree; record an engine ask-to-deny conversion as a runtime capability if there is one;
and update the two tests that pin today's `ask` to the decided behaviour, so the decision stays pinned.

**Decisions and alternatives.** The issue leaves the target decision open and names no options.
[ASSUMPTION: these two directions are the ones its scope leaves open.]
- **The hook emits `deny`.** The stance is already right, and only the hook, its reason string and its
  comment change. [ASSUMPTION: this matches the observed engine outcome, but loses the in-session
  confirmation the current reason text offers.]
- **The hook keeps `ask`.** The stance changes back to describe an ask, and the runtimes or modes that
  resolve an ask as a deny are stated beside it, from the capability record.

AD-7 allows pre-tool deny or ask "wherever the runtime supports each", and says a gap is declared in
`capabilities.json`, never papered over
[Source: _bmad-output/planning-artifacts/architecture-spines/architecture-agent-harness-2026-09-23/ARCHITECTURE-SPINE.md#AD-7: What a hook may and may not do [ADOPTED]].
That is where criterion 3's capability belongs.

**Do not change:** the `tiered` and `session-model` branches of the hook; only the `off` branch is in
scope.

## Regression test

Written. `test_off_denies_every_spawn` (formerly `test_off_asks_before_every_spawn`) and
`test_env_override_beats_config` in `tests/test_tier_agent_spawns.py` now assert `"deny"` for `off`,

## Dev agent record

- **Default taken:** with delegation off, the hook denies the spawn and names the stance, rather
  than asking; an ask would stall unattended runs.
- **Finding for AC 3:** no engine converts this hook's `ask` into a deny. Under `off`, the shared
  lifecycle's `Agent` branch emits `deny` ("Delegation is off; perform the work inline or change
  the selected stance.") and never invokes `tier-agent-spawns` at all
  [Source: lib/harness_core/lifecycle.py]. That deny is what the 0.11.0 qualification observed, so
  the `[ASSUMPTION]` about headless ask resolution in the root cause is not needed, and no
  capability is recorded in either `capabilities.json`.
- **Change:** the hook's `off` branch emits `deny` with the lifecycle's reason, and its header says
  the lifecycle denies first, so the branch decides only a direct run of the hook.
- **Tests:** `test_off_asks_before_every_spawn` became `test_off_denies_every_spawn`;
  `test_env_override_beats_config` asserts `deny`, and so does
  `test_posture.HooksUseIt.test_a_hook_honours_harness_home`, a third pin of `ask` the story did
  not list, which uses `off` only to prove the hook reads `HARNESS_HOME`. The new
  `tests/test_delegation_off_agreement.py` holds the stance text, the hook header and the hook's
  reason against the lifecycle's, so the three cannot drift apart again.
- **File list:** `policy/hooks/tier-agent-spawns.py`, `tests/test_tier_agent_spawns.py`,
  `tests/test_posture.py`,
  `tests/test_delegation_off_agreement.py`, `changelog.d/687.fixed.md`, this story, and the
  regenerated sprint status.
