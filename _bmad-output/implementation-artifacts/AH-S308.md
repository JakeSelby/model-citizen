## Story

As a developer, I want to test a draft against its base and get a verdict, so that I know whether my change helped before I apply it.

## Context and value

The loop the Studio exists for. "Test this draft" runs the chosen suites on the draft and on its base with matched parameters, pairs the results, and puts a verdict on the draft's page: what changed, whether it helped, by how much and with what interval, and what it cost to find out. Too few trials to detect the effect the developer cares about is flagged before the run, from the power analysis in #796.

## Acceptance criteria

1. Given a draft, when it is tested, then the base and the draft run as a pair on the same suite, tasks, model and trials.
2. Given too few trials for the stated effect, then the Studio says so before the run and offers the number needed.
3. Given a finished test, then the draft's page shows the verdict, links to the comparison, and keeps a verdict for each checkpoint.
4. Given a draft changed after its test, then its verdict is marked stale.

## Design

### Approach

A draft test is one live replay (#1062's `ReplayAdmission`) whose target 1 is the commit the draft
was based on and whose target 2 is the draft's checkpoint, so both run as a pair on the same tasks,
model, trials, evaluator pack and caps (AC 1). `lib/harness_core/studio/draft_tests.py` builds that
form from the draft's state (read through `drafts.read_snapshot`), checks that a resolved request is
a test of this draft's current checkpoint against its base, and records each started test once
under the supervisor's state root (`draft-tests/<run id>.json`) with the draft id, checkpoint and
power check. The verdict is #990's `compare.compare_runs` of target 1 against target 2, read and
never recomputed; staleness is `replay.draft_staleness` (AC 4).

Before the run the plan route reports power from the engine: `replay_stats.minimum_detectable_effect`
at the pair's attempts per side and a planning coefficient of variation, stated with the test or
taken from the repository's declared assumption in `benchmarks/ablations.json`, against the effect
the developer names. Fewer than the engine's `MIN_TRIALS` trials, or a detectable effect larger
than the named one, is flagged with the fewest trials up to the replay's limit of 20 that would do
(AC 2). The spend preview and confirmation are the replay's own.

`POST /api/configure/test/plan`, `/start` and `/verdicts` serve the draft page's new "Test this
draft" panel; `citizen draft test NAME [--json]` prints the verdicts route's answer. The panel keeps
the latest verdict for each checkpoint with its headline, the engine's Cost-of-Pass and pass-rate
entries, spend, power line, the comparison command and an "Open comparison" view that renders
#990's report (AC 3), and marks a stale verdict "Stale: the draft changed after this comparison."
(AC 4).

### Decisions and alternatives

- **When the Studio may say "helped".** Only when the comparison is comparable, withholds no
  direction (`compare.direction_withheld` empty: both sides pre-registered, no arm the engine marks
  exploratory, one run window), and every measure in `compare.PREFERRED` reads its preferred way:
  Cost-of-Pass lower and pass rate higher. "Worse" is the mirror; otherwise "inconclusive", or
  "exploratory" when a direction is withheld. `replay.target_evidence` registers only a release
  target, so a draft target always runs `--exploratory` and a draft test never says helped today.
  SM-2's `decide` is not used: the engine defines it for harness against bare only.
- The base is named by commit (a `branch` target accepts a full commit), not as `installed` or a
  tag, so a moved checkout can never stand in for the commit the draft started from.
- One run with two targets, not two runs: the pair shares one admission, one cap and one run
  window, which is what the comparison's matching demands.
- Power uses `minimum_detectable_effect`, the planning figure the ablation and unit-economy
  commands already state before spend, not `replay_power.py`, which sizes SM-2's harness-against-bare
  design and needs pilot variance. The planning cv falls back to the repository's declared
  assumption, quoted with its source, rather than an invented default.
- An underpowered test is flagged, not refused: it is exploratory either way, and the developer
  may still want the readings.
- Records live in the Studio state root, keyed by run id and filtered by draft id, so a draft
  recreated under the same name never inherits another's verdicts, and no draft state is written.

### Do not implement

No interval, ratio, reading or decision rule computed in Studio or the browser beyond reading the
engine's readings against `compare.PREFERRED`; no pre-registered draft test (it needs a replay
change to register a draft target); no automatic rerun of a stale verdict; no change to the replay
runner, the comparison or live configuration.
