## Context

`harness stances --json` resolves the full ladder: the defaults, the user configuration, the file named by `HARNESS_PROJECT_CONFIG`, then `HARNESS_STANCE_*`. `harness sync` projects only the user-level selection into the client's instruction files. A project file or a session variable therefore changes what the hooks decide, because they resolve the ladder at run time, but not the stance text the model reads, because that text is a link written at sync. The two halves of a stance, the prose the model follows and the switches the hooks read, can disagree within one session ([#276](https://github.com/JakeSelby/agent-harness/issues/276)).

The gap was found while automating the `stance-switch` qualification case, which could not observe a project override natively ([#276](https://github.com/JakeSelby/agent-harness/issues/276)).

The 2026-09-23 PRD lists it as open question 4, "Selections a native client cannot read", blocking FR-2 and needed by v0.14.0, and its UJ-2 edge case says "The linked stance text stays user-level until #276 is decided" [Source: _bmad-output/planning-artifacts/prds/prd-agent-harness-2026-09-23/prd.md]. FR-2's status records the related defect that `sync` ignores `HARNESS_STANCE_*` variables that `harness stances` honours (#294).

What exists on `main`: when a session override or `HARNESS_PROJECT_CONFIG` is present, the session-start hook runs `harness stances --json` and adds an "Effective session stance" line, with the variant's behaviour text, for each dimension that differs from the user configuration [Source: policy/hooks/harness-session.py#resolved_overrides]. The "Effective session stance" text first appears in commit ca5547f, titled with PR #106, which merged on 2026-09-19 and whose file list includes `policy/hooks/harness-session.py` ([PR #106](https://github.com/JakeSelby/agent-harness/pull/106)); this issue was created on 2026-09-21 ([#276](https://github.com/JakeSelby/agent-harness/issues/276)). [ASSUMPTION: this partly implements option 2 below for the environment-driven case; neither the issue nor any later record says whether it satisfies the decision.]

## Options

1. **Document it as the contract.** Prose is user-scoped and sync-time; project and session selections affect hooks only. The issue calls it the cheapest, and says it leaves a real gap for stances that are mostly prose.
2. **Inject the resolved stance text at session start** when the project or session stance differs from the synced one. It keeps sync simple, costs context each session, and must stay within the spirit of the always-loaded budget.
3. **Project a per-project instruction file at sync** for directories that carry a project config. The issue calls it closest to native, and notes it needs ownership rules for files inside repositories the user does not control.

[Source: [#276](https://github.com/JakeSelby/agent-harness/issues/276)]

## Decision

Done when: one option is chosen and documented in `docs/sync-model.md` and `docs/primitive-authoring.md`, and the `stance-switch` and `custom-stance` qualification cases either observe a project and a session selection natively or state precisely why that scope is verified another way ([#276](https://github.com/JakeSelby/agent-harness/issues/276)).

Decided by the owner on 2026-09-26: option 2. At session start, inject the resolved stance text when the project or session stance differs from the synced one. It must fit the always-loaded budget and costs context only when a selection differs. The work finishes the "Effective session stance" line PR #106 added: the differing variant's operative text is injected, bounded by the always-loaded budget that `citizen lint` enforces, with a pointer to the full text when it cannot fit.

As built:

- **Differs from what.** The synced selection is the one the sync manifest records (`manifest.config.stances`), falling back to the configuration file only when no manifest record exists. A session whose resolved selection matches it runs the resolver and injects nothing; a session with no project or session selection does not run the resolver at all [Source: policy/hooks/harness-session.py#resolved_overrides].
- **The budget.** `ALWAYS_LOADED_TOKEN_CAP` less the estimated tokens the sync already made always-loaded: `claude/CLAUDE.md`, the rules not switched off, and the targets of the manifest's `harness-stances` and `harness-roots` rule links. The hook carries the cap and the chars-per-token figure as constants, and a test asserts both equal `bin/harness`'s [Source: policy/hooks/harness-session.py#synced_tokens; tests/test_session_stance_injection.py].
- **Fitting.** Every differing dimension is always named. Pointers are paid for first; the budget left then upgrades each pointer to the full text in dimension order while it fits (`fit_stances`). A pointer names the variant's file and tells the model to read and follow it instead of the linked variant.
- **Qualification.** `custom-stance` now observes a session selection natively (`HARNESS_STANCE_PROOF=plain`, a fresh turn must close PLAIN with the global link unmoved) beside the project selection it already observed. `stance-switch` stays user-level by design: both of its switches are sync-time links, and a project or session selection reaches the model by the dimension-independent injection path that `custom-stance` observes; its docstring says so [Source: scripts/native_acceptance.py#case_stance_switch, #session_override].

Default taken: the budget is the lint's token cap less the synced always-loaded layer, counted additively, because the linked variant stays loaded beside the injected one, so the model really does read both.
Default taken: the synced selection is the manifest's record, not the configuration file, because an edit to the file since the last sync is drift the hook already reports, and the links reflect the manifest.

## Consequences

- Until decided, a project or session selection can leave the model reading user-level stance text while the hooks act on another variant ([#276](https://github.com/JakeSelby/agent-harness/issues/276)).
- The decision unblocks FR-2 per the PRD's open question 4.
- AD-6, One effective policy for every consumer, requires every consumer to ask `posture.py` for the effective policy; linked stance text read by the model is a consumer that does not today. [ASSUMPTION: the spine does not name #276; the fit is inferred from AD-6's rule.]
- Option 3 would need ownership rules under AD-3, Reversible configuration ownership. [ASSUMPTION: inferred from the issue's own caveat about repositories the user does not control.]

## Review findings

- **CodeRabbit, round 1, `policy/hooks/harness-session.py`:** `synced_tokens` counted the checkout's rules and the stance links but not the `primitive_roots` rules sync links under `rules/harness-roots/`, so a configured root could let injected text exceed the real budget. Fixed: those manifest links are counted, with a test where an installed root rule turns a fitting variant into a pointer.
- **CodeRabbit, round 1, `scripts/native_acceptance.py`:** `session_override` passed on a PLAIN reply even when the transcript did not carry the session hook's line, which does not prove the selection arrived through the hook. Fixed: a PLAIN turn without the line is `unverified`, with a test.
- **CodeRabbit, round 2, outside the diff, `policy/hooks/harness-session.py`:** `fit_stances` charged each line on its own, so the `"\n\n"` separators and per-line rounding went uncharged and the joined stance text could exceed the budget. Fixed: an upgrade is kept only when the joined text, separators included, fits, with a test that fails on the per-line version.
