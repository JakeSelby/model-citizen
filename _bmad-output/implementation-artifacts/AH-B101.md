# AH-B101 — fix(remote-control): files an agent sends cannot be opened from the app

## Reproduction

1. Start a Remote Control session, for example from a host serving a repository with
   `spawn: worktree`, so the session's working directory is its worktree.
2. Have the agent write a file outside that directory, such as a report in a temp directory or a
   render in a task worktree, and call `SendUserFile` with its path.
3. Open the file card in the app. It shows "Couldn't load this file … It may be outside the
   session's working directory, or it may have been moved or deleted."

## Root cause

In a Remote Control session `SendUserFile` uploads nothing: the session has no upload route, so
the app keeps the absolute path and later sends the session a `read_file` request for it. Claude
Code 2.1.280 answers that request only when the file's real path, symlinks resolved, is under the
session's start directory or a directory added to the session, and the ordinary Read permission
check allows it. The start directory is `originalCwd`, which is the worktree in worktree spawn
mode, not the current directory and not the repository the worktree came from. Agents write the
files they show to Claude Code's temp and scratchpad directories, `/tmp`, `~/.claude/scratch`, task
worktrees and the main checkout's `.agent-harness/`, all outside that set. Across one user's local
transcripts, about four in five sent files were outside the sending session's working directory.
[Source: Claude Code 2.1.280, `readFileForRemote` and the working-directory set `sb()`]

## Acceptance criteria

1. **Given** a `SendUserFile` call naming a regular file whose real path is outside the hook's
   working directory, **when** the PreToolUse coordinator runs, **then** the file is copied to
   `.agent-harness/outbox/<digest>/<name>` under that directory and `updatedInput.files` names the
   copy, with every other input field unchanged.
2. **Given** a file inside the hook's working directory, a relative path that resolves inside it,
   a missing path or a directory, **when** the call is dispatched, **then** its entry is unchanged
   and no outbox is created for it.
3. **Given** a path inside the working directory that is a symlink to a file outside it, **when**
   the call is dispatched, **then** the real file is copied, matching the real-path check the
   client's request goes through.
4. **Given** a git repository, **when** a file has been copied, **then** `git status` shows nothing
   new, because the outbox holds a `.gitignore` that ignores everything in it.
5. **Given** the same unchanged file sent twice, **when** it is staged, **then** the first copy is
   reused; **given** the file changed in between, **then** a second copy is made and the first
   keeps its content.
6. **Given** outbox directories untouched for longer than two weeks, **when** a file is copied,
   **then** only digest-named directories past that age are removed.
7. **Given** a file past the call's byte or time budget, an outbox or outbox entry that is a link,
   or a copy that fails, **when** the call is dispatched, **then** that entry is unchanged, the
   other entries are still rewritten, and a notice names the file; the hook never returns a
   permission decision, and malformed payloads produce no output.
8. **Given** a saved `harness task` handoff, **when** a file is staged, **then** the handoff stays
   current, because the outbox holds delivery copies, not task inputs.

## Design

A new policy, `policy/hooks/stage-user-files.py`, answers `PreToolUse` for `SendUserFile` through
the coordinator in `lib/harness_core/lifecycle.py`, which reaches it before the existing routing,
so the plan-mode approval still answers for that tool. It returns only `updatedInput` and a
`systemMessage` notice, which the coordinator already merges and passes through for Claude Code.

The staging root is the hook payload's `cwd`. Claude Code resets the shell to the start directory
when a command leaves the session's working directories, so `cwd` is always a directory the
client's check accepts. `CLAUDE_PROJECT_DIR` was rejected: hooks receive the project root
there, a separate value from the start directory the check uses. The git top level was rejected
because it can sit above a session started in a subdirectory.

A copy, not a hard link, so each card keeps the content it was sent with even when the source is
later rewritten in place. The digest covers the real path, size and modification and change
times, so a rewrite that restores the modification time still gets a new copy. One call
copies at most 64 MiB and starts no copy after four seconds, against the coordinator's ten-second
budget; the time check runs between files, so a single slow source can still outrun it, and the
call then goes through unchanged. `harness task` leaves the outbox out of its fingerprint.

Rejected: an always-loaded rule telling agents to write shareable files inside the working
directory, which costs context in every session and depends on compliance; adding the temp and
scratch directories as additional working directories, which widens what Claude may edit and
still misses task worktrees and the main checkout; staging into Claude Code's own project
directory, which the check also accepts but only as an undocumented internal path.

The fix must not change any other tool's routing, refuse a `SendUserFile` call, or write outside
the working directory.

## Regression test

`tests/test_dispatch_model.py::RoutingTests::test_a_file_sent_from_outside_the_session_is_staged_inside_it`
dispatches a `SendUserFile` call for a file outside the session directory through the
coordinator. Before the dispatch change it failed with `KeyError: 'hookSpecificOutput'`, since the
call passed through unchanged; it passes after. `tests/test_stage_user_files.py` covers
criteria 1 to 7 against the policy itself.
`tests/test_tasks.py::TaskTests::test_files_staged_for_a_remote_control_client_leave_the_handoff_current`
covers criterion 8; it failed with `'stale' != 'current'` before the fingerprint change.

## Review findings

A fresh-context review of the first diff returned six should-fix findings and four notes.

- Fixed: the `harness task` fingerprint hashed every staged copy, so staging made a saved
  handoff stale; the outbox is now excluded, with a test.
- Fixed: the 64 MiB cap applied per file with no deadline; it is now a budget per call plus a
  four-second deadline checked between files, and the claim about the budget was reworded.
- Fixed: a planted link at the outbox's `.gitignore` or a digest folder could be written through;
  both are now refused, with a test.
- Fixed: path resolution sat outside the per-entry error handling, so one bad entry dropped every
  rewrite in the call; each entry now fails alone, with a test.
- Fixed: a failed copy and a reused copy were not proved; the tests now force a copy failure and
  compare the reused copy's inode.
- Fixed: the missing-path and directory cases now assert no outbox is created.
- Accepted: a reuse can race a prune from another session in the same directory, which needs a
  two-week-old copy sent again at the moment another session prunes it.
- Accepted: files under the start directory but outside a subdirectory the agent moved into are
  copied although the client would serve them; the copy is harmless, and the criteria now say
  "the hook's working directory".
- Fixed: the documentation said copies never reach the lint; that holds only in a repository and
  now says so.

The pull request's automated review raised two more.

- Fixed: a same-size rewrite that restored the modification time kept the old digest, so the stale
  copy was sent. The digest now includes the change time, which any write or timestamp change
  moves, with a test. Comparing the bytes on every reuse was rejected, because it rereads both
  files each time and overwrites a copy an earlier card still shows.
- Changed, premise rejected: the policy test loaded the hook through `claude/hooks`, which the
  review said a clean checkout lacks. That path is a tracked symlink to `policy/hooks`, and CI's
  clean checkout ran the test. The test now names the canonical `policy/hooks` path, as
  `tests/test_tasks.py` already does.
