## Story

As a developer using the harness, I want every installed unit selectable from one selection document
resolved by one function, so that a stance, rule, hook, skill, workflow or role can be chosen in one
place and every consumer acts on the same answer.

## Context and value

Epic #552 makes the harness the configurable layer under a skill library: every unit becomes a
dimension with variants, and a mode is a named set of selections [Source: #552]. This story is the foundation: #555,
#556 and #557 are blocked on it. Its principle from the epic: one selection document shape in five
places, one resolver, no second path. [Source: #552]

Today only stances are selectable. `policy/hooks/posture.py` resolves the stance ladder (defaults,
user config, the `HARNESS_PROJECT_CONFIG` file, then `HARNESS_STANCE_*`), and `bin/harness` keeps its
own `load_config` ladder beside it. There is no `posture.selection()`, no `HARNESS_SESSION_CONFIG` and
no `harness selection` command on `main`. `catalog.KINDS` exists, but as a map from kind to source
directory only.
[Source: https://github.com/JakeSelby/agent-harness/issues/554]

## Acceptance criteria

1. **Given** any installed unit, **when** `harness selection --json` runs, **then** it lists every unit
   of every kind with its value and source; `harness stances --json` is unchanged for existing keys.
2. **Given** a project file, **when** it sets `rules`, **then** the setting is honoured; **when** it
   sets `identity`, **then** it is refused with a message naming the key.
3. **Given** `HARNESS_SESSION_CONFIG`, **when** selections resolve, **then** it is read after the
   project file and before the environment sugar, and a worker run resolves the same selection as the
   session that launched it.
4. **Given** the unit tests, **when** they run, **then** they cover precedence for each of the five
   sources and the refusal of non-selection keys.
5. **Given** the docs, **when** the shape is documented, **then** `docs/preferences.md` states it once
   and other docs point at it.
6. **Given** the change, **when** the gate runs, **then** `bin/harness lint` is clean and the suite is
   green under both a current Python and the system Python 3.9.

## Design

### Approach

- **A unit is a dimension with variants.** Stance dimensions keep named variants; every other kind is a
  switch kind with exactly `on` and `off`, default `on`. Kinds: `stances`, `rules`, `hooks`, `skills`,
  `workflows`, `roles`.
- **One JSON shape in five places:** a mode file, the user's `config.json`, the project file
  `HARNESS_PROJECT_CONFIG` names, the session file `HARNESS_SESSION_CONFIG` names, and the output of
  `harness selection --json`. The issue's example carries `mode`, then one object per kind.
- **One resolver:** `posture.selection()` returns every unit with its value and source (`default`,
  `mode:<name>`, `user`, `project`, `session`), in that precedence. `HARNESS_MODE` and
  `HARNESS_STANCE_*` stay as session sugar that resolves through it.
- **One reader set:** sync, `lifecycle.invoke`, `workers.py`, `harness selection`, `harness stances`
  (kept as an alias) and `catalog` all read that function.
- **A kind is one entry in `catalog.KINDS`:** source directory, value type (`variant` or `switch`) and
  projection. Adding a kind adds no config-schema or resolver code.

### Decisions and alternatives

- **Selections carry selections only.** Identity, permissions, runtime `manage` flags,
  `primitive_roots` and telemetry stay top-level with their own validation.
- **`harness stances` is kept as an alias**, so its JSON output keeps its shape; AD-2 relies on this for
  the session hook.
- **The mode key may resolve to nothing until #557 lands** (issue: "that is fine").

### Do not implement

- Modes themselves (#557), hook ids (#555), and per-file rule links (#556).
- Any selection key outside the six kinds and `mode`.

## Review findings

CodeRabbit, round 1 on PR #836:

- `workers.run()` still injects a skill a session selection switches `off`. Declined here: sync and
  workers acting on an `off` rule, skill, workflow or role is #556; this story resolves and reports
  switch kinds only.
- A project or session file with a non-object kind value, such as `{"rules": []}`, was silently
  ignored. Fixed: `selection()` refuses it when strict and drops only that kind otherwise, with a
  test.
- Review body, outside the diff: the `precedence` list in `harness stances --json` omits the mode
  layer. Not changed: the acceptance keeps that output unchanged for existing keys, and the mode
  layer shows in `sources`.

CodeRabbit, round 2:

- An explicit `null` kind (`{"rules": null}`) still passed strict resolution. Fixed with the
  non-object refusal: a present kind that is not an object is refused.
- A switch value of `null`, an empty string or a non-string was skipped before the on/off check,
  so strict resolution reported `on`. Fixed: every supplied switch value is checked first, with a
  test. Stance values keep their existing handling.
