## Story

As a developer, I want to run the live replay benchmark on two targets from the Studio, so that I measure cost per passed task for a draft against a release.

## Context and value

Run `cost_bench.py replay` from the Studio with two targets (a release against a draft, say), the model, the repetitions and a subset of tasks, under the spend guard. Progress shows per task and arm, and the rows land in the run store and, for a release target, in the benchmark history the project keeps.

## Acceptance criteria

1. Given two targets, then each arm runs against its own built profile, and the run records both targets.
2. Given a replay with no explicit target, then the Studio refuses it, as `cost_bench.py replay` refuses one without `--tag` (#944).
3. Given a finished run, then the per-task table shows cost per passed task and pass rate for each arm.

## Design

### Approach

Add a replay-specific adapter around the native `cost_bench.py replay` runner instead of copying
its measurement logic into Studio. The adapter accepts exactly two already-resolved targets, runs
each target through the benchmark's own built-container profile, applies one whole-set spend cap,
preserves each native `results.jsonl` and authoritative `spend.json`, verifies every result against the target's immutable revision,
and derives the per-target/task/arm table from those rows. A small allowlisted wrapper emits the paid
suite result protocol for the shared supervisor. The Experiments panel owns selection, preview,
one-use confirmation and the result table; shared route and catalog wiring reuse the run supervisor.

### Decisions and alternatives

- Require two explicit target references and full resolved revisions. The installed profile is never
  an implicit fallback. The UI sends kind/ref to the AH-S301 resolver, preview returns immutable
  version/commit/draft/config identity, start consumes that resolved request, and a moved ref is caught
  when native rows do not match the resolved revision.
- Let `cost_bench.py` build the isolated arm profiles. A second profile builder would drift from the
  benchmark's declarations, manifests, admission checks and container fence.
- Run targets separately under one decreasing spend cap. This lets release targets use a committed
  pre-registration and project benchmark history while drafts remain exploratory and cannot pollute it.
- Consume the native replay's spend sidecar for cap accounting. Preflight charges, scored rows and
  fail-closed null-cost charges all reduce the same whole-set cap before target two is admitted.
- Preserve native rows as authority and index those rows with the existing run-store adapter. The
  replay summary and SQLite table are derived and rebuildable.
- Report intention-to-treat pass rate and cost divided by passed attempts for every target, task and
  arm. Missing cost remains unavailable instead of becoming zero.

### Do not implement

Generic target resolution and checkpoint creation belong to AH-S301; this adapter consumes their
immutable revisions. Comparison intervals and causal verdicts belong to AH-E025. Four-arm and
factorial runs belong to AH-S306. This story does not change the benchmark engine or publish results.
