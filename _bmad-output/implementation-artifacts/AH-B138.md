# AH-B138 — Concurrent first Studio lock opens fail with ENOENT on macOS

## Reproduction

Run `tests/test_studio_targets.py` `test_concurrent_target_builds_do_not_hold_the_supervisor_lock` repeatedly; about one run in three fails with `BrokenBarrierError` because one of the two concurrent starts raises `run lock is missing or unsafe`. Two threads calling `os.open(name, O_RDWR|O_CREAT|O_NOFOLLOW, dir_fd=fd)` on a new name fail with ENOENT in 261 of 600 opens on Darwin 25.5; absolute-path opens never fail.

## Root cause

macOS can fail the losing `openat(O_CREAT)` of a name another thread is creating at the same moment with ENOENT. `RunSupervisor.lock` treats any `OSError` as an unsafe lock. [Source: lib/harness_core/studio/runs.py#lock]

## Acceptance criteria

1. **Given** a fresh state root, **when** two supervisors take the lock at once, **then** both succeed.
2. **Given** an exclusive create, a plain open or a removed directory, **when** the open fails with ENOENT, **then** it is not retried past the attempt limit and still raises.

## Design

`state.open_shared` retries only a non-exclusive create that failed with `FileNotFoundError`, up to eight attempts with exponential backoff from one millisecond, and is used at every shared-name create through a directory descriptor: supervisor lock, instance lock, run-store authority lock, run-store appends and run output logs. Exclusive temporary-file creates use unique names and are left alone.

## Regression test

`tests/test_studio_runs.py` `test_first_concurrent_lock_opens_do_not_fail_the_losing_creator` (40 trials of two supervisors racing the first lock; fails on the old code) and `test_open_shared_retries_only_a_non_exclusive_create_that_lost_a_race`.
