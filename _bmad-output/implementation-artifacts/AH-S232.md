## Story

As a harness maintainer, I want every module to declare its claims, surface, instruments, slot, dependencies and conflicts in a manifest the resolver enforces, so that a flipped switch can be attributed and scored rather than only toggled.

## Context and value

#554 gives every module a switch in one selection document. A switch alone does not say what the module is for, what it costs to carry, how its effect is measured or what it collides with, so a flipped switch cannot be attributed or scored. AD-22 makes each module declare six manifest fields, resolved by `posture.py` as the one resolver: claims, surface, instruments, slot, dependencies and conflicts.

Depends on #554. Traces to FR-15 and AD-22.

## Acceptance criteria

1. Given a module in the selection document, when the selection resolves, then its manifest carries all six fields, and a missing field fails resolution with the module and the field named.
2. Given two selected modules that claim one slot, when the selection resolves, then it fails unless one declares that it cedes the slot.
3. Given a selected module whose dependency is not selected, or that conflicts with another selected module, when the selection resolves, then it fails and names both.
4. Given a module with no instrument, when a report or scorecard lists it, then it shows as unmeasured, never as having no effect.
5. Given the unit tests, then they cover each field for every switch kind, and the slot, dependency and conflict refusals.

## Design

### Approach

Manifests are data beside the module source, and `policy/hooks/posture.py` stays the one resolver (AD-22). Shipped rules, skills, roles and workflows declare theirs in `primitives/manifests.json`, hooks in `policy/hooks/manifests.json`, and a user primitive root may carry a `manifests.json` of the same shape. `posture.selection()` validates every declared manifest and applies the missing-manifest, dependency, conflict and slot refusals whenever it resolves strictly, raising one `ValueError` that names each module involved. `posture.measurement()` is the one wording of a module's measurement state, and the `harness selection` text report prints it beside every switch unit.

### Decisions and alternatives

1. **One JSON file per catalog, not frontmatter.** Rules carry no frontmatter and are loaded into context verbatim, so a header on each would cost context and change every content digest. Rejected: per-file frontmatter; one sidecar per module (43 files for one table).
2. **Switch kinds only.** A stance variant is chosen, not switched, and AD-22's fingerprint lists stance variants apart from switched-on modules. Rejected: manifests for stance variants.
3. **A user root's module may omit its manifest.** `docs/compatibility-policy.md` makes rejecting previously valid configuration a major change; a root written by `harness import` has no manifest. An omitted manifest reports as unmeasured; a declared one is validated and enforced in full. Rejected: requiring one everywhere in a minor release.
4. **`cedes` lives inside `slot`.** The six fields stay six: `slot` is `null` or `{"id", "cedes"}`. Ceding clears the error only; switching the ceding module off is the v0.16.0 slots work.
5. **A dependency is what breaks the module when absent.** Workflow-to-role spawns, a role's declared skills and the design loop's two roles are dependencies; a rule's pointer to a skill is further reading, not a dependency.
6. **Enforced on strict resolution only.** A hook or worker resolving non-strictly keeps running on what it can read, as for every other selection error.
7. **A report shows instruments, or `unmeasured`.** The `--json` selection document is unchanged, because it must read back as a session file.

### Do not implement

- The scorecard (v0.15.0) and slot adapters (v0.16.0).
- Hook ids and a shipped hook manifest: the hook-id story enumerates hook units.
- Sync acting on an `off` unit (#555) and the profile fingerprint (#789).
- Any change to `harness selection --json` or to `lib/harness_core/catalog.py`.

`tests/test_manifest.py`, on a fixture checkout with one module of every switch kind:
- AC 1 and 5: `Fields` removes and malforms each field for every switch kind; `Shipped` holds the shipped file to the installed units and resolves it strictly.
- AC 2: `Refusals` slot tests (clash, ceding, a switched-off holder).
- AC 3: `Refusals` dependency and conflict tests; `Shipped` switches off `roles/builder` under `workflows/build`.
- AC 4: `Reports` checks `measurement()` and the `harness selection` text.
- User roots: `UserRoots` (omitted manifest resolves, declared one enforced, no redeclaring a shipped module).
