# AH-B100 — /close-out files follow-ups after it lands, so the filing's own changes never merge

## Reproduction

1. Finish a session in this repository with a green pull request and a follow-up worth filing,
   then run `/close-out <what is finishing> archive`.
2. Step 2 lands the pull request through the `land` workflow, which also removes the session's
   worktree.
3. Step 4 files the follow-up with `scripts/bmad_issue_sync.py new`, which files the issue and
   writes `_bmad-output/issue-map.json`, `sprint-status.yaml` and a story skeleton into whichever
   checkout it runs in.
4. Steps 5 and 6 message dependent sessions and archive. Nothing lands the filing's changes: they
   sit uncommitted or in a pull request nobody merges, and a later `new` that sees the stranded
   map stops on an ID collision until it passes `--advance`.

## Root cause

`primitives/workflows/close-out.md` had no step that could merge what filing wrote. It assumed
filing only talks to the issue tracker. Here `new` also reserves the ID in tracked files, and
`docs/bmad-governance.md` requires that reservation to ship in the delivery pull request or before
it, so filing makes work that needs a pull request of its own. The only landing step ran before
filing.

## Acceptance criteria

1. **Given** the `/close-out` body, **when** its numbered steps are read in order, **then** the
   follow-up batch comes first, then the landing step, then the filing step, then the archive.
2. **Given** a filing that writes tracked files, **when** the approved follow-ups are filed,
   **then** filing runs in a new worktree off the updated default branch, what it wrote goes into
   its own pull request under the repository's pull request rules, and the close-out lands that
   pull request with the `land` workflow once its checks pass.
3. **Given** follow-ups and pull requests ready to land, **when** the workflow asks for approval,
   **then** one explicit go-ahead names the follow-ups, the pull requests to merge and any the
   filing would open and then merge, and it is the go-ahead the `land` workflow asks for in both
   the landing and the filing steps.
4. **Given** a pull request the filing opened has not merged, whether still open or closed
   without merging, **when** the invocation asked for an archive, **then** the workflow ends on
   the checklist instead of archiving.
5. **Given** a filing that writes no tracked files, **when** the follow-ups are filed, **then** no
   extra pull request is opened.
6. **Given** the change, **when** the unit suite runs, **then** the new ordering and phrase tests
   fail on the old text and pass on the new, the existing close-out tests pass unchanged, and the
   body stays inside the suite's 40-line cap and FR-59's 35-line figure.

## Design

The follow-up batch moves ahead of landing and becomes the one approval stop: a single explicit
go-ahead names the follow-ups, the pull requests step 3 would merge and any pull request step 4
would open and then merge, and it is the go-ahead the `land` workflow would otherwise ask for in
both steps. Landing stays step 3. Filing becomes step 4, after the merges: when it writes tracked
files it runs in a new worktree off the updated default branch, so the filing pull request starts
current and cannot conflict with the merges it followed, and the close-out lands it with the
`land` workflow once its checks pass. The archive step archives only when every pull request step
4 opened has merged, so a filing pull request held back by a red check or an open review thread,
or closed without merging, ends the run on the checklist instead of being stranded.

Rejected: filing before landing, which the issue first proposed. A filing branch cut before the
merges is behind the default branch by the time it lands, and in this repository both pull
requests write `issue-map.json` and `sprint-status.yaml`, so it conflicts or needs an update and a
second check run. Rejected: a second, separately approved landing pass after filing, which keeps
two approval stops. Rejected: shipping the reservation inside the session's own pull request, which
breaks one delivery issue per pull request.

Must not change: the sweep comes first, `land` and `handoff` are invoked as workflows and never
inlined, the session archives only when asked, it never clears or compacts first, and the body
stays inside its cap.

## Regression test

`test_close_out_asks_once_then_lands_before_it_files` in `tests/test_commands.py` reads the
numbered step titles and requires the batch, landing, filing and archive steps in that order. On
the old text it finds the steps at `[3, 1, None, 5]`, with no filing step and the batch after
landing, and fails; on the new text they are at `[1, 2, 3, 6]`. The phrase tests for the tracked
files, the archive condition and the single go-ahead also fail on the old text.

## Review findings

Blind review, eleven findings:

1. The filing pull request cannot pass `issue-ownership`. Real in part: the check needs exactly one
   delivery issue, and the workflow did not point at the repository's rules; "every time" is
   false, since #777 and #752 passed with a delivery chore. Fixed: step 4 opens the pull request
   under the repository's pull request rules, and step 2 names it in the go-ahead.
2. Step 2 did not say where filing runs. Real. Fixed: step 4 runs it in a new worktree off the
   updated default branch.
3. A filing pull request cut before the merges goes stale or conflicts on the map. Real. Fixed by
   the design change: filing now follows landing.
4. One go-ahead covered a pull request that did not exist yet. The AD-20 part is false, because
   AD-20 governs approvals crossing a session or runtime boundary and this stays in one session.
   Fixed the rest: the go-ahead names the pull requests to merge and any the filing would open.
5. No path for a partial answer. Real, low. Fixed: "Act on what it approves".
6. The archive condition was ambiguous, since issues never merge. Real. Fixed: the condition now
   names the pull requests step 4 opened; CodeRabbit's second round tightened it further.
7. The ordering test compared first occurrences of phrases. Real, low. Fixed: it parses the
   numbered step titles.
8. Acceptance criteria not enforced. The claim that FR-59 states no cap is false: its consequences
   state a 35-line cap, which predates #786 raising the suite's cap to 40. Fixed by rewording AC 6
   to both caps, which the 34-line body meets; AC 5 rests on the conditional a phrase test pins.
9. `docs/bmad-governance.md` not updated. False: it already lets a reservation ship before the
   delivery pull request, which is what a filing pull request does.
10. The story recorded no gate run. Real. Fixed: the dev agent record points at the gate evidence
   on the pull request.
11. Accuracy and churn. Fixed: the changelog no longer overstates the pass or contradicts the
   reproduction, the dev notes cite `create_issue` beside `reserve` and explain the moved map
   entry, and the archive step is rewrapped.

CodeRabbit, first round, one thread:

1. Step 2 approved opening the filing pull request but not merging it, and step 4's `land` call
   did not say it reuses step 2's go-ahead. Real. Fixed: step 2 names any pull request step 4
   would open and then merge, and step 4 says step 2's go-ahead covers landing what the filing
   writes; a phrase test pins both.

CodeRabbit, second round, one thread:

1. "No pull request step 4 opened is still open" let a filing pull request closed without merging
   through, leaving its files unmerged at the archive. Real. Fixed: the session archives only when
   every pull request step 4 opened has merged, and the phrase test pins that wording.
