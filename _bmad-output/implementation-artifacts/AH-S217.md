## Story

As a developer who relies on the harness's spawn guards, I want a launch of the Claude Code `Workflow`
tool to be logged, refused under `delegation: off`, and refused when its script names a constrained
role, so that a workflow script cannot run a confined role's work in session, unconfined.

## Context and value

The #540 spike, `docs/spikes/2026-09-22-workflow-tool-band-routing-and-ledger.md`, recorded its result
as "partially bypassed, measured 2026-09-22 on Claude Code 2.1.280":

- a workflow script's `agent()` calls produce no `Agent` tool call in the session, so
  `tier-agent-spawns`, `brief-guard` and the constrained-role refusal in `lib/harness_core/lifecycle.py`
  never see them;
- band routing and role confinement are both bypassed, and a script can run a read-only harness role in
  session by naming it.

The issue adds that `agentType: 'reviewer'` runs the read-only role in session on a frontier-class
model. The launch itself is a tool call the harness can match, and its input is the script text
(`script` or `scriptPath`), so the check reads text the session already has.

At `origin/main`, `dispatch` in `lib/harness_core/lifecycle.py` has `PreToolUse` branches for `Bash`,
`Agent` and `WebFetch`, and none for `Workflow`.

## Acceptance criteria

From the issue's "Done when" section:

1. **Given** a `Workflow` launch, **when** the `PreToolUse` hook runs, **then** a decision row is
   written to `decisions.jsonl`.
2. **Given** `delegation: off`, **when** a `Workflow` launch arrives, **then** it is refused with a
   reason.
3. **Given** a script whose text names a constrained role in `agentType`, or carries a `harness-role:`
   marker for one, **when** it is launched, **then** it is refused with the same `role_instruction`
   sentence the `Agent` refusal carries.
4. **Given** a script naming only band workers, **when** it is launched, **then** it is allowed.
5. Tests drive `lifecycle.dispatch` with a `Workflow` payload for each case.

## Design

### Approach

From the issue: add a `PreToolUse` branch for `Workflow` in `lib/harness_core/lifecycle.py` beside the
`Agent` branch. It records the launch, refuses it under `delegation: off`, and scans the script text,
inline or at `scriptPath`, for a constrained role in `agentType` or a `harness-role:` marker. A refusal
reuses `role_deny` and `role_instruction`, so the sentence matches the `Agent` refusal.

### Decisions and alternatives

- Guard the launch, not the `agent()` calls: the spike found the calls never reach a hook, and the
  launch is the one point the harness can match.
- Reuse the `Agent` refusal's wording rather than a new message, so every refusal of a constrained role
  reads the same.

No rejected alternative is recorded.

### Do not implement

- Band routing for the script's `agent()` calls. The issue scopes the launch check only.
- The ledger separation, which is #577 (AH-S216).

### Completion notes

- The installed client (Claude Code 2.1.280) declares the `Workflow` input as `script`, `name`,
  `scriptPath` or a run id, with `scriptPath` taking precedence over `script` and `name`, and a name
  resolving to "a predefined workflow (built-in or from .claude/workflows/)". The guard reads the
  same precedence; a name resolves to `.claude/workflows/<name>.js`, `.mjs` or `.ts` under the
  working directory, then under the home directory. A built-in workflow and a resume carry no text
  the hook can read, and are logged and allowed.
- A quoted `agentType` value is read directly. Any other `agentType` mention (a computed value, a
  shorthand property) makes any whole string literal naming a constrained role count, which errs
  towards refusing as `constrained_role` does for a contract it cannot load.
- A `harness-role:` marker in a script usually sits inside a string literal, so the script matcher
  also accepts a quote or a `\n` escape as the line boundary.
- The refusal is `role_deny` with an origin sentence, so its tail is the `Agent` refusal word for
  word.
- Every launch writes a `workflow-launch` row, `allow` or `deny`. The point is not added to
  `decisions.POINTS` or the controls list, as `framework-spawn` is not: nothing grades it yet and
  no `governance.jev` mode names it.
- Plan-mode behaviour is kept: a `Workflow` launch the user listed under `plan_allow_tools` is
  still allowed in plan mode when nothing refuses it.

## Review findings

CodeRabbit, round 1 on PR #847, three inline threads, all fixed:

- Major: a `scriptPath` file longer than the 1 MiB read limit ran in full but was judged only on its
  prefix. Fixed: the hook reads one character past the limit and refuses the launch.
- Major: `agentType: 'worker-a' && 'reviewer'` was read as the literal `worker-a`. Fixed: a literal
  counts only when a delimiter follows it, and a template literal with `${` counts as computed, so
  both fall to the literal scan. A value assembled from fragments such as `'revi' + 'ewer'` is still
  beyond a text scan.
- Major: the plan-mode `plan_allow_tools` answer had no test. Fixed: a test covers the allow and a
  refusal that wins over it.

CodeRabbit, round 2, one inline thread, fixed:

- Major: an escaped value such as `agentType: 're\u0076iewer'` evaluates to a role but matched no
  literal. Fixed: a string literal holding an escape is decoded before the computed-value scan
  checks it, wherever it sits in the script.

CodeRabbit, round 3 (a full review requested for the escape fix), three inline threads:

- Major, fixed: an escaped key, `{"agent\u0054ype": "reviewer"}`, hid the `agentType` mention.
- Major, fixed: `\x0a` escapes around a `harness-role:` line hid the marker. Both are caught by
  reading the script a second time with its escapes decoded, quote and backslash escapes kept so
  literals keep their bounds.
- Major, declined: a commented-out `// agentType: 'reviewer'` in a band-only script is refused. The
  guard leans towards refusing, and a comment stripper that misreads a string, template or regex
  literal would hide live code from the scan. Deleting the comment clears the refusal.
